## What it defines

The five tables of arch 09's "Documents and licenses" domain (arch 09 line 472: 5 tables; arch 09 gives no names), under Q-33's default (arch 09's shape, FS section 9 as the checklist), from FS line 736's document row and 02-contracts section 7 row K-35. Every table and column names its source in `documents-licenses.v1.tables.json`.

- **`documents`**: one document of a business, a team member, a space or thing, a booking or a customer. Either a paper a person gave as their own word (a license, insurance, a bond, a registration, background check or certificate, a family's legal papers or court order on file, or any other document they add), kept exactly as given and never checked, or a document Rosie built for its signers to sign or OK on the secure page (an agreement, contract, estimate, proposal, design or form, the business's own standard agreement for one service among them). Sources: FS line 736; FS rows Q02, Q10; S1-23, S1-29, S1-60, S1-61, S1-72, S1-81, S2-06, S2-11, S2-28, S2-29, A4-24, A4-25, A4-43, A5-19, A5-20, S13-11; MC C4, C7; D96; RULES 10.1 to 10.5.
- **`document_files`**: a photo or file uploaded with a given document (a license photo, an insurance certificate), kept private in R2: the row holds only its object key, sealed. Sources: FS line 736 ("file (secure)"); MC 8 "Files"; MC C10; S13-43; RULES 4.5; Q-31.
- **`document_texts`**: the exact words of a document Rosie built, per language, with their sha256 and the checked text's version. Sources: A5-20; S1-72; RULES 4.11; arch 09 line 492.
- **`document_signers`**: who a built document asks to sign or OK it. Sources: FS line 736 ("signers"); A5-20; S1-72.
- **`document_signatures`**: each signer's signature, written once: who, when, how (a tap or a typed name, on the secure page) and the hash of the exact words signed. Sources: FS line 736 ("signed_at"); A5-20; S1-72; A4-43; S13-38; RULES 4.10; S13-08.

### Which part owns what

Each fact has one home; this part names the others' rows by their keys and repeats none of their columns.

- **K-04 core** (frozen, #55) owns the business head (`businesses`, with `time_zone`), every person (`persons`: a signer, a giver, a customer), the booking head (`bookings`), the per-person sealing keys (`sealing_keys`, migration 0003, with `seal`, `unseal` and `erasePerson()` in `db/repo/sealing.ts`, T-182), the turns and the event log (every write here appends to it: arch 09 line 457).
- **K-22 people and access** (frozen, #109) owns the team member (`staff`): a team member's document names their staff row by K-22's key `staff_business_person_key` (`business_id`, `person_id`). K-22 also owns the owner's ID upload (`id_uploads`, MC C10): an ID document is never a document here. K-22's README already places "a person's license, certificate or background check (T08)" here, kept as given (S2-11).
- **K-23 business setup** (frozen, #78) owns spaces and things (`places_or_things`). FS line 741's "papers (document ids)" are the `documents` rows here that name the space or thing, so K-23 holds no papers column (K-23 v1 README).
- **K-25 services and prices** (frozen, #108) owns each service (`services`, whose id is stable: never deleted or re-keyed). The business's own standard agreement names the one service whose contract step it turns on (`documents.service_id`, held to the document's business by K-25's `services_id_business_key`: `documents_service_fk`), so K-25 holds no document column. K-25's services name their kind in K-24 (frozen, #89).
- **K-29 conversations and consent** (frozen, #59) owns every yes as a consent row. The owner's yes to the health privacy agreement (S1-72) is one of kind `health_agreement` (FS line 735), which Go live reads with this part's signed agreement. The commit that writes the signature here writes that consent row too, with the same words and sha256 (rule 9); no table here refers to K-29 (open gaps).
- **K-13 files port** (not frozen: T-022) owns the files themselves, in R2: a signed upload, a short signed read link with each view logged, and the delete for erasure under RULES 4.10. A row here holds only a file's object key, sealed, never the file or its bytes.
- **K-30 bookings and changes** (F15) owns a booking's secure link and its page answers; a booking's document names only K-04's booking head.

### FS line 736, field by field

- `id`: `documents.id`.
- `owner` (business, staff, place_or_thing, booking, customer): `documents.owner_kind`, with exactly the matching one of `staff_person_id`, `place_or_thing_id`, `booking_id` and `customer_person_id` set (`documents_owner_named`), and none for the business itself.
- `kind`: `documents.kind`, FS's eleven values and four more a person gives as their own word (`documents_kind_known`): `bond`, `legal_papers`, `court_order` and `other` (defaults 13 to 15).
- `name or number`: `documents.title` (what the paper is called, from the plug-in or the kind, plain) and `documents.number` (the number as given, sealed).
- `issuer`: `documents.issuer` (as given, sealed).
- `end_date`: `documents.ends` (the words given, sealed, never read as a date).
- `file (secure)`: `document_files` rows (the R2 object key, sealed, seen only on the secure page and in the portal).
- `shown_on_listing`: `documents.shown_on_listing`.
- `signers and signed_at`: `document_signers` rows, `document_signatures` rows (each with `signed_at`), and `documents.signed_by_all_at` once everyone has signed.
- **No "checked" column**: none here, and none that says verified or approved (`refuse-checked-column`).
- Beyond FS line 736: `documents.kind_id`, the kind of work a license or an agreement is for (the profession file's id, as K-23's `company_kinds.kind_id`), since the plug-in of a kind of work names its licenses (S1-60) and the agreement it needs (S1-71), and an unsigned agreement keeps that kind of work offline (S1-29, S1-31); and `documents.service_id`, the one service whose contract step the business's own standard agreement turns on (S1-29; FS row Q02, "O per service"; default 16).

### Kept as given, never checked (MC C4, C7; D96; RULES 10)

- A given document is optional, the business's or the person's own word, shown as given and never checked; nothing waits on it, and it never stands for the owner's control (S1-23: "Never: let a license stand for control (S1-75), say Rosie checked it, or make it required"). Switch verify stays off (MC C4; RULES 10.5), so no lookup result, status, lapse or end-date check is stored: `ends` is the words given, which Rosie never compares with a clock.
- "As given" means exactly as given, with who gave it (`given_by_person_id`), where (`given_via`: their chat, their secure page or the portal) and when (`added_at`). The number is the quoted words of the person's text or the page's field, never parsed or corrected. Neither application role may change a given value (rule 5: `refuse-as-given-edit`). A correction is a new document, and the old one is withdrawn as `replaced`.
- No column says Rosie checked, verified or approved a document (`refuse-checked-column`). The gives keys `license` (S1-23, S1-61) and `license_checked` (S2-11, S2-29) are the step graph's runtime record (build prompt 3.5): each is given when its step runs, whether or not the person added anything, since adding is optional. This part stores only what was added, as given (02-contracts section 8: "license_checked: K-35: person licenses kept as given (C4)").
- A document's photo or file is taken only on the secure page or in the portal, never kept from the chat (default 6: MC C10; RULES 4.5; S13-43's own line, "A license photo goes only on the secure page", though that step runs only with switch verify on): `refuse-file-from-chat`. A number may come by text (S1-23, S1-61).
- Customers see a document only as the business's own word (S13-11: "never as checked by Rosie"; C-196: "documents only as added by the business"), and only one whose `shown_on_listing` is true, or one the plug-in's rules want on the job (S13-13). Only the business's own papers may be shown: the business's, a team member's or a space's (`documents_listing_only_own_papers`). A customer's own document or a booking's never is, so the listing never says whether someone is a customer (RULES 4.9; S13-27 rules 35, 36; RULES 4.10): `refuse-customer-document-listed`. Work with no license shows no license claim (RULES 10.1).
- A bond is its own kind, `bond`, and never reads as insurance: the listing says "bonded" only for a bond and "insured" only for insurance, each as the business's own word (S1-23, S1-61, S13-11; default 13). Any other document the owner adds is `other` (FS row Q10: "upload anything"; default 14).

### Built documents and signatures (S1-72, A4-43, A5-19 to A5-23)

- Rosie builds an agreement, contract, estimate, proposal, design or form from the plug-in's and the owner's parts (A5-20: "Rosie builds the document from the price and the parts the plug-in and the owner require"; S1-72: the plug-in names the agreement). A built document has `origin` `built`, no given values (`documents_built_holds_no_given_values`) and its words in `document_texts`, one row per language, since "each signer reads it in their own language, from a checked text" (A5-20; RULES 4.11). The words are written once and never edited; `document_texts_words_sha256_match` holds the hash to them. A changed text is a new document.
- `document_signers` lists who must sign: the owner for the agreement the work needs (S1-72), or everyone the plug-in or the owner says must sign a booking's document, each on their own link the customer forwards (A5-20; MC C9: Rosie never texts them itself). "The business sending it is its signature" (A5-20), so the business is never a signer row. A co-signer the customer names gets a K-04 person first; nobody signs for someone else (A5-20).
- `document_signatures` holds each signature, written once: the signer row and person (`document_signatures_signer_fk` keeps both to the same document), when (`signed_at`), how (`tap` or `typed_name`, on the secure page) and the exact words signed (`document_signatures_text_fk` holds `words_sha256` equal to that text row's, of the same document). A typed name is sealed under the signer's key. Each signer signs once (`document_signatures_one_per_signer`). Neither application role may edit or delete one (`refuse-signature-edit`).
- When the last signer signs, the same commit sets `documents.signed_by_all_at` (A5-20's "All signed"), and every signature's commit raises the document's version, so two last signers cannot both leave it unset (rule 9). Once set it never changes, and it cannot be set while a signer has not signed (rule 11: `refuse-signed-by-all-moved`, `refuse-signed-by-all-before-signer`). The money step waits for it (A5-20). Go live reads an agreement the work needs (`kind_id` set) with none as left unsigned, and that kind of work stays offline, saved (S1-29, S1-31; S1-72: "Not signed now: setup goes on, but that work stays offline, saved"). Not everyone signed before the saved time ended: the clock withdraws it as `not_signed_in_time`, with no person (A5-23).
- **The business's own standard agreement** (S1-29: "can be signed once here, so a customer's signature completes it. That turns on its contract step for that service"; FS row Q02: "added once", "O per service"): a `documents` row of `owner_kind` `business`, `origin` `built` and `kind` `agreement`, with `service_id` naming the one service and no `kind_id` (`documents_standard_agreement_for_service`). Rosie builds it from the owner's own agreement, its words in `document_texts` per language from a checked text (RULES 4.11), as A5-20 builds from "the parts the plug-in and the owner require". Its one signer is the owner (a `document_signers` row, `signs_as` Owner), who signs it once on the Go live page. Its `signed_by_all_at` turns that service's contract step on (A5-19: "no document, unless Sam set one for this service"); each booking of the service then gets its own document built from those words, which the customer and anyone the plug-in names sign, the business's side being this signature and its sending (A5-20). Unsigned or withdrawn, it turns nothing on and keeps no work offline, since Go live's "Left unsigned" reads only agreements with a `kind_id`. One stands per service at a time (`documents_one_standard_agreement_per_service`); a new one replaces it (default 16).
- **Rosie's health privacy agreement** is signed once per business (S1-72's card: "Signed once, on the secure page"; S13-49: "at sign-up or when added later"). Its `kind_id` names the health kind it was first signed for. Go live reads it for every health kind the business has, one added later too, through K-29's consent of kind `health_agreement` for the business and the signed document with that consent's `words_sha256`, so a kind added later asks for no second signature (default 17). If that consent is revoked (K-29: a newer row with `revoked` true decides), the consent decides: Go live reads the agreement as unsigned and the health work stays offline, while this part's document and signature stay as the proof of the earlier yes (default 18).
- A signer's copy (A5-20: "each gets a copy") is made from the text and the signatures when it is sent; v1 stores no copy file (open gaps).

## Each table: writer, readers, scope, version, retention, sealing

### `documents`

- **Written by:** the action layer, in a turn's one commit (C-074, C-087): a paper texted in the owner's chat (S1-23, S1-61), a space's papers (S1-81), the agreement the work needs, built and sent to the owner (S1-72), and the business's own standard agreement for a service, built and sent to the owner to sign once at Go live (S1-29); the page calls behind the secure page and the owner console (K-21): a team member's paper on their page (S2-06, kept as added at S2-11 or S2-29), the owner's Documents page; with journeys 4 and 5, a booking's forms and documents built and sent (A4-43, A5-19), a family's legal papers or court order on the secure page (A4-24, A4-25), `signed_by_all_at` when the last signer signs and the version raised by every signature's commit (A5-20; rule 9), and the clock's withdrawal of one not signed in time (A5-23). Updates touch only `shown_on_listing`, `signed_by_all_at` and the withdrawn columns (rule 5).
- **Read by:** the business's owner, and an admin the owner lets manage the team or settings (K-22 `team_powers`), in the portal and by text; a team member reads their own papers on their secure page (S2-06's read-back says "as you gave it", never the number) and never another member's number; **a customer's own document and a booking's given document show their number, issuer and end only on the secure page**, to the person it is about and to the owner or that admin in the portal, each view logged, never in a text, an email, a call summary or a customer's AI (RULES 4.5: "ID numbers ... stay on the secure page"; K-22 v1 README: a person's own details are sealed and secure-page-only), and a legal paper or a court order keeps its kind and title there too (RULES 4.5: legal status, a child's details), so a text says only "Read it on the secure page." The columns' audience (customer, staff, owner) is the business's, a team member's and a space's papers', which customers see as S1-23, S2-06 and S13-11 give them; on a customer's or a booking's row the claim check (limit 7) and the slot filler hold those values to the secure page, as K-28 v1 does for `under_18` (default 19). A customer reads only a shown document's kind, title, number, issuer and end, as the business's own word, on the listing and with the work (S1-23; S13-11; S13-13); the person a document is about reads their own on their secure page; the composer's slot filler reads through limit 7's claim check, which holds each column to its audience (C-088, C-091). Never another business: row-level security.
- **Scope:** business (`business_id`, not null).
- **Version and repeats:** versioned; every update raises `version` by one (K-04's `enforce_version_raise`), and a commit compares and sets it. A retried write with the same id is refused by the primary key (rule 10).
- **Kept:** no row is deleted (no DELETE grant): documents are records, kept 7 years, or longer where the trade's rules say (RULES 4.10; S13-08; FS line 754). No shorter rule is invented (Q-31). A withdrawn document keeps its row.
- **Erasure:** `erasePerson()` (`db/repo/sealing.ts`, T-182; C-156) deletes the person's key, so `number`, `issuer` and `ends` of every document whose `person_id` is that person can never be read again (RULES 4.10's 45-day delete). The plain columns stay.
- **Sealed, column by column:** `number`, `issuer` and `ends`, under `person_id`'s key: a license number, an ID detail or anything taken from a document is personal data. Plain: `title` and `kind` (they name a paper, never a person's detail, and never carry the person's own words), `owner_kind`, the ids, `shown_on_listing`, `origin`, `given_via`, the times, `withdrawn_why` and `version`. Not kept at all: any checked, verified or approved value (D96), a lookup result (MC C4), and the person's own message words (K-04's `messages` hold those, sealed: CQ-54).

### `document_files`

- **Written by:** the page calls that take an upload on the secure page or in the portal, through K-13's signed upload (K-21: "a signed upload for ... license files"; S2-06), once per file.
- **Read by:** the person the document is about, on their own secure page, and the owner, or an admin the owner lets manage the team or settings, in the portal, each through K-13's short read link with each view logged (RULES 4.5: "These stay on the secure page, each view logged"). Never a customer, never in a text, an email or an AI's answer, never another business.
- **Scope:** business.
- **Version and repeats:** none: written once; no UPDATE or DELETE grant (rule 5). A retried upload with the same id is refused by the primary key.
- **Kept:** the row as long as its document; the R2 object private, with no deletion rule invented (Q-31).
- **Erasure:** deleting the person's key makes `object_key`, the only way to the file, unreadable. So the object itself is removed through K-13's delete for erasure under RULES 4.10 first, unsealing `object_key` while the key still exists, and only then is the key deleted; otherwise the object stays in R2 with nothing pointing to it (rule 8; K-13 and C-156, open gaps).
- **Sealed, column by column:** `object_key`, under `person_id`'s key (held to its document's person by `document_files_document_fk`). Plain: `content_type`, `uploaded_at`, `uploaded_via` and the ids. Not kept at all: the file or its bytes, which live only in R2.

### `document_texts`

- **Written by:** the call that builds and sends a document (S1-72; A4-43; A5-19), once per language.
- **Read by:** each signer on their secure page and in their copy (A5-20), and the owner in the portal; never another business.
- **Scope:** business.
- **Version and repeats:** none: written once, never edited (no UPDATE or DELETE grant); one text per document and language (`document_texts_one_per_language`).
- **Kept:** 7 years with its signatures (S13-08: "contracts and every yes are kept 7 years"; FS line 754).
- **Erasure:** nothing here is sealed: the words shown and their hash are the proof that survives a person's key being deleted (arch 09 line 492; RULES 4.10: "the proof of every yes stay"), as K-29's consent words are.
- **Sealed, column by column:** none, on purpose. The builder keeps a private detail out of the words and points to the secure page instead (RULES 4.5; open gaps).

### `document_signers`

- **Written by:** the call that sends a built document, once per signer.
- **Read by:** each signer, their own row, on their secure page; the customer whose booking it is (who still has to sign: A5-20); the owner in the portal; never another business.
- **Scope:** business.
- **Version and repeats:** none: written once; one row per person and document (`document_signers_one_per_person`).
- **Kept:** with its document.
- **Erasure:** nothing here is sealed; `signs_as` is a role in the plug-in's or the owner's words (such as Owner or Customer), never a name, and the person id is opaque.
- **Sealed, column by column:** none. Plain: `signs_as`, `asked_at` and the ids.

### `document_signatures`

- **Written by:** the secure page's sign call, once per signer (S1-72; A4-43; A5-20), which takes the signer from their own link and never from the page (rule 9); each one's commit raises its document's version, and the commit that writes the last one also sets `documents.signed_by_all_at` (rules 9 and 11).
- **Read by:** the signer, their own; the owner in the portal (who signed and when); the customer whose booking it is (whether everyone has signed); a typed name only on the secure page; never another business.
- **Scope:** business.
- **Version and repeats:** none: written once, insert only, never edited or deleted (`refuse-signature-edit`); each signer signs once (`document_signatures_one_per_signer`).
- **Kept:** 7 years (S13-08), and after a delete (RULES 4.10: "The ... proof of every yes stay").
- **Erasure:** deleting the signer's key makes `typed_name` unreadable; who signed (the opaque person id), when, how and the hash of the words signed stay as the proof (arch 09 line 492).
- **Sealed, column by column:** `typed_name`, under the signer's key (`person_id`, held to the signer row's person by `document_signatures_signer_fk`). Plain: `how`, `signed_at`, `words_sha256`, `channel` and the ids.

## Database rules beyond the table list

The table list's meta-schema has no place for these; the migrations must produce them too, and T-112 checks them.

1. **Same schema as core:** the five tables live beside K-04's, K-22's, K-23's and K-25's tables, and their foreign keys name `businesses.id`, `persons.id` and `bookings.id` (K-04), `staff (business_id, person_id)` (K-22's `staff_business_person_key`), `places_or_things.id` (K-23) and `services (id, business_id)` (K-25's `services_id_business_key`, whose services name K-24's kinds), with no schema prefix. No table here refers to K-29, K-13 or K-30, and none of theirs to these. One seed loads K-29's `seed-consent-health-agreement` (Lee Nutrition Clinic and Sam's consent row) and one refused fixture K-25's `seed-services-price-list`, so the contract test migrates K-24, K-25 and K-29 too.
2. **Versions:** `documents` has `version integer not null default 1` and the BEFORE UPDATE trigger `documents_version_raised`, which runs K-04's `enforce_version_raise()` (migration 0002): an update must raise the version by exactly one, else SQLSTATE 23514, and a commit compares and sets it (arch 01 line 85; K-04 v1 rule 2). The other four tables are written once and carry none.
3. **Ids** are `text`: opaque strings code makes and never parses (CQ-09).
4. **Row-level security per business** (arch 10 line 546; K-04 v1 rule 4): all five tables are scoped by `business_id`, which is not null in every one, so each row is its business's alone and no other business scope sees it (RULES 4.10: "never joined across businesses"; S13-42). The runtime side reads unscoped only for jobs that work by person across businesses: the 45-day copy or delete (C-156; RULES 4.10).
5. **Grants, the same for both application roles** (the Tool API role and the runtime side): `SELECT` and `INSERT` on all five tables; `UPDATE` on `documents` only of `shown_on_listing`, `signed_by_all_at`, `withdrawn_at`, `withdrawn_why`, `withdrawn_by_person_id` and `version`; no `UPDATE` on the other four; no `DELETE` on any. So what a person gave, and what a document is (`title`, `kind`, `kind_id`, `service_id`, `number`, `issuer`, `ends`, the owner columns, `person_id`, `origin`, `given_by_person_id`, `given_via`, `added_at`), never changes (SQLSTATE 42501: `refuse-as-given-edit`), a file, a text, a signer and a signature are never edited (42501: `refuse-signature-edit`), and nothing is deleted. Only the tables' owner, the migrations' role, holds more, as K-29 v1 does for `consents`.
6. **Sealed fields:** `documents.number`, `documents.issuer`, `documents.ends` and `document_files.object_key`, each under `person_id`'s key, and `document_signatures.typed_name` under the signer's (`person_id`), in K-04's `sealing_keys` (arch 01 line 93; K-04 v1 rule 6; migration 0003, with `seal`, `unseal` and `erasePerson()` in `db/repo/sealing.ts`, T-182). A sealed value carries its person's id as authenticated data, so it cannot be moved to another person's row. The wrapping key is a Workers secret, named and never stored (rule 7). Every write here appends to the event log (arch 09 line 457); a sealed value it copies there goes only in `event_log.sealed_values`, sealed under the same person's key (K-04 v1 rule 6), never in plain. A document's `person_id` is the person it is about: the team member or the customer for their own (`documents_sealed_for_owner`), the person who gave a business's or a space's paper (`documents_paper_sealed_for_giver`), and for a built document the person it is for.
7. **Times and zones:** every time here is a `timestamptz`, an instant in UTC (CQ-09). It is shown in the business's zone (K-04 `businesses.time_zone`), or for a booking's document in the visit's zone, else the business's (S13-03; CQ-05's default, as K-25 v1 reads its time conditions). No column holds a local clock time or a parsed date: `ends` is the words given, and Rosie never compares it with a clock (MC C4).
8. **Kept and erased:** no application role deletes a row (rule 5); rows are records kept 7 years, or longer where the trade's rules say (RULES 4.10; S13-08; FS line 754), with no shorter deletion rule invented (Q-31). Files stay private in R2 with no deletion rule invented (Q-31). A person's delete within 45 days (RULES 4.10) deletes their key: every value sealed under it here (a document's number, issuer and end, a file's object key, a typed name) can never be read again, while the proof of every signature stays (who by id, when, how, the words' hash and the words shown: arch 09 line 492). The R2 objects of that person's files are removed through K-13's delete for erasure before the key is deleted, since the key is the only way to unseal their `object_key` (K-13 and C-156: open gaps).
9. **Rules across tables, kept by code** (not constraints): a booking's document's `person_id` is that booking's person served (K-04 `bookings.served_person_id`); a booking and a space named here belong to the document's business (K-04 v1 and K-23 v1 give `bookings` and `places_or_things` no key on their id with the business, so the foreign keys hold the id alone); a given document has files and no texts or signers, and a built one has texts and signers and no files; a built document is inserted with `signed_by_all_at` null, and it is set in the update of the commit that writes the last signer's signature, and only then (rule 11 refuses an update that sets it early, moves it or clears it; an insert is code's, since its signers come after it); each signature's commit also updates its document, raising the version read by one (compare and set, K-04 v1 rule 2), so of two last signers signing at once one commit is refused and retried and sets it, and limit 4 sees each new signature; no signer is added once `signed_by_all_at` is set; a signature is written only by the sign call of the signer's own link (K-21's secure page, K-30's links), which takes the person from that link and never from the page, since an application role in scope may insert a signature row for any signer (A5-20: "Never: sign for someone"); a customer's or a booking's number, issuer and end, and a legal paper's or a court order's kind and title, go only to the secure page (the claim check, limit 7; documents' readers); a signature's `signed_at` is not before its signer's `asked_at`; for S1-72, K-29's `consents` row of kind `health_agreement` is written in the same commit as the signature, for the same person and business, with the same words and `words_sha256` and `at` equal to `signed_at`; `title` never holds words the person typed.
10. **Repeats:** each row's id is made by code once per write (CQ-09), so a write retried with the same id is refused by its primary key (SQLSTATE 23505) and nothing is written twice; a turn's writes ride its one commit, which K-05 makes once per turn id. A signer is asked once per document (`document_signers_one_per_person`) and signs once (`document_signatures_one_per_signer`), and a document has one text per language (`document_texts_one_per_language`), each refused with 23505 when repeated.
11. **Signed by all, set once:** `documents` has a second BEFORE UPDATE trigger, `documents_signed_by_all_once`, running this part's function `documents_signed_by_all_once()`. It refuses an update that changes `signed_by_all_at` once it is set (moves or clears it), and one that sets it while the document has no `document_signers` row or any of its signer rows has no `document_signatures` row (matched by `signer_id`). Each refusal is SQLSTATE 23514 naming the constraint `documents_signed_by_all_once`, as K-04's `enforce_version_raise()` names `<table>_version_raised` (`refuse-signed-by-all-moved`, `refuse-signed-by-all-before-signer`). The function reads the signer and signature rows as the calling role, so row-level security shows it its own business's, and a call that sees no signer is refused. It fires on update only: a built document is inserted before its signer rows (their foreign key), so an insert's `signed_by_all_at` is code's (rule 9), and a seed loads a signed document as it stands (`seed-agreement-signed`). Any other update (the version alone, `shown_on_listing`, a withdrawal) passes it.
