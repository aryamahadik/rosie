### Which part owns what

One fact lives in one place: this part names other parts' rows by their keys and copies none of their values.

- **K-04 core** (frozen) owns the booking head (its stage: entry, booked, checked_in, done, cancelled), reservations (the booked time and the worker), persons, handles, turns, open questions (every question asked here: a late notice's, a no-show's, the owner's OK of a price, the customer's answer to it, A8-47's question to the owner, the visit check's), clock rows (the 30-minute waits, the waits at the door, the night check, the next day's visit check, each day list's hour, the on-my-way nudge) and outbox rows. The commit that writes the first check-in, or the end of a booking's last visit, here moves the head's stage in the same commit (rule 10); no head column is repeated here.
- **K-30 bookings and changes** (frozen) owns the visit (`booking_visits`) with its sealed check-in code, which this part never copies: a check-in compares the typed code with it in code, and a wrong try keeps only its time. It owns the booking lines with their prices copied in, which a DONE line names; moves, cancels and stand-ins (`booking_changes`), which a late notice's 2 or 3 writes with no fee; and the secure page's sealed answers (gate and door codes, access notes, an entry code sent for a failed way in: B8-52).
- **K-32 money** (frozen) owns payments (a rest taken at the visit, 'DONE paid 100' or 'paid cash', is its payment), the one late-cancel or no-show fee per visit (`booking_fees`, asked only after the no-show here has its outcome, carrying the customer's reply when they gave one, or saying the mark was set on silence: S11-22, B8-11) and Rosfield's $2 (`rosfield_fees`, counted at the first check-in code or DONE recorded here, `counted_by` check_in_code or done; in flow B a check-in at the door counts only once nothing required is missing, so one that ends `not_started` counts no $2: B8-04, B8-60, B8-61). An extra's payment item names no line yet (K-32 v1 open gaps: "until K-31 names them"); `visit_price_lines.id` is that name, for a K-32 minor version.
- **K-34 safety and incidents** (frozen) owns the check-out timer for a pro alone (B8-86) and every safety outcome and hold; a visit stopped for safety records here only that it stopped and on whose side.
- **K-22 people and access** (frozen) owns staff, their day-list time (`staff.day_list_time`) and who may OK what; **K-26 rules** (frozen) owns the price OK limits and the owner's rules a price at the visit names; **K-13 files** owns the photos and receipts whose object keys this part keeps; **K-08 event and trace** (frozen) gives the owner's answer its shape (`visit_prices.owner_*`, as K-30's `owner_oks`).

### Check-in and DONE (A8-03 to A8-10, A8-70, A8-87; B8-03 to B8-08, B8-40, B8-41)

- **The code confirms the visit**: the customer gives it at the chair, the door or the start of a video visit, and the pro's own phone or the desk's Today page enters it (`checked_in_via`), so 'checked in' shows who came. Codes are 4 digits, new each visit, sealed in K-30 under the key of whoever gets them; this part keeps no digit. A typed code is checked once more, never guessed: `wrong_try_1_at` to `wrong_try_3_at` hold the times of three wrong tries in a row; after the third no code is taken (`visit_marks_code_before_third`), the owner is told (`tries_told_at`; in flow B the customer too) and DONE at the end counts the visit. With no code (the phone is away: `no_code_at`), DONE confirms it. A class roster, a drop-off's code, a mail-in's arrival and a self check-in (ID on the secure page, 'I've left' to close: `left_at`) are the other ways in. In flow A the code is taken only once nothing required is missing (A8-02); in flow B the door check comes first, so `checked_in_at` is written at the door and the ready check follows (B8-03, B8-04, B8-45), and the visit counts only once nothing required is missing.
- **One event, one moment** (A8-87): a visit ends once. `done` comes from the pro's DONE (with its lines: a `visit_prices` row of kind done, `done_price_id`), the desk, the owner's 1 Yes, mark it done when nothing was entered by night (the bill goes as booked, so no lines: Q-13 gives it `visit_done` in both flows), or the code itself when nothing is billed after and no date was promised (`done_via` code, nobody's DONE). `part` is PART, priced for what was done. `not_started` names whose side, as a text may say it: the customer's or the shop's (`side`: A8-51, A8-56, A8-61); whether the customer's side was their own state is `customer_state`, shown only on the secure page (A8-81, B8-76: why a person was turned away never goes in a text). `stopped` names why: safety or conduct, which an owner text may say (`stopped_why`: A8-40, A8-80), or a finding or a first step's result, shown only on the secure page (`stopped_found`: A8-35, A8-72, B8-90: "The text says only 'result added'"). The details of either go only on the secure page. `door_shut` (B8-07: not the pro) and `didnt_happen` (A8-47's 2) are visits never met. One DONE per visit: a job over several days gets it on its last day (B8-40), each earlier day checked in with its own code.
- **DONE's photo and date**: nobody home needs a photo with DONE (`photo_key`, an object key in K-13's private store), which rides on the bill or the receipt; a report promised by a date is DONE's `report_by`.

### No-shows (A8-14 to A8-16; B8-10 to B8-12; FS line 623)

- Marked 15 minutes after the start (10 for a video or phone session nobody joined) by the pro or the desk; code holds the time to the visit's start, a later start a late notice gave first (rule 10).
- **Marked by a clock's silence** (flow B): a failed way in waits 15 minutes for a new one (B8-52), and only a child home waits 30 minutes for an adult (B8-09); silence "goes on as nobody home", so the clock's turn marks the no-show with `marked_via` clock and no person (`no_shows_marked_by`; default 15). The pro whose wait ran out is the `by_person_id` of the visit event that started the wait, so no commit invents who marked it, and the fee question can say the mark was set on silence (B8-11, S11-22).
- **Safety first**: where the person may be unable to answer (the plug-in's welfare switch, someone on the booking in care, or a booker who said so: `welfare_first`), no fee or no-show words go until they are found safe (`found_safe_at`; `no_shows_asked_after_safe`). Not reached in 30 minutes, the owner is told and the plug-in's welfare plan runs (`owner_told_at`). Rosie's own messages go by text to open chats and by email, and Rosie places no call; the business's calls are its own (Q-06).
- **The customer is heard** before the owner decides anything: asked to reply within 30 minutes (`asked_at`, `reply_by`, a CHECK), their reply (here, on the way, cancelled, an emergency), and the outcome: checked in after all (a normal visit), not met (heard but not met, after any reply: they said they were there or on the way and still could not be met, replied with an emergency, or said "I cancelled" when the record shows no cancel; nothing charged now: `no_shows_not_met_after_reply`; default 16), no visit (only after the 30 minutes pass with no reply: `no_shows_no_visit_after_silence`, so the owner never reads "didn't answer" for someone who replied: A8-14, B8-10), or cancelled first (a cancel on record). The 30-minute clock or the reply's own turn may close a mark the customer answered. Any fee is K-32's question to the owner, with the reply in their words only if nothing private (A8-14, B8-11); silence charges nothing.

### The late row and its fan-out (arch 09 line 484; A7-14; B7-18)

A worker running late is one `late_reports` row: the pro's LATE N, or a visit running long so that the next customer will start late (A7-14; A8-33). Code fans it out to that worker's later visits that day at that business, each as its own `visit_events` row of kind late with its own question (`visit_events_late` requires it) and the new start ('your 11:00am starts about 11:20am') or window ('New time: arriving 8:20–10:20am'). The customer keeps it (1, or no reply), moves it or cancels, both free: a move or cancel is K-30's change row; a later start that stands moves nothing in K-04 or K-30, but it is the start a no-show is counted from (rule 10), and a start the business moved, kept on silence, carries no no-show fee unless a person reached them first.

### Prices and extras at the visit (A8-24 to A8-49, A8-88; B8-19 to B8-26, B8-48, B8-49, B8-77, B8-92, B8-93)

- A service priced at the visit (only the consult or service call was promised: `included_cents`) and an extra (more work, more time or another way) are priced first, with their lines. Where the owner's limit (K-26 `price_ok_limits`) or rule (K-26 `rules`: 'At the shop, only Sam OKs prices made at the chair') asks, the owner is asked at once, with 30 minutes before the customer hears it is with them (`owner_answer_by`, a CHECK), one reminder, and the answer in K-08's ownerYes fields; nothing is shown before 1 Send it (`visit_prices_shown_after_ok`). 2 Change it, or the customer's asked change, is a new price naming the one it replaces (once each).
- The customer's own yes: in their own chat, on their secure page, on the pro's or the shop's phone (saved with the time and the pro's name, a copy to their own mobile) or through the owner's call (`yes_where`); 3 OK some lines marks each line yes or no (`customer_ok`), and what is left stays good 7 days (`good_until`). A price still waiting for the owner, or no answer after one reminder, goes as not today (only what was promised) or none (nothing priced is done).
- DONE's and PART's totals and lines are prices of kind done or part: the booked work names its K-30 line (whose price was copied in at booking), agreed work names the line the customer OK'd, parts at cost carry the store's receipt (`receipt_key`), and after Not today DONE carries only the visit fee. A DONE total over the owner's limit waits for the owner the same way (A8-37: 'No OK in 30 minutes: the bill or charge waits').

### The visit check (D98; FS lines 624, 670, 740; A8-47, B8-47)

The day after a booking Rosie brought in (K-30 door ai, page or chat) that had no check-in code and no DONE by night, the customer is asked once, their way and in text hours, 'Did your visit with <business> happen?'. Not for sensitive work, a private booking or a number that sent STOP. The answer is recorded only, for Rosie's team: no charge, refund, fee or other action follows, and the business never sees it. The check runs whatever the owner answered to A8-47's own question that night, since A8-47 lists both asks in one step (`seed-visit-check`: the owner marks it done, the customer says No, and nothing follows). `visit_checks` has no Tool API grant, and its question and outbox row carry no business (QUESTIONS.md CQ-56's default), so no business scope sees any of it.

### Day lists, on my way and the door (A8-01; B8-01, B8-02, B8-91; B8-03, B8-07, B8-09, B8-52)

- A day list goes once per staff member, business and day, at their own day-list time (K-22), else the staff text hour; a visit before that hour goes on the evening before's list (`day_lists_sent_that_day_or_the_evening_before`), and a booking added after it goes at once in its own text. Answers, notes and gate codes open only on the signed-in page; no list holds them. Which visits a list held is read from K-04's reservations, not stored.
- On my way (flow B): the person who meets the pro gets the pro's name and photo, the arrival time (`arrives_about`; a sent-now job's minutes in `minutes`) and the code; no OMW by 30 minutes after the window opens nudges the pro, then the owner (a K-04 clock). Live job updates go whenever the job runs (B8-01's rule).
- At the door: 2 It isn't Jordan keeps the door shut while the owner reaches the customer (`not_the_pro`, then `was_the_pro`, or the visit ends `door_shut`); only a child home waits up to 30 minutes for an adult; a failed way in asks for a new one on the secure page within 15 minutes (`wait_until`, CHECKs), and the new code itself is a K-30 page answer, never kept here.

### Times (rule 9)

Every instant is `timestamptz` in UTC and is shown in the visit's zone: K-30's `booking_addresses.zone` for a visit at the customer's place, else the business's `time_zone` (S13-03; CQ-05; K-30 rule 9). The day columns read their day in the business's zone, kept with them (`late_reports.day` and `zone`, `day_lists.day` and `zone`, CHECKed against the instant); `good_until` and `report_by` are days in the visit's zone. The 30-minute and 15-minute waits are CHECKs; the 15 minutes before a no-show and 7 days of `good_until` are code's (they need the visit's start and zone).

### Money (rule 9)

Every amount is integer minor units in `bigint` (cents for USD) with its three-letter currency, never a decimal (CQ-09; K-30 and K-32 'Money'): `'160.00'` as cents is refused by the type (22P02). This part prices what is done at the visit; it never charges, holds or refunds: the payments, the fee and the $2 are K-32's, and a booking's line keeps the price it was made with (RULES 3.7).

## Database rules beyond the table list

The table list's meta-schema has no place for these; the migrations must produce them too, and T-108 checks them.

1. **Same schema as core:** the 8 tables live beside K-04's and the other parts' tables, and their foreign keys name them by key with no schema prefix (`booking_visits (id, booking_id)`, `booking_visits.id`, `businesses.id`, `persons.id`, `handles.id`, `turns.id`, `open_questions.id`, `outbox_rows.id`, `booking_lines.id`, `price_ok_limits.id`, `rules.id`). The migration runs after K-30's (C-166) and K-26's, and creates `visit_prices` before `visit_marks` and `visit_price_lines`, and `late_reports` before `visit_events`.
2. **Extensions:** none beyond K-04's (`btree_gist`); `tstzrange` is built in, and no PostGIS type is used here.
3. **Ids** are `text`, opaque strings code makes (CQ-09).
4. **Versions:** `visit_marks`, `visit_prices`, `visit_price_lines`, `no_shows` and `visit_checks` have `version integer not null default 1`, raised by every update and compared and set by a commit (arch 01 line 85; K-04 v1 rule 2). `visit_events`, `late_reports` and `day_lists` are only inserted and carry none.
5. **Row-level security per business** (arch 10 line 546; K-04 v1 rule 4): every table but `visit_checks` is scoped by `business_id`, read and written by a Tool API call only in its own business (`business_id = nullif(current_setting('rosie.business_id', true), '')`, the policy's `USING` and `WITH CHECK`). K-04's head, K-30's visits and lines and the other rows named here have no `(id, business_id)` key, so on the Tool API's insert and update policy, in `WITH CHECK` only, each of these columns a row carries must name a row of the same business: `(<col> is null or exists (select 1 from <table> r where r.id = <row>.<col> and r.business_id = <row>.business_id))`, for `booking_id` (`bookings`) on `visit_marks`, `visit_prices`, `no_shows` and `visit_events`; `owner_open_question_id` and `customer_open_question_id` (`open_questions`), `price_ok_limit_id` (`price_ok_limits`) and `rule_id` (`rules`) on `visit_prices`; `open_question_id` (`open_questions`) on `no_shows` and `visit_events`; `booking_line_id` (`booking_lines`) on `visit_price_lines`; `from_visit_id` (`booking_visits`) on `late_reports`; `outbox_row_id` (`outbox_rows`) on `day_lists`. Their own row-level security limits the subquery to the call's scope, so a call can never attach a row to another business's booking, question, limit, rule, line, visit or text (`refuse-mark-on-other-business-visit`, 42501).
