### Who owns what (K-23, K-01, K-37 and this part)

One fact lives in one place. Where another part already holds a field, this part refers to it and never repeats it.

- **The trade's defaults** (what a kind of work starts from) are this part's: `kinds` (name, style, pattern, facts) and `kind_flows` (money paths, switches, arrive, cutoff), written from the compiled bundle (K-01 `tradeOverlay` and `tradeFlow`), so the database and the bundle agree. The rest of a trade file (its money examples, amounts, services, booking values, labels, renames, ops, slot rows) is K-01's bundle, never stored here.
- **A business's own values** are K-23's: the company of each kind, its trade name, and its facts and the switches on in each flow (`company_kinds`, written at S1-04 from the defaults here or the draft's blocks, then the owner's); the business's default free-cancel time and arrival per flow (`flow_defaults`, H06 and H07, typed). This part never repeats them.
- **A business's plug-in text blocks** are this part's (`picked_kind_texts`): K-23's README places `extras` here (row K-24; MC R3). The typed plug-in keys never come here: `picked_kind_texts_key_known` takes only the 11 free-text keys, the ones T-143's key map sends to `pluginText/<key>` (Q-39).
- **A pick and its company:** once S1-04 places a pick, `(company_id, kind_id)` is a row of K-23's `company_kinds` (`picked_kinds_company_kind_fk`), and `(company_id, business_id)` is the company's own (`picked_kinds_company_business_fk`, on K-23's `companies_id_business_key`). `picked_kinds_one_per_company_kind` keeps one pick, so one set of text blocks, per company kind.
- **The team's review of a draft** is K-37's `review_items` row of kind `new_work`, with `subject_table` `new_work_drafts` and `subject_row_id` the draft's id (K-37 left the table name open until this part froze); its due time, decision and who decided live there. The decision's effect is written here as the draft's `state`.
- **Which fact and switch names exist** is K-26's closed registry (arch 09 line 480); here names are only checked for form (lowercase letters and digits).

### The kinds (S1-02, S1-03, Q-42)

- `kinds.id` is the trade file's name for the 243 (as `company_kinds.kind_id`), and `new-` plus an id code makes for a drafted kind (`kinds_new_work_id`), so a drafted kind never takes a trade file's id. Code makes a drafted id unique (two owners may both draft "pack hikes").
- `facts` is the trade file's `pf.facts` after MC C5's fill (insurance: video, forms, firststeps, documents). Null means no facts list, so every fact-gated branch shows (SPEC-master 5d), as K-01's `tradeOverlay.facts`; after C5 no trade-file row is null. A drafted kind's facts are its checklist's, so its `facts` is always null (`kinds_drafted_facts_on_draft`).
- **The kind matcher** (C-130; Q-42; QUESTIONS.md M4.1): v1 stores no index and names no model. The matcher reads the catalog as data: `kinds.name`, `style` and `pattern` of the rows whose `source` is `trade_file`. If the spike (T-631) shows a stored index is needed, the architect freezes an additive K-24 version and one migration adds it (M4.1's default).

### The flows (money paths, switches, settings)

- Two rows per trade-file kind (SPEC-prof 1: both flows in full). `main_combo` is one of `combos` (`kind_flows_main_listed`); each path is `price|before|after`; `counter` is a flow A after and `own` a flow B after (K-01 v1 `after`).
- `switches_on` is K-01's `tradeFlow.switches`: `pf.switches` split per flow, every switch not named off. `no2` comes from the trade's choice at the $2 split S1-62; every trade file of fixture set v1 keeps the $2 (FS line 562: `no2` is never on).
- `arrive` and `arrive_window_hours` hold `"setstart"`, `"window"` or `{ "window": N }`; `cutoff` the free-cancel time as the file words it ("24 hours before", "6pm the day before", "7am the day of"), free text (FS line 294). MC C5: a trade with no `pf.settings`, or none for a flow, starts at window with an empty cutoff (null). K-23's `flow_defaults` types the business's own (a span, or a clock time the day before).

### Picks, text blocks and drafts (S1-02, S1-11, S1-03)

- **Order of sign-up:** S1-02 gives `kinds`, S1-11 loads each kind's plug-in, S1-04 gives companies and S1-09 the business (master-A.json's section 1 order). So a pick and its text blocks exist before any company or business: `company_id` and `business_id` are null until S1-04 places the pick, and code sets the business on the pick, its text blocks and its draft in the same commit. Such rows are seen by no business scope; sign-up's turns read and write them on the runtime side (K-23 rule 5).
- **Outcomes** follow S1-02's three branches: `listed` names a trade-file kind; `new_work` names the drafted kind (`picked_kinds_outcome_matches_kind`); `not_booked` names none and is never placed (S1-74: "sets nothing up"), but is kept so Rosie's team can see the owner's words within 1 business day.
- **Text blocks:** for a listed kind each block is the trade file's value written as JSON text, unchanged (`JSON.stringify` of the value as parsed: K-01 `pluginText`, T-133's loader), checked with `block is json`. S1-11 loads a kind's blocks when the owner gets to it ("the barbershop's now, and plumbing's and electrical's when Sam gets to them"), so a pick may have none yet. A missing block reads as its safe default (S1-11: "Plug-in silent anywhere: the safe default each silent read names"). No code and no screen reads a sub-key by name (FS line 748).
- **Drafts:** one per `new_work` pick (`new_work_drafts_one_per_pick`); offline until `approved`. Each block of S1-03's checklist starts from its safe default; a row holds only an answer or a clear no (`answered`, `no`), and a no sets nothing (`new_work_draft_blocks_no_sets_nothing`). The protective facts (contracts, crews and forms) stay on unless a clear no turns them off; which facts the draft ends with is code's, read from these rows, and lands in K-23's `company_kinds` once the kind has a company.

## Database rules beyond the table list

The table list's meta-schema has no place for these; the migrations must produce them too, and the contract test checks them.

1. **Same schema as core:** the six tables live beside K-04's and K-23's tables, and their foreign keys name them by their keys (`persons.id`, `businesses.id`, `companies (id, business_id)`, `company_kinds (company_id, kind_id)`) with no schema prefix. Nothing here refers to K-37; K-37's review item refers to `new_work_drafts` by name and id.
2. **Row-level security** (arch 10 line 546; K-04 v1 rule 4): `picked_kinds`, `picked_kind_texts`, `new_work_drafts` and `new_work_draft_blocks` are scoped by `business_id`; a row whose business is null is seen by no business scope. `kinds` and `kind_flows` are the shared catalog (scope none): the Tool API roles may select them and never insert, update or delete (refused 42501); the catalog seed job and the runtime side (S1-03's drafted kinds) write them.
3. **Versions:** every table here is updated, so each has `version integer not null default 1`, raised by every update and compared and set by a commit (arch 01 line 85; K-04 v1 rule 2).
4. **Ids** are `text`. `kinds.id` is the trade file's id or `new-...`; the other ids are opaque strings code makes (CQ-09).
5. **Arrays:** `facts`, `combos`, `switches_on`, `facts_on` are `text[]`; a fixture gives them as a JSON array (K-04's fixture format). `kinds.facts` may be null; the others are not null.
6. **JSON text:** `picked_kind_texts.block` is `text` checked with the SQL/JSON `is json` predicate (PostgreSQL 16 and later; Q-21's local PostgreSQL is 17), not `jsonb`, so the block keeps the trade file's text exactly as K-01 holds it.
7. **The catalog seed** is written per bundle from the compiled trade overlays (C-155 after F14: 02-contracts section 7 notes): one `kinds` row and two `kind_flows` rows per trade file, the same values as K-01's `tradeOverlay`. A business's picks and blocks are copies made at sign-up and are never rewritten by a new bundle (open gaps).

## Seed and refused-row fixtures (`fixtures/`, listed in `fixtures/index.json`)

## Open gaps

- **The foreign key from K-23's `company_kinds.kind_id` to `kinds.id`**, which K-23's README leaves to K-24: a foreign key belongs to its own table's entry, so it is a change to K-23's frozen table list (proposed: K-23 v1.1 adds `company_kinds_kind_fk`, a new task for the lead after this merge). - **The owner's price list** S1-03 drafts from (a file through K-21's signed upload, K-13) and its services (K-25, S1-12): no column here; the draft refers to neither until K-25 and K-13 freeze.
