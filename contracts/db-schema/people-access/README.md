### Where each field of FS line 723 (staff) lives

- In K-04 core: `id` of the person, `name` (`persons.name`), `role` (owner, admin, staff, own business: `person_roles.role`), and when a removed person's role ended (`person_roles.ended_at`).
- Here: `business_id`, `mobile` (T02), `agreed_to_text_at` (T03, as `agreed_to_text_ticked_at` and who), `status`, `skills` (T04, as `staff_skills` rows), `supervisor` (T07), `languages` (T09), `day_list_time` (T10), `video_link` (L06, with `calls_customer_mobile`), `emergency_contact` (T11, as `emergency_contacts`), `on_call` (T12, as `on_call` rows); who may OK what (T05) as `team_powers`.
- Elsewhere: `price` (T06) is K-25's: 02-contracts section 8 puts staff prices there ("team: K-22 skills, who OKs what, supervision; K-25: staff prices (FS T06)"), as a price rule by worker with effective dates (02-contracts row K-25; arch 09 line 488); `calendar_link` is K-27's (calendar links per person, tokens sealed); a person's license, certificate or background check (T08) is K-35's (kept as given, S2-11); the staff invite's chat link and the person's own texts yes are K-29's `chat_links` (purpose `staff_invite`) and `consents` (kind `texts`).

### Joining under C9 (S2-05; Q-08)

- S2-02 adds a person only after the owner's tick that they agreed to a text (`agreed_to_text_ticked_at`, NOT NULL; Q-08 keeps it). Status starts `invited`; Rosie sends no invite text (C9): the owner gets that person's chat link (K-29 `chat_links`, `staff_invite`, found by business and person) to pass on.
- Their sent ready text is their yes to join. It counts only from the mobile the owner gave: `staff_joined_from_own_mobile` holds `joined_from_number = mobile`, so a ready text from another mobile cannot join anyone (Q-08) and takes S2-09's wrong-number path (`wrong_number_at`).
- Nobody is offered to customers before joining and the owner's yes (`staff_bookable_after_join`; S2-07, S2-22); `bookable_at` is S2-24's `staff_live`.
- A STOP (S2-08; RULES 7.7) sets `stopped`; START returns them to `joined` (or `invited`) and `stopped_at` keeps the last stop. Removal sets `removed` and ends the core role in the same commit.

### The owner's mobile, email and ID (S1-10; C9; C10)

- The mobile is proven by the owner's own text from it to Rosie's number (C9: no code is texted to a mobile that has not texted in); `accounts.mobile_proven_at` records it, and the phone row is core's. The email is proven by a code typed on the page (`proof_codes`, purpose `owner_email`; `accounts.email_proven_at`).
- The ID is an upload on the secure page, never in the chat, accepted as given: a `sign_up` row in `id_uploads` is "the ID confirmed" (S1-10 gives `id_checked`; S1-32's ID half). No face match or video check runs, so nothing of a face is stored. The file stays private in R2 (Q-31); its object key is sealed under the owner's key, so deleting the key erases the way to the file. The ID-check service C10 adds later behind a switch has no column until Jay turns it on (02-contracts K-19).
- A new owner mobile or email needs a signed-in session plus the ID re-check (S13-45 row 8): a `re_check` upload, and a `contact_changes` row of way `signed_in_id_re_check` naming it.

### Codes and sessions (RULES 6.2; S11-52; rule 7)

- A code is never stored: `code_hash` is its HMAC-SHA-256 under a Workers secret named in `hash_key_name`, so a 4- or 6-digit code cannot be found by hashing every code without the key. `expires_at` is `sent_at` plus 10 minutes (`proof_codes_ten_minutes`); the fifth wrong code sets `paused_until` 15 minutes later (`proof_codes_pause_after_five`); a code is used once, within its 10 minutes, and never after five wrong codes (`proof_codes_used_in_time`).
- A session holds `token_sha256`, never the token (`sessions_token_hash_form`); `device_sha256` lets a sign-in from a new device ask the extra proof (S13-45 row 8), through `device_known` (rule 5), since no Tool API call reads it. Sessions end when the person signs out, their sign-in contact changes, they leave (RULES 8.7) or the business is handed over (S11-100).

### Emergency contacts (S1-78; S2-06; Q-06)

- The pro (a solo owner on S1-70's page, or a team member whose work uses a timer, on their secure page) types the contact's name and mobile and ticks that they agreed; both values are sealed under the pro's key and are secure-page-only (T11: not shown).
- The contact is on file only after their own yes, which comes by texting Rosie (Q-06's default; C9: Rosie never writes first): `contact_person_id`, `contact_handle_id` and `contact_yes_at`. K-34's `safety_timers` copy that handle and time, and run only with them. The Team page shows who has a contact (S2-21), never who it is.
- A STOP or removal ends their yes (`ended_at`, `ended_why`; S13-10). The contact is never the pro (`emergency_contacts_not_the_pro`).

### Contact changes (D75, D77, D100; RULES 9.1 to 9.3)

- One row per change, never edited; the old contact stays only for the "don't text me" proof (FS line 756) and leaves every owner and staff view. The two consent rows a switch adds (the old contact's texts yes revoked, the new one's given) are K-29's.
- The way is the proof: `own_chat` (D75: a code to the new contact, typed back in the person's own chat), `email_on_file` (D100: a lost phone, a code to the email on file), `in_person` (D77: a code to the new contact read or typed at the desk, made by staff for that person only), `own_code` (a staff member's own change, FS section 8), `signed_in_id_re_check` (an owner's own, S13-45 row 8) and `owner_team_edit` (S11-20). CHECKs hold each way to its proof and its maker.

## Database rules beyond the table list

The table list's meta-schema has no place for these; the migrations must produce them too, and T-099 checks them.

1. **Same schema as core:** the ten tables live beside K-04's tables, and their foreign keys name core tables by K-04's keys (`businesses.id`, `persons.id`, `handles.id`, `handles.address`, `phones.number`), so the references carry no schema prefix. No table here refers to K-23, K-29 or K-34; K-34's `safety_timers` and later parts may refer to these.
2. **Versions:** every table that is updated has `version integer not null default 1`, raised by every update and compared and set by a commit (arch 01 line 85; K-04 v1 rule 2). `id_uploads`, `staff_skills` and `contact_changes` are written once (a skill is added or removed, never changed) and carry none.
3. **Ids** are `text`, opaque strings code makes (CQ-09). `kind_id` is the profession file's id, as K-23's `company_kinds.kind_id`.
4. **Row-level security per business, and per person where a row has no business** (arch 10 line 546; K-04 v1 rule 4): `staff`, `staff_skills`, `team_powers`, `on_call`, `emergency_contacts` and `contact_changes` are scoped by `business_id`. `accounts` and `id_uploads` are per person across businesses (`scope: none`), as K-04's `persons`; so are `proof_codes` and `sessions`, whose Tool API rows rule 5 binds to the call's person.
   - **The call's person, `rosie.person_id`** (beside K-04's `rosie.business_id`): the person a Tool API call acts for. It is set for the transaction with `set_config('rosie.person_id', <persons.id>, true)`, as `db/repo/scope.ts` sets `rosie.business_id` (PostgreSQL drops it at COMMIT or ROLLBACK), and read as `nullif(current_setting('rosie.person_id', true), '')`, so an unset setting, or the `''` an ended transaction leaves on its connection, matches no row (ids are text, rule 3: no cast). The data-access layer sets it from whom the call serves, never from the rows it writes, and K-05 states it per call, as K-04 rule 4 leaves each call's business scope to K-05:
     - a turn: the person the turn's handle belongs to (core `person_handles`, as the guard resolved it), so a turn in Alex's own chat acts for Alex; none while the handle is no one's yet, or several people's until the turn knows which of them it serves (S13-45 row 2: "A phone for more than one person: ask whose records"); in a lost phone's new chat (D100), whose handle is not yet theirs, the person whose email on file got the code, once that code is typed back right in that chat (RULES 6.1: "Or a code is sent to the contact on file and typed back in the same conversation"), set in that turn's transaction, as it is for D100's booking-page link (FS line 709) in the call where its code is typed back;
     - a sign-in call (S11-52, and S1-10's owner email): no person until its code is right. Until then it may only send the code (rule 5's `INSERT`), read the contact's limits through `proof_code_limits` and check a typed code through `check_proof_code`, by the code id it made, as the desk (D77) and a lost phone's new chat (D100) check a code for a person they do not act for yet. K-05 keeps that code id, and the person the code was made for (`proof_codes.person_id`), on the server from the code's request to its check, never taking either from the page, which holds at most an opaque attempt id. Once `check_proof_code` answers `right` for that code, which went to the account's own mobile or email (`accounts.mobile` or `accounts.email`, the one typed), the data-access layer sets `rosie.person_id` to that person in the same transaction, asks `device_known`, and only then, on a device seen before, starts the session (rule 5), naming that sign-in code. So typing someone's mobile or email gives a call none of their codes, sessions or contact changes (`refuse-sign-in-session-read`, `refuse-sign-in-session-end`, `refuse-sign-in-session-start`, `refuse-sign-in-own-change`);
     - a new device's second proof (S13-45 row 8: "A new device needs a code to the owner's email, typed back, or the ID re-check"; S11-52; FS line 688): a sign-in call whose code is right on a device `device_known` does not know starts no session. K-05 keeps the used sign-in code's id and its person on the server, and the call that completes the second proof starts the session, naming that same used sign-in code, so each sign-in starts at most one session, whichever proof completes it (`sessions_proof_code_key`). By a code to the owner's email on file (purpose `new_device`): it is sent and checked by its id as the sign-in code was, with no person until it is right; then `rosie.person_id` is set to that code's person, who is the sign-in code's person (K-05 checks), in that transaction, and the session starts with `proven_via` `code_and_email_code`. By the ID re-check: the call that takes the upload on the secure page (the runtime side writes its `id_uploads` row, purpose `re_check`, since this part gives the Tool API no grant on `id_uploads`) sets `rosie.person_id`, in its own transaction, to the person K-05 kept with the used sign-in code, and starts the session with `proven_via` `code_and_id_re_check`. That is the one sign-in step whose person comes from a code checked in an earlier call, so the session insert policy holds it to a used sign-in code of that person, `sessions_proof_code_key` to one that no session names yet, and until it sets the person its insert is refused like any call's with no person (`refuse-sign-in-session-start`);
     - a portal or secure-page call with a session: the session's person, which `session_for_token` answers (rule 5);
     - any other call: unset, so it reads no person's code or session, starts no session and writes no contact change with no business.
   - **A contact change with no business** is the person's own change (`own_chat`, `email_on_file`, `own_code`, `signed_in_id_re_check`), which covers every business (D75, D102). The Tool API writes it only with no business, in the turn or call that proves it, only for the call's own person, and no Tool API call reads it back; a business scope writes only its own desk and team-edit rows:
     - The Tool API role has `SELECT` and `INSERT` on `contact_changes`, and no `UPDATE` or `DELETE` (never edited).
     - Its select policy is `business_id = current_setting('rosie.business_id', true)`, so a row with no business is seen by no business scope (K-04 rule 4), nor by the person's own call.
     - Its insert policy is `(business_id = current_setting('rosie.business_id', true) and way in ('in_person', 'owner_team_edit')) or (business_id is null and person_id = nullif(current_setting('rosie.person_id', true), '') and changed_by_person_id = person_id and (way not in ('own_code', 'email_on_file') or exists (select 1 from proof_codes c where c.id = contact_changes.proof_code_id and c.person_id = contact_changes.person_id and c.used_at is not null)))`, whatever the call's business scope: a business scope writes only its own desk and team-edit rows (`in_person`, `owner_team_edit`), never a person's own change under its business id, whoever that person is (`refuse-own-chat-change-under-business`: the barbershop's scope writing Alex's own-chat change under its id), and a row with no business is admitted only when its person is the call's own person and made it, and, by `own_code` or `email_on_file`, only with a used code of that person (one `check_proof_code` answered `right`; a send cannot write `used_at`, rule 5). A change with no business for anyone else, from a call with no person (a sign-in call before its code is right: `refuse-sign-in-own-change`), or by `own_code` or `email_on_file` with a code not yet right or someone else's, is refused by the policy (42501): Sam's call writing an own-chat change for Alex is (`refuse-own-chat-change-for-another`). `contact_changes_desk_has_business` and `contact_changes_by_whom` refuse a desk row or someone else's row with no business on any side (23514). The insert takes no `RETURNING`, which would read the row back (42501); the id is code's (rule 3).
     - Bound to the caller, and by `own_code` or `email_on_file` to a used code of that person too (default 10): D75 counts the request "only from the customer's own chat (a message from some other number changes nothing)", so in `own_chat` who asks is proven by the chat the call acts in, the turn's person (rule 4), while the code D75 sends proves only the new contact, which may be anyone's (Sam's mobile, in the refused fixture). `own_code` (a code to the phone or email on file, FS section 8) and `email_on_file` (D100: a code to the email on file) are proven by the code itself, so the policy also holds their row to a used code of the person whose contact it is, a second lock beside the call's person. `signed_in_id_re_check` is the session's person's (rule 4), with its ID re-check. The row moves where every update goes and feeds the "don't text me" proof (FS line 756), so it must name the person the call acts for. Its proof stays required as before (`contact_changes_code_proof`, `contact_changes_id_proof`).
   - The runtime side reads and writes these rows unscoped (the "don't text me" proof, FS line 756), as K-04 rule 4 allows for jobs across businesses by handle. The owner's "Contact details changed." note for a customer comes through K-28 (open gaps).
5. **Codes and sessions: the Tool API's narrow grants, bound to the call's person** (RULES 6.2; S11-52; S13-45; S1-10; 02-contracts K-09 "shared core": proof codes; BP rule 7). The Tool API sends a code, in the one commit with its outbox row (arch 10 line 508), checks a typed code in the turn or call it is typed in, and serves the portal's sign-in (C-095, S11-52, S1-10's owner email). Neither table is per business (`scope: none`): a sign-in covers every business of the person. So row-level security binds the Tool API's rows of them to the call's person (rule 4's `rosie.person_id`), no column grant reaches a hash, and what the Tool API needs beyond its own person's rows comes only from security-definer calls keyed by what the caller holds. The Tool API role holds exactly:
   - `proof_codes`:
     - `SELECT` on every column but `code_hash`, of the rows its select policy admits: `person_id = nullif(current_setting('rosie.person_id', true), '') or (person_id is null and business_id = current_setting('rosie.business_id', true))`. That is the call's own person's codes (the live code for a purpose, its key name, its pause), and a listing's control code, which has no person (S1-75), in its own business's scope; never another person's code, from any business scope (`refuse-other-person-code-read`).
     - `INSERT` of the columns a send writes only (`id`, `purpose`, `person_id`, `business_id`, `sent_to_handle_id`, `channel`, `code_hash`, `hash_key_name`, `sent_at`, `expires_at`), under an insert policy of `true`. `used_at`, `wrong_tries`, `last_wrong_at`, `paused_until` and `version` are not granted, so a code always starts unused, untried and unpaused at version 1 (their defaults), and only `check_proof_code` moves them: a code inserted already used, tried or paused, or naming its version, is refused (42501; `refuse-proof-code-inserted-used`). Sending is not bound to the call's person, since a code may prove someone the call does not act for (the customer at the desk, D77; the new owner, S11-100; an old record, RULES 6.5; the account a sign-in is for, before its code is right, rule 4). It reads nothing back (no `RETURNING`, which the select policy refuses on another person's row, 42501), and what a code proves is bound where it is used: a session, or a contact change with no business, is the call's own person's; a session also needs a used sign-in code of that person, and an `own_code` or `email_on_file` change a used code of that person.
     - No `UPDATE` or `DELETE`.
     - A typed code is checked only by `check_proof_code(code_id text, typed_hash text, at timestamptz) returns text`; the caller hashes the typed code first with the key `hash_key_name` names, which never enters the database. The call locks the row and returns `unknown`, `used`, `paused` (after five wrong codes), `expired` (outside its 10 minutes), `right` (sets `used_at`) or `wrong` (raises `wrong_tries`, sets `last_wrong_at`, and at the fifth sets `paused_until` 15 minutes on and returns `paused`); never a hash. It runs in the caller's transaction, so a try is counted in the turn's one commit. It is keyed by the code id the caller made and holds (ids are code's, rule 3), not by the call's person, because the desk (D77) and a lost phone's new chat (D100) check a code for a person they do not act for yet; it answers only the outcome.
     - What a sender must know of other people's codes comes only from `proof_code_limits(handle_id text, purpose text, since timestamptz, at timestamptz) returns table (sent_since integer, paused_until timestamptz)`: for the contact a code is about to go to, how many codes went to it since `since`, for every person and purpose (S13-45: "At most a few codes a day per contact"; the number and the window are code's), and the latest `paused_until` after `at` of a code for that contact and purpose (default 8), else null. One row; never an id, a person, a business or a hash.
   - `sessions`:
     - `SELECT` on every column but `token_sha256` and `device_sha256` (both session hashes), and `UPDATE` of `last_seen_at`, `ended_at`, `ended_why` and `version` only, each of the rows its policies admit: the select policy `person_id = nullif(current_setting('rosie.person_id', true), '')`, the call's own person's sessions; the update policy `using (person_id = nullif(current_setting('rosie.person_id', true), '') and ended_at is null) with check (person_id = nullif(current_setting('rosie.person_id', true), ''))`, so the row as it was must be the call's own person's and not yet ended, and signing out passes. So a call touches and ends only its own person's live sessions (signing out; `contact_changed` when that person's sign-in contact changes) and never reopens one that ended, whoever ended it (RULES 8.7; S11-100; `refuse-ended-session-reopened`: no row changed); in another person's call, or a sign-in call before its code is right, the same read gets no row and the same update changes none (`refuse-other-person-session-read`, `refuse-other-person-session-end`, `refuse-sign-in-session-read`, `refuse-sign-in-session-end`). Ending someone else's sessions (`left` when they leave, S13-56 and RULES 8.7; `handed_over`, S11-100) is not the Tool API's: the commit writes it on the runtime side, as K-05's commit writes rows with no business and tables scoped none (`contracts/data-access/README.md`, "Scope").
     - `INSERT` of the call's own person's session only, with a used sign-in code of that person: the insert policy is `person_id = nullif(current_setting('rosie.person_id', true), '') and exists (select 1 from proof_codes c where c.id = sessions.proof_code_id and c.person_id = sessions.person_id and c.used_at is not null and c.purpose in ('sign_in', 'new_device'))`, so `proof_code_id` must name a code of the same person, of a sign-in purpose (`sign_in`, or a new device's `new_device`: S13-45 row 8), that `check_proof_code` answered `right` (a send cannot write `used_at`), and `sessions_proof_code_key` lets that code start one session. The subquery reads `proof_codes` as the Tool API, through its own grant and select policy, which show the call's own person's codes. A call with no person, as a sign-in call is until its code is right and a new device's ID re-check call is until it sets its person (rule 4), starts none (`refuse-sign-in-session-start`), nor does a person's own call naming a code not yet right, another person's code or a listing's control code (`refuse-session-unused-code`), or a used code that proved something else, such as a contact change (`refuse-session-contact-change-code`); no `RETURNING` of a hash (42501); no `DELETE`.
     - A presented token is found only by `session_for_token(token_sha256 text, at timestamptz) returns table (session_id text, person_id text)`: the session with that hash that has not ended and has not expired at `at`, with its person, whom the call then acts for (rule 4); no row otherwise; never a hash. It answers the person beside the id because the call cannot read the row before it knows whom it acts for.
     - Whether a device was seen before comes only from `device_known(device_sha256 text) returns boolean`: true when the call's own person (`rosie.person_id`) has a session, live or ended, from that device, so a sign-in from a new device asks the extra proof (S13-45 row 8: "A new device needs a code to the owner's email, typed back, or the ID re-check"); false otherwise and with no person set. A sign-in call asks it once its code is right and its person is set (rule 4). It never answers for another person and never returns a hash; no Tool API call reads or searches `device_sha256` (`refuse-session-device-read`).
   - All four calls are `SECURITY DEFINER`, owned by the migrations' owner (the tables' owner, so row-level security does not bind it: no `FORCE ROW LEVEL SECURITY` on these two tables); `EXECUTE` is revoked from `PUBLIC` and granted to the Tool API role and the runtime side. Each one's `search_path` is pinned to the migration's own schema, then `pg_temp` last, so neither another schema's object nor a temporary table the caller makes stands in for `proof_codes` or `sessions` (PostgreSQL searches `pg_temp` first unless it is named). That schema changes per run (`public` on staging, `preview_<slug>` for a preview, a test's own schema), so the migration sets the path when it runs, from `current_schema()` (for example `alter function <schema>.check_proof_code(text, text, timestamptz) set search_path = <schema>, pg_temp`, built with `format` in a `DO` block), never as a fixed name. Their bodies qualify every column with its table's alias and every parameter with the call's name, since parameters and output columns share names with columns (`token_sha256`, `device_sha256`, `person_id`, `purpose`, `paused_until`).

   So no Tool API call reads, searches or sets a code hash, a token hash or a device hash, lifts a pause, uses a code without its hash, inserts a code already used, tried or paused, reads another person's code or session, starts a session without a used sign-in code of its own person, reopens an ended session, or starts, touches or ends another person's session, and no sign-in call acts for anyone before its code is right (SQLSTATE 42501, or no row); only hashes are stored, never a code, a token or a device's id (BP rule 7; `proof_codes_hash_form`, `sessions_token_hash_form`, `sessions_device_hash_form`). The runtime side keeps full access, unscoped: the jobs K-04 rule 4 names, and K-05 v1's commit, which may write a row with no business on that side (`contracts/data-access/README.md`, "Scope").

6. **Sealed fields:** `id_uploads.object_key` (by `person_id`), `emergency_contacts.name` and `emergency_contacts.mobile` (by `person_id`, the pro), each under that person's key in core's `sealing_keys` (arch 01 line 93; migration 0003's seal, unseal and erase). The wrapping key and the code-hash key are Workers secrets, named and never stored (rule 7).
7. **Arrays:** `staff.languages` is `text[]` and `on_call.days` is `smallint[]`, not null, default `'{}'`; a fixture gives them as a JSON array (K-04's fixture format).

       1. `check_sha256` equal to the attempt's `last_check_sha256`: **a repeat**; nothing is written, and it answers `repeated` true with the attempt's `wrong_tries`, `paused_until` and `last_outcome`, the first result.
       2. `outcome` NULL: **the look**; nothing is written, and it answers `repeated` false with the attempt as it stands. The check makes it before `check_proof_code`, since no call returns `last_check_sha256` (below).
       3. `outcome` `wrong`: **a wrong try**, counted when the attempt has fewer than five, no pause, and `at` is not after `expires_at`: `wrong_tries` rises by one, `last_wrong_at` becomes `at`, and at the fifth `paused_until` becomes `at` plus 15 minutes, as `check_proof_code` counts a code's (rule 5); the check is recorded with `last_outcome` `wrong`, or `paused` at the fifth. Otherwise nothing is counted and the check is recorded with `paused` while the pause is on at `at`, else `expired`.
       4. Any other K-21 label: the check is recorded with that label, nothing counted.

       Each write sets `last_check_sha256` to `check_sha256` and raises the version by one, and the call answers `repeated` false with the attempt after it.

     - `sign_in_attempt_signed_in(id text, session_id text) returns boolean`, language `plpgsql`, `volatile`: sets the attempt's `session_id` and raises its version only when the attempt names a code, names no session yet, and the session exists with the attempt's person and the attempt's code as its `proof_code_id` (rule 5's `sessions_proof_code_key` then lets that code start no other); answers true. Anything else, a NULL argument included, writes nothing and answers false. A new device's second proof starts its session naming the same sign-in code (rule 4), so the call that completes it names the attempt the same way.
   - **The hashes**, each the lowercase hex of its digest over UTF-8 text, a line feed (U+000A) between parts:
     - `request_sha256` = sha256(`device_sha256` LF `requestId`): the start's `page.requestId` with the starting device, so the same id from another browser never matches (K-21 v1 schema, `page.requestId`).
     - `last_check_sha256` = sha256(`id` LF `device_sha256` LF `requestId`): the attempt's own `id` (ADR-016 section 4: "the attempt's `id`", which `sign_in_attempt` answers), the starting device's sha256 and the check's `page.requestId`; **never over a typed code**, whose plain sha256 a million tries would give up (default 7). Its first part is fixed per attempt and its second fixed-length, so two requestIds of one attempt never share a key.
     - `contact_hash` = HMAC-SHA-256, keyed with the Workers secret `hash_key_name` names (`PROOF_CODE_HASH_KEY`, read by name and never stored: rule 6), over `rosie-sign-in-contact` LF kind LF contact, where kind is `email` (the address in lower case), `mobile` (E.164) or `link` (a start with account `link`: the page's `linkCode` as presented, default 15); never the contact itself. A code's own HMAC message (`proof_codes.code_hash`) never begins with that prefix, so under the one key (CQ-240) a contact's hash and a code's never share a message.
     - `device_sha256` = sha256 of the device cookie as sent (K-21 v1 `deviceToken`).
   - **The start's counts** (ADR-016 section 4 rules 0, 2 and 3; CQ-237; CQ-249), each by the database's clock: `now()` is the start's transaction time, the same value the insert's `started_at` takes from its default, and `expires_at` is written as `now() + interval '10 minutes'`. "The window" is the attempts a count reads, ordered by `started_at`, then `id`:
     - **Rule 0, the hourly bound**, across every contact, read before the contact's lock: n = `count(*) where a.started_at > now() - interval '1 hour'`. When n reaches `SIGN_IN_STARTS_PER_HOUR` (default 100), the start answers `paused` until u, the `started_at` of the window's (n − 100 + 1)-th attempt plus 1 hour, and writes nothing; with n = 100 that is the moment the oldest of them is an hour old. Read outside any lock, a burst passes it by at most the starts running at once (CQ-249).
     - **Rule 2, the contact's pause:** `max(a.paused_until) where a.contact_hash = <the contact's hash> and a.paused_until > now()`; when not null, the start answers `paused` until it and writes nothing. A wrong try is counted only inside its attempt's 10 minutes, so a pause ends at most 25 minutes after its attempt started, and the read may add `a.started_at > now() - interval '25 minutes'` to use `sign_in_attempts_contact_idx`.
     - **Rule 3, the day's cap:** n = `count(*) where a.contact_hash = <the contact's hash> and a.started_at > now() - interval '24 hours'`. When n reaches `SIGN_IN_STARTS_PER_DAY` (default 5), the start answers `paused` until u, the `started_at` of the window's (n − 5 + 1)-th attempt plus 24 hours, and writes nothing. **"The oldest of five is 24 hours old"** is that u with n = 5: the instant `now()` equals the oldest attempt's `started_at` plus exactly 24 hours, when `started_at > now() - interval '24 hours'` stops holding for it. A start at u itself counts four and is admitted; one a microsecond earlier (PostgreSQL's resolution) counts five and answers `paused` until u. A start past the cap writes nothing, so under the contact's lock the window never holds more than five; n above five comes only from a cap lowered or rows written another way, and u is then still the moment the window holds one fewer than the cap.
     - **The lock:** rules 1 to 5 run under `pg_advisory_xact_lock(hashtext('sign_in_attempts:' || <the contact's hash>))`, the blocking form, so a second start for the contact waits for the first to commit and then counts it: two parallel starts at the cap give one attempt. Rule 1's repeat is the row whose `request_sha256` is the start's key, answered again (`started`, its `attempt_id` and `expires_at`) with nothing written; rule 5's insert names `person_id` and `owner_or_admin` (true only for a person with a live owner or admin role), or null and false.
     - Rules 0 to 3 read no account, and every count is by the contact's hash, so a pause and a cap answer alike for any typed contact (K-21 v1 schema line 780).
   - **The check** (K-05's `proveSignIn`, as the Tool API, in one transaction; ADR-016 section 4, "The check"), in this order:
     1. `sign_in_attempt(attemptId, sha256 of the deviceToken, at)`: no row answers `attemptNotFound`, nothing written.
     2. `check_sha256` from the answered `id` (above); `sign_in_attempt_tried(id, check_sha256, NULL, at)`, the look: `repeated` answers the first result (`signedIn` as `alreadySignedIn`, with no token; `wrong` with 5 − `wrong_tries` tries left; `paused` until `paused_until`), nothing written. So a repeat never reaches `check_proof_code`, and the code counts no try for it.
     3. From the binding: `signed_in` answers `alreadySignedIn`; `paused` answers `paused` until `paused_until`; `expired` answers `expired`; each recorded by `sign_in_attempt_tried` with that label, no try counted. The attempt expires no later than its code (`started_at` is no later than the code's `sent_at` on one clock) and counts every try its code counts, so `check_proof_code`'s early answers, `paused` for a code already paused and `expired` (0020 lines 744 to 750), come first only in the race below.
     4. `check_proof_code(proof_code_id, typed hash, at)` (rule 5); a null `proof_code_id`, with no account or no code yet, answers `unknown` before any write.
     5. `right`: rule 4's steps (`rosie.person_id` set to the binding's person, `device_known`, the session insert), then `sign_in_attempt_tried` with `signedIn` and `sign_in_attempt_signed_in(id, session_id)`; or `secondProofNeeded` for an owner or admin (`owner_or_admin`) on a device `device_known` does not know, once they have had a session (K-21 v1 README line 110), recorded with no session. `used` with no session naming the code: `secondProofNeeded` again, recorded. **`wrong`, `paused`, `expired` and `unknown`: one wrong try**, `sign_in_attempt_tried` with `wrong`, and the answer is the attempt's after it: `wrong` with 5 − `wrong_tries` tries left, or at the fifth `paused` until `paused_until`. The null id's `unknown` is a wrong try here, not K-21 README line 116's `attemptNotFound` (T-1250 round 2 security note b; K-05's sign-in version, T-1277, says so for the page). A wrong try commits at once, so it counts whatever fails after it (ADR-016 section 4, on this README's open gap "A wrong try in a turn that does not commit").

     So **every answer to a code that is not right comes from the attempt**, on both paths: with an account and without one the same checks count the same tries, give the same pause at the fifth (`at` plus 15 minutes), and answer `wrong`, `paused` and `expired` alike (`seed-sign-in-attempt`'s two attempts of Oct 28; K-21's `sign-in-wrong-five.json`, paused until 15:22:10). Way `text` (`waitingForText`) is not served in ADR-016's lane (CQ-244).

   - **DL-526's ruling** (T-1250 round 2 security note a; T-1274's lead note). `check_proof_code` answers `expired`, before any write, to a check whose `at` is earlier than the code's `sent_at` (0020 line 748): a guess that reads the attempt after `sendSignInCode` committed, with an `at` taken before the code's `sent_at`. **Ruled: that `expired` is a wrong try of the attempt, as the null id's `unknown` is**: step 5 records it through `sign_in_attempt_tried` with `wrong` and answers from the attempt, so the attempt with a code and its twin with none count the same try at the same check, whatever the clocks. One clock alone would not settle it: with every time from the database, a check whose transaction began before the send's can still read, in a later statement, the code the send committed (each statement of a READ COMMITTED transaction reads its own snapshot), so its `at` is still earlier than `sent_at`. The same rule covers a code whose 10 minutes end before its attempt's, should a send ever write `sent_at` on another clock. A check past the attempt's own 10 minutes answers `expired` at step 3 with no try, on both paths. T-1284 (R2) tests it: a check at a time before its code's `sent_at`, after the code is written, and the same check of an attempt with no code, leave equal attempts (`wrong_tries`, `last_wrong_at`, `paused_until`, `last_outcome`) and give the same answer.
   - What the page gets differs with or without an account only in time, which is not measured (CQ-251).

## Defaults used (T-1274, v1.2)

20. **A wrong try counts only inside the attempt's 10 minutes, unpaused and under five**; otherwise the check is recorded as `paused` while the pause is on, else `expired`, so a count never passes five and a pause never starts after the attempt's end.

23. **The counts' "until"** is the moment the window holds one fewer than its limit, (n − limit + 1)-th attempt plus the window's length, which with n at the limit is ADR-016's "the earliest `started_at` among those attempts plus 24 hours" and "until the oldest of them is an hour old"; the contact's lock is `pg_advisory_xact_lock(hashtext('sign_in_attempts:' || <the contact's hash>))`, ADR-016's "transaction-level advisory lock keyed on the contact hash" in the blocking form.
