## What it defines

The port in Rosie's own terms (02-contracts K-12, section 5): three calls and the double's two test hooks. Resend's paths, headers, field names and codes stay inside the adapter (C-213); the fixtures are port-level exchanges. Each call is a definition set under `$defs`: `<call>.request`, `<call>.response`, `<call>.errors`, and `<call>.exchange` (a fixture). Every field's `description` names its source; "arch NN line N" are the lines of `scratch/text/architecture.txt`.

### The email row (`sendEmail.request`)

One email to one person, plain text, under its K-07 key (02-contracts K-12 "Send one email row"; arch 07 line 371: "Email is its own row with the same plan, the automated-assistant line (RULES 1.11), a code-built subject like S12-10's, typed options and a manage link, in the booking's reply thread"). The email rows (C-129) build it from the row's final parts, whose one `words` send carries the options typed (K-07 "Email rows"), and add the four things K-07 v1's final parts carry none of (K-07 open gap 7): `subject`, `assistantLine`, `manageLink` and `thread`.

What the schema holds: an email about a booking carries its reply address and manage link, and one about no booking has neither and no thread (an email thread belongs to one booking: K-04 `threads_chat_or_email`), which `refuse-no-reply-address.json` shows; a `confirmation` names its booking and carries the chat link, and no other purpose carries one; a `copy` names its booking; a thread that names `inReplyTo` lists at least one reference; the subject and the From name are one line (`refuse-subject-line-break.json`), the From address is on mail.rosfield.com (`refuse-from-other-domain.json`), and the assistant line says "automated". What it leaves to code and the contract test: that `text` starts with `assistantLine` and holds `manageLink` and `chatLink.link` word for word, and that the last of `references` is `inReplyTo`.

### Outcomes of a send

`accepted`: Resend's id for the email (`providerMessageId`, K-07's part id; every receipt names it as K-06 `status.messageId`) and when Resend took it (K-08 `providerAccepted`). Accepted is not delivered: the receipt comes later. `failed`, by `kind`:

| `kind`         | Read from                                                                                                                                                       | What the dispatcher does (K-07)                                                                 |
| -------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| `rateLimited`  | 429 `rate_limit_exceeded`, with `retryAfterSeconds` from the retry-after header                                                                                 | The next try after it (arch 10 line 540; rule 6)                                                |
| `quotaReached` | 429 `daily_quota_exceeded` (resets at midnight UTC) or `monthly_quota_exceeded`                                                                                 | No try within the 15 minutes clears it: the row fails and the next way follows (rule 5)         |
| `refused`      | Any other 4xx: `validation_error` (an unverified domain, a bad field, a bad key), `invalid_idempotent_request` (one key, another email), 401 and 403 key errors | Not tried again as it was; the row fails and the next way follows; the console shows it (C-194) |
| `transient`    | A 5xx (`application_error`, `service_unavailable`), a 409 `concurrent_idempotent_requests`, a timeout or a network error                                        | K-07 rules 1 and 5 (open gap 9)                                                                 |

### Delivery events (`verifyWebhook`)

Resend signs every webhook through Svix. Each email event Rosie uses becomes one K-06 v1 event with provider `email` and service `email` (K-06's own provider rules), with the email's Message-ID beside it for the thread (K-06 v1 has no field for it, so it travels beside the event, never in it):

| Resend event                                                                                                                                                               | Result    | K-06 kind   | K-06 `status.failure.code` | `rfcMessageId` |
| -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------- | ----------- | -------------------------- | -------------- |
| `email.delivered`                                                                                                                                                          | `event`   | `delivered` | (none)                     | `message_id`   |
| `email.bounced`, bounce type Permanent                                                                                                                                     | `event`   | `failed`    | `bouncePermanent`          | `message_id`   |
| `email.bounced`, any other bounce type                                                                                                                                     | `event`   | `failed`    | `bounceTemporary`          | `message_id`   |
| `email.suppressed`                                                                                                                                                         | `event`   | `failed`    | `suppressed`               | null           |
| `email.failed`                                                                                                                                                             | `event`   | `failed`    | `notSent`                  | null           |
| `email.received`                                                                                                                                                           | `reply`   | (readReply) |                            |                |
| any other type, such as `email.sent`, `email.delivery_delayed`, `email.complained`, `email.opened`, `email.clicked`, `email.scheduled`, `domain.*`, `contact.*`, `inbox.*` | `ignored` |             |                            |                |

The event's id is the webhook's id (svix-id, the same on every retry); its handle is the address the email went to (`data.to`, lower case: K-06 default 6); `status.messageId` is Resend's `data.email_id`; `status.at` is the event's `created_at`, to whole seconds (default 8); a failure's `reason` is Resend's own words (`bounce.message`, `suppressed.message` or `failed.reason`) with any address taken out. `delivered` arms the question's clock (arch 02 line 127: "Resend's delivered on email") and moves the part and row (K-07); `failed` starts the channel fallback (02-contracts K-12: "failed or bounced (the channel fallback)"; arch 02 line 125). A delay is not a failure: Resend keeps trying and a delivered or bounced event follows, so `email.delivery_delayed` is ignored (`verify-ignored-delivery-delayed.json`).

### Inbound replies (`verifyWebhook`, then `readReply`)

Resend's `email.received` webhook carries only a reply's metadata ("Webhooks do not include the email body, headers, or attachments, only their metadata"), so a reply takes two steps. `verifyWebhook` gives `reply`: the event id, Resend's id for the received email, and the address on Rosie's receiving domain it came to (`replyAddress`), so the gateway can tell a booking's reply from other mail before reading it. The gateway drops a known event id with 200, calls `readReply`, writes the event and answers 200; when the read fails `transient` it answers 503, so Resend retries (for about 27 hours: spike row 9), and when it is `unreadable`, 200 and the reply is dropped (default 11). `readReply` gives one K-06 text event, built so:

| K-06 field              | From Resend's received email                                                                                                                              |
| ----------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `eventId`               | The webhook's id (svix-id)                                                                                                                                |
| `handle`                | `from`, the bare address, lower case                                                                                                                      |
| `messageId`             | `message_id`, as Resend gives it (a real one is `<id@host>`; the fixtures keep K-06's placeholders)                                                       |
| `sentAt`                | `created_at`, when Resend's server received it, to whole seconds (default 15)                                                                             |
| `body`                  | `text`, the quoted earlier email dropped (default 14); for an email with only HTML, the HTML's words                                                      |
| `attachments`           | Each attachment as K-02's attachment: `attachmentId` Resend's attachment id, `mediaType` its `content_type` (default 16)                                  |
| `email.replyAddress`    | The first of `to`, `cc` and `received_for` on Rosie's receiving domain (default 13): the booking's reply address picks the booking and thread (RULES 4.1) |
| `email.subject`         | `subject`                                                                                                                                                 |
| `email.senderCheck`     | `passed` when Resend's `authentication.dkim` or `authentication.dmarc` is `pass`; anything else, or none, is `failed` (default 12)                        |
| `receivedAt`, `traceId` | The request's (the gateway's)                                                                                                                             |
| the rest                | `chatId` null, `threadedReplyTo` null (default 18), `fromRosie` false, `scrubbed` zero: the gateway's scrub counts its tags                               |

The sender check comes from the receiving mail server, not from the message's own headers, "so the sender cannot forge them" (spike row 12). An email counts only when it passes; one that fails proves nothing (RULES 6.1), as `inbound-reply-failed-check.json` shows. An automatic reply (Auto-Submitted other than "no", RFC 3834) is `ignored` (default 17).

### The thread (In-Reply-To and References)

Resend sets each email's Message-ID itself and reports it as `message_id` on its email webhooks; In-Reply-To and References are custom headers it documents for threading (spike rows 13, 15). So `thread.inReplyTo` and `thread.references` hold Message-IDs: Rosie's answer to a person's reply threads under that reply's Message-ID (K-06 `messageId`), and Rosie's later emails about a booking under the earlier ones, whose Message-IDs their receipts reported (`rfcMessageId`). The first email of a booking's thread has none. Where the runtime keeps Rosie's own Message-IDs between emails is open gap 2.

### The double

The email double (C-213's double, test code only) answers `sendEmail` with any outcome this contract defines, as the test chooses, records every accepted email once per key, and gives them to the test-phone page through `doubleSentEmails` (02-contracts K-12 "The double's test hooks"; BP 9.4), so a tester can see a confirmation's chat link and send its ready text from a test phone. `doubleWebhook` makes signed webhooks for a faked delivered or bounce receipt (with its Message-ID) and for a faked inbound reply, which it keeps so `readReply` on the id it gives answers the reply's event with the gateway's `receivedAt` and `traceId`.

## Defaults used (T-021)

1. **Secret names:** `RESEND_API_KEY` (the send-only key, DL-022), `RESEND_WEBHOOK_SECRET` (the webhook's `whsec_` signing secret) and `RESEND_RECEIVING_KEY` (a key that can read received email), until the CTO and the release engineer name them (02-contracts section 2 item 13).
2. **The one confirmation address** is a config value on mail.rosfield.com (DL-028), which the schema pins by its domain alone; the fixtures use `rosie@mail.rosfield.com` as an example.
3. **The From name** is the business's display name (K-04 `businesses.display_name`; RULES 4.6 for sensitive work) for an email about one business, else "Rosie" (an email Rosie writes for no booking, such as a sign-up code or S12-10's notice to the owner). RULES 4.1 says only "It shows the business name".
4. **Purposes** (above) are the uses 02-contracts K-12 and Q-02's default name; a booking email carries its reply address and manage link (RULES 4.1; arch 07 line 371), and only a confirmation carries the chat link (MC C9).
5. **The QR** is drawn by the adapter from `qrText` as a PNG attached as `chat-link-qr.png`, since a plain-text email shows no image inline and v1 has no HTML part.
6. **The thread:** In-Reply-To and References as Resend documents them (spike row 13), from K-06 `messageId` and the receipts' `rfcMessageId`; the first email of a booking's thread has none.
7. **The event id is the webhook id** (svix-id), the same on every retry (spike row 8).
8. **Times** are Resend's ISO 8601 times written in UTC to whole seconds, as K-06's and K-07's fixtures write them.
9. **Failure codes:** `bouncePermanent` for bounce type Permanent, `bounceTemporary` for any other, `suppressed`, `notSent`; the reason is Resend's words with any address taken out.
10. **Ignored event types:** every type but `email.delivered`, `email.bounced`, `email.suppressed`, `email.failed` and `email.received` is verified, answered 200 and dropped. A delay is not a failure (a delivered or bounced event follows); `email.sent` adds nothing a delivered event lacks; `email.complained` is open gap 4; opens and clicks are not read (open gap 8).
11. **The gateway reads a reply before it answers**, and answers 503 when the read fails `transient`, as arch 02 line 109's "Write fails: 503, and the provider retries". The read is one more API call inside the gateway's answer.
12. **The sender check** is `passed` when Resend's `authentication.dkim` is `pass` (signed by the From domain: spike row 12) or `authentication.dmarc` is `pass`; SPF alone, `gray`, `fail`, `processing_failed`, `unknown` or no `authentication` is `failed` (K-06 default 4: a check that did not run is failed). DMARC `gray` with a DKIM pass passes, as for an address whose domain uses p=none.
13. **The reply address** is the first address of `to`, then `cc`, then `received_for`, on Rosie's receiving domain (a config value until J-14).
14. **A reply's body** drops the quoted earlier email: from a line "On ... wrote:" followed by lines starting with ">" to the end; text the adapter does not recognize as a quote is kept, and the model reads it as words (RULES 2.2).
15. **`sentAt`** is when Resend's server received the reply (`created_at`), not the sender's own Date header, which the sender writes.
16. **Attachments:** every attachment of the reply, inline ones too, as K-02's attachment with Resend's attachment id; K-13 turns each into a file reference.
17. **An automatic reply** (Auto-Submitted other than "no": RFC 3834) is `ignored`, so no answer to it starts a loop; Resend's documented example shows only three headers, so the adapter reads the header where `headers` holds it.
18. **A reply threads under no message in v1** (`threadedReplyTo` null): its reply address already picks the booking and thread (RULES 4.1).
19. **Staging sends only to the few named inboxes** (Q-23's default), by an allow-list in the adapter, as C-210 does for Linq; it is not a port field.

## Open gaps

1. **Inbound replies (J-14; Q-23):** the receiving domain (receiving turned on for mail.rosfield.com, or a subdomain such as reply.rosfield.com: spike row 11), its MX record, the `email.received` webhook to staging's gateway, and a key that can read received email: the send-only key cannot (`restricted_api_key`: spike rows 3, 4), and the only other key Resend offers is `full_access`, which can also change domains and webhooks. Decided at M5 (the card's outside item); until then the double serves inbound, and the fixtures' reply addresses use K-06's `reply.example.com`. For the CTO and Jay.
2. **Where Rosie's own Message-IDs live:** K-04 v1 stores none (no column on `threads`, `messages` or `outbox_parts`), and Resend sets them itself (spike row 14) and reports them only on its webhooks or `GET /emails/{id}` (which a send-only key cannot call). Until a K-04 minor version adds a column, the email rows can thread an answer under a person's reply (K-06 `messageId`, which the actor holds) but not under Rosie's own earlier emails, and send those with an empty thread; the reply address still keeps the booking's thread on Rosie's side (RULES 4.1). For the database engineer.
3. **Volume:** Resend Free's 100 emails a day (J-14; Q-23); past it, `quotaReached` and the next way.
4. **Spam complaints** (`email.complained`): no source says what Rosie does when a person marks an email as spam. Ignored in v1; proposed for QUESTIONS.md: stop emails to that address, as a new K-06 kind or a v1.1 outcome.
5. **Owner email answers:** S1-10 makes the owner email "for notices, sign-in recovery and answers by email", but K-04 v1 has an email thread only for a booking (`threads_chat_or_email`), so an email about no booking carries no reply address and a reply to it reaches the From address with no thread. For QUESTIONS.md.
6. **Quoted text** is found by the forms default 14 names; a client that quotes another way (such as a "From: ... Sent: ..." block) leaves Rosie's earlier words in the body, which the model reads as the person's.
7. **The sender check's rule** (default 12) decides what an email can prove (RULES 6.1); proposed for the security reviewer's look before inbound replies go live.
8. **Open and click tracking** must stay off for mail.rosfield.com: a tracked link is rewritten, and Rosie reads no opens. A domain setting at J-14 (release engineer), not a port field.
9. **K-07 rule 1 and Resend's key:** K-07 gives a reported failure (a 5xx) a new key, but a 5xx may still have sent, and only the same key, within Resend's 24 hours, would stop a second email. So a duplicate email is possible after a 5xx. Whether an email part keeps its key after a `transient` failure is K-07's to state, as a minor version; this port answers the same either way. For the runtime engineer.
10. **No calendar file and no HTML part in v1:** a calendar file is an iMessage format (arch 07 line 383), and K-12 asks for plain text; each can come as a minor version.
11. **The chat link in a plain-text email** is an `sms:` link (K-09's form); some mail clients do not make one tappable, and the QR serves a reader on a computer. K-09's link form decides; a page link would need a K-09 minor version.

## Keywords beyond ADR-005's list

`dependentSchemas` with `if`/`then`/`else`, `allOf` over K-06's schema, `oneOf`, `not`, `minItems`, `maxItems`, `minimum` and `maximum`, as K-06 and K-11 use them; nothing here is model-facing, so the structured-outputs subset does not apply. The consistency checks sit in `dependentSchemas` rather than `allOf`, so json-schema-to-typescript keeps the types (T-010's finding); the generated types are wider than the schema there.
