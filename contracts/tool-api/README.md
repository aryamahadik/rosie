## What it defines

The calls that own every read and write (arch 02 line 139), "generated from the master's needs and gives keys" (arch 12 line 590). The same calls serve texts, secure pages and outside AIs under the same limits; free text from pages and AIs gets the safety read first (arch 02 line 129); row-level security scopes every call by the caller's business (arch 10 line 546; K-04 v1 rule 4). Every request carries a `caller` (`$defs/caller`): who calls (a turn, a page, an agent, the console, a job, a clock firing, or the handle actor writing on return), the business it runs under, the person it acts for (stated per call as the session's `rosie.person_id`, which K-22 v1's row predicates read: K-22 v1 rule 4; none for a sign-in call until its code is right), the key a repeat is known by, and the trace it joins (K-08).

Every field's `description` names its source (02-contracts section 2 item 4). "arch NN line N" are the lines of `scratch/text/architecture.txt`, as `ops/plan/02-contracts.md` cites them. Frozen contracts are reused by relative `$ref` where a call carries their shapes: K-01 v1 (`stepId`), K-02 v1 (`context`, `text`, `contextAndDecide`, `plannerOutput`, `safetyResult`, `safetyOutcome`, `language`), K-03 v1 (`composeInput`, `rowPlan`, `finalParts`, `checkResult`), K-05 v1 (`turn`, `commitResult`, `rowRef`, `sendClass`, `phoneNumber` and its errors), K-07 v1 (`effectKind`, `rowState`), K-08 v1 (`traceId`, `limitResult`) and the shared formats (`id`, `turnId`, `utc`, `money`). The table parts (K-04 core, K-23, K-24, K-26, K-29, K-33, K-34, K-36, K-37) are table lists, so the calls name their tables, columns and closed lists in words and enums, never by `$ref`. K-22 v1's proof codes and the call's person are mapped as frozen ("Proof codes in K-22 v1"); the rest of K-22, K-25 and K-28 (frozen on main after this contract was first written) and the parts not yet frozen (K-27, K-35, and the ports K-12 to K-16) are named in words only (open gap 2).

**CQ-25 (settled):** decide reaches the model in two calls a read, made by the AI gateway (T-361). The turn face passes K-02 v1's context to decide, and takes K-02 v1's decide result back, unchanged; the wire form is C-115's and C-121's, not the Tool API's.

### In a turn or alone

A turn commits once (arch 02 line 121; arch 10 line 508). So a shared-core call made in a turn (a STOP, a safety outcome, a door, an owner's answer to a hand-off, a staff member's ready text) rides inside `gateAndCommit`: its request in `request.core` (`$defs/coreAction`, with `caller.kind` turn) and its response or error in `response.core` (`$defs/coreResult`). A setup step's write in a turn is the effect code adds for the choice decide picked, after limits 1 to 6 pass, and the part's result names the keys it gave (`partResult.gives`). The one setup step that rides as a core action is S2-05's ready text: `coreAction`'s saveSetupStep takes `$defs/saveSetupStepInTurn`, whose step is only `SetupS2_05`, so no consent, money or team write (S1-25's fee_ok, S1-27, S1-29, S2-02, S2-24) can commit from a turn's core outside the limits (`invalid/refuse-core-setup-step-not-ready-text.json`). A refused core action stops only itself. A call made alone (by a page, an agent, the console, a job or a clock firing with no handle) commits once under `caller.requestId`, which waits for K-05's commit with no turn (CQ-44's default). An exchange whose `caller.kind` is turn and whose call is not `gateAndCommit` shows a core action or a step's write as it rides inside a turn's commit: the same request and result, which the mock answers the same way.

### A clock's firing (`gateAndCommit`, `input.kind` clock)

QUESTIONS.md NQ-RT-4: a clock is a turn on the handle's actor, or a sweep job for a row with no handle, which calls `gateAndCommit` with the clock branch, no decide reads and the firing's own trace id (CQ-06), and commits through K-05 v1 `fireClock`.

- **The turn:** for a row a handle owns, a clock turn on that handle: its one event id is the clock row's id (K-05 v1 default 9: K-04 needs one, and a firing has no text), its id that event id's hash, as every turn's is (CQ-09), so one row's firing has one turn id; its trace id is the firing's own; `caller.kind` turn, with `caller.turnId` and `caller.requestId` its id. ### The safety record on arrival (T-246's open point)

T-246 records a text's safety outcome before any turn, through `recordSafetyOutcome` with `caller.kind` job, `turnId` null and `requestId` `safety:<eventId>`, and releases an at-once hold with `expectVersion` 1, because v1 names no caller and no first-version rule for that early record. v1's answer (default 5: the outcome rides in the turn its text joins, and with danger the actor closes the batch at once) does not cover it, and the job caller cannot carry it: K-34 v1 holds a text's outcome to a turn (`safety_outcomes_text_has_handle_and_turn`), and K-04 an outbox row to its turn (`outbox_rows.turn_id` not null), so a record with no turn is refused by the database. v1's request stays valid in v1.1 (a minor version only adds), so the action layer answers a text's outcome (source text) sent alone with no turn with `constraint` (`safety_outcomes_text_has_handle_and_turn`, 23514) and writes nothing; v1's page and agent records, which carry no turn, are unchanged. v1.1's answer, only adding:

- **`caller.kind` actorOnArrival** (`$defs/arrivalCaller`; default 36): the handle actor records a text whose read holds danger or timed out at once, before batching, in the text's own **arrival turn**: one event id, the text's; its id the hash of a marked input, `arrivalTurnId(eventId)`: the SHA-256 of the UTF-8 bytes of `arrival:` followed by the event id, in lowercase hex (`tool-api.rules.mjs` exports the function, so the actor and QA compute it the same way), as a clock turn's input is its clock row's id (K-05 v1 default 9); its trace id the text's own (CQ-06). `recordSafetyOutcome.arrival` carries that turn (K-05 v1 `turn`), and the call commits through K-05 v1 commitTurn: the outcome row, its hold, the checked line as an outbox row of send class safety and who is told, in one transaction. The text joins its batch's turn too, and **the two ids never meet**: a batch turn's id is the hash of its sorted event ids alone (CQ-09; T-248 builds it), never the marked input, so even the usual batch of the danger text alone (default 5 closes it at once) gets an id of its own, and K-05 v1 commitTurn writes it instead of answering `repeated` with nothing written (K-05 README item 1). Its `recordSafetyOutcome` core action for the text answers `repeated` (the event id is the key), its routine parts the hold answers `held` while it is open, and a STOP in any words or a protecting change in that text commits there at once, past the hold (RULES 7.2; MASTER-FLOW-A line 7208; default 35): `j3-safety-arrival-batch-turn.json`, after `j3-safety-arrival-emergency.json` (whose words hold neither, so its commit is the turn and the safety record's repeat), and `j3-safety-arrival-threat-batch.json`, after `j3-safety-arrival-threat.json` (A3-48: its commit writes the pause and the visit's call-off clock). The rule `arrivalTurn` checks the arrival id from the event id, and that a batch turn's id is none of its texts' arrival ids.
- **A read that timed out** (no verdict in 4 s: arch 02 line 111) is recorded on arrival too: with a danger word, that word's safety line, an outbox row of send class safety (`j3-safety-arrival-timeout.json`, K-02's `safety-timeout-danger-word.json` word for word); with none, the outage line, an outbox row of send class quick_reply as T-246 sends it, named by `safetyLine` the same way (its fixed line id and row); routine is held either way. K-02 v1 has no fixture of a timeout with no danger word, so that branch has none here. A read of No has no arrival record: it rides in the turn its text joins, as default 5 says (`invalid/refuse-j3-arrival-record-of-no.json`). Only these two variants take the arrival caller, and only alone, never inside `gateAndCommit`.
- **The first version rule** (default 37): a hold the call writes is at version 1 (K-34 v1 rule 2: `version integer not null default 1`), and v1.1's answer returns it (`hold.version`, its stored version on a repeat). The actor's at-once release (`releaseSafetyHold.arrival`) names it (`expectVersion`) under the same arrival turn, with `why` `outcome_message_sent` only, once it has handed the checked line on (arch 06 line 319).
- **For T-246's code** (a new task for the runtime engineer, outside this card): the early record moves from the job caller to `actorOnArrival` with the arrival turn, and the release takes its version from `hold.version`.

### Named rules added (`tool-api.rules.mjs`)

v1's four rules stay as they are; v1.1 adds two under new names.

- **`givesJourneyKeys`:** an exchange whose `given.stated` names a journey 3 step writes exactly the keys that step gives (`J3_STEP_GIVES`, from A-J3.md and B-J3.md), its outcome wrote exactly the stated keys, and, made alone, its call is the one call that writes each key (`KEY_CALL`).
- **`arrivalTurn`:** a call made by `actorOnArrival` names its arrival turn as `caller.turnId` and `requestId`, a SHA-256 in hex; a record's turn id is `arrivalTurnId` of its text's event id, its one event id the text's, its handle and its trace id the text's, its read holds danger or timed out, its answer gives safe, and a hold it wrote is at version 1. On the batch turn after an arrival record (`gateAndCommit`), its id is none of its texts' arrival ids, it commits under its own id (`repeated` false), and each text's safety record in it answers `repeated`. `ARRIVAL_MARK` and `arrivalTurnId` are exported beside the rule.
