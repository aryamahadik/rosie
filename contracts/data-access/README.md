## The calls

Every call reads and writes PostgreSQL's **primary, uncached**: each one is a decision or a write ("Decision reads go to the primary, uncached": arch 02 line 117; arch 10 lines 504, 536, 538). None of v1's calls is search or a report, so none reads the replica, and none goes through Hyperdrive's 60 s read cache (arch 10 line 504).

**Scope** (arch 10 line 546; K-04 v1 rule 4): `runtime` means the unscoped side K-04 names for the jobs that work across businesses by handle; `business` means the Tool API side, with the setting `rosie.business_id` (K-04 rule 4's proposal) set to the request's business for the transaction; `per write` means the transaction sets `rosie.business_id` to each write's own business before that write (`set_config(..., true)`), so a turn touching two businesses' bookings (arch 03 line 159) never reads or writes a third's, while writes with no business (sign-up before there is one, Rosie's own lines) and the tables K-04 scopes `none` (turns, handles, phones, persons, threads) go on the runtime side.

## How each call works on K-04 v1 as frozen

These are the rules the database engineer builds (C-152) and QA's contract test checks (T-084). Each call is one transaction.

1. **`commitTurn`** inserts the `turns` row as `committed` (QUESTIONS.md NQ-RT-3's default: the 60 s lease lives in the actor, so the row is written once). A unique violation on the turn id means a repeat: a committed turn returns its first commit (`turnId`, `committedAt`, its outbox rows by `turn_id` in commit order; `written` and `promoted` empty, since this call wrote nothing; K-04 keeps no copy of a result), whatever the repeat's body; a parked turn returns `turnParked`. Then, in this order: every row in `versionsRead` is read `FOR SHARE` (`FOR UPDATE` when the turn writes it) and compared, and every reservation to confirm is locked `FOR UPDATE`; a reservation that is not `held`, or is held past its `held_until`, refuses the commit with `reservationLost` (limit 5, checked before its version); any other version mismatch refuses it with `versionChanged`, listing every row that changed (limit 4: arch 06 line 305). Then the writes: state writes (an update raises `version` by one), open questions opened (status `waiting`) or closed, clock rows made (`waiting`, or `armed` with `due`) or cancelled, outbox rows with no plan (K-04's default state; `commit_seq` from its identity column, so commit order is the database's), reservations confirmed (`booked`, with the booking, and the reservation's saved-time clock row cancelled) or released (as `release` does, promotion included), and the event-log entries, each carrying the turn id, its trace id and its bundle. A database rule that refuses a write (EXCLUDE 23P01, CHECK 23514, unique 23505, foreign key 23503) rolls everything back and answers `constraint`.
2. **`writePlan`** locks the row; a row that already holds a plan answers `alreadyPlanned` (checked before its version), else the version is compared and `plan` and `final_parts` are written together (K-03 v1 `rowPlan` and `finalParts`; that the plan's `row` is this row is a code check). **`unplannedRows`** lists a turn's rows whose `plan` is null (K-04 `outbox_rows_unplanned_idx`).
3. **`claimOutbox`**, with no claim-time column on outbox rows (K-04 v1): recipients are taken one at a time, earliest open `commit_seq` first, each under a transaction-level advisory lock keyed on the recipient's handle id (`pg_try_advisory_xact_lock`); a recipient whose lock another claim holds is skipped, which is `SKIP LOCKED`'s meaning per recipient. Under the lock the recipient's open rows are read in `commit_seq` order `FOR UPDATE` and walked: a row held for text hours (`held_until` after `now`) is passed and reported in `passedHeld` (arch 02 line 125, DD); a row claimed earlier and not finished, or one with no final parts yet, stops the walk for that recipient (commit order); any other row is claimed: its state moves to K-07's claimed state and its version rises by one, and each part gets its row under the key `<row>/<part>/<try>` (a new part try 1 with `attempts` 1 and its K-03 send kind; a part the provider never accepted keeps its stored key with `attempts` raised: arch 11 line 576). The claim is that state move under compare-and-set, so two dispatchers never hold one row. How a claim that is never finished lapses (a dispatcher that died) is K-07's (open gap 1).
4. **`markPart`**: `sent` records the provider's ids and `sent_at` (first time only); `delivered`, found by the provider's message id, records `delivered_at` once and says `firstDelivery` when no part of the row was delivered before, so the caller arms the question's clock (arch 02 line 127); `failed` records `failed_at` and the error code, and with `retry` writes the next try's part row under a new key (arch 01 line 65); `attempt` raises `attempts` for a retry under the same key after a timeout. **`markRow`** is limit 8's outcome (arch 06 line 313): `held` sets `held_until` and returns the row to the open rows, to be claimed again after it; `droppedStopped` and `withdrawn` close it; `stale` clears `plan` and `final_parts`, so `unplannedRows` lists it and it is composed again from today's record (S13-57). The state words are K-07's.
5. **`armClock`** finds the row (or the question's `question` clock row), locks it, and moves `waiting` to `armed` with `due_at`, `due_zone` and `armed_at`; its open question moves from `waiting` to `open` in the same transaction (default 8). An armed row answers `repeated` with its first arming; a fired or cancelled one `clockClosed`. **`cancelClock`** moves a waiting or armed row to `cancelled`, and with `withdrawQuestion` withdraws its open question in the same transaction (the passed-on path: arch 02 line 123).
6. **`dueClocks`**: for a handle, its armed rows due by `now`, earliest first, and `nextDueAt`, its earliest armed row after `now`, where the actor sets its one alarm (K-04 `clock_rows_handle_due_idx`); for the sweep, armed rows no handle owns due by `now` and handle rows due before `missedBefore` (K-04 `clock_rows_due_idx`; arch 10 line 540). A read: the firing does the compare-and-set.
7. **`fireClock`** locks the row: `fired` answers `repeated` with the first firing; `waiting` or `cancelled` answers `notArmed`; a version mismatch `versionChanged`; a due time after `firedAt` answers `notDue` unless `by` is `fireNow` (staging only, BP 9.4; the Tool API allows it on staging alone, K-21). Then, as `commitTurn` does, the firing's turn row (when given) and its writes, and the row moves to `fired` with `fired_at`, all in one transaction (arch 10 line 508). Its event-log entries carry the `jobId`, and the turn id when there is a turn (K-04 `event_log_turn_or_job`). Per QUESTIONS.md NQ-RT-4's default the firing is a turn on the handle's actor whose only input is the clock row; its one event id is the clock row's id (default 9).
8. **`reserve`** runs under the reservation's business. The same reservation id with the same request answers its outcome again (`repeated`), with another request `idConflict`. An inactive resource, or one of another business, is `notBookable`. **The cap of 2 saved times** (arch 05 line 247): for a mobile, the call first locks its `phones` row `FOR UPDATE`, so two parallel reserves for one mobile run one after the other, then counts its `held` rows whose `held_until` is after `at` across every business, through a database function that runs unscoped and returns only those rows' ids and ends (row-level security would hide the other businesses'); for an agent token, which has no row in K-04, it takes a transaction-level advisory lock keyed on the business and the token, then counts the token's held rows at that business. A third is refused with `savedTimeCap` and both ends. Waiting rows never count ("they wait next in line while saving another": A4-18). A worker, room or vehicle: the held row is inserted in a savepoint with `held_until` = `at` + the door's minutes; EXCLUDE refusing it (23P01) means `overlap` if a booked row overlaps or `waitIfSaved` is false, else a `waiting` row whose `queued_at` is `at` (A4-18). A class session: `class_seats.taken` rises by `seats`; the CHECK refusing it (23514) is `seatsFull` with the capacity and seats taken. A held row gets its saved-time clock row, id `<reservation id>/saved-time`, kind `saved_time`, armed and due at `held_until` in the business's time zone (CQ-05's default), owned by the mobile's handle or, for an agent token or a booking, by the sweep, firing `{"release": <reservation id>, "why": "expired"}`.
9. **`release`** locks the row: a released row answers `repeated` with its first release; `expired` needs a held row whose `held_until` has passed (`notExpired` otherwise); else the version is compared (null for the clock's expiry). The row moves to `released` with `released_at` and `released_why`; a class session's `taken` falls by its seats; its saved-time clock row, if not fired, is cancelled. **Promotion** (A4-18; K-04 `queued_at`): when the row was held or booked, the waiting rows of the same resource whose time overlaps the released time are read `FOR UPDATE` in `queued_at` order, a tie to the lower id (compared, never parsed: CQ-09; K-04 `reservations_waiting_queue_idx`). Each in turn: its mobile's or token's cap is checked as `reserve` checks it (two held already: `skipped`, `savedTimeCap`); then, in a savepoint, it becomes `held` with `held_until` = `at` + 10 minutes (the standard saved time, S12-01; it must have an end: K-04 `reservations_held_has_end`), which EXCLUDE refuses (23P01) when another held or booked row overlaps it (`skipped`, `overlap`; it stays waiting). The first one held is promoted, with its own saved-time clock row, and the walk stops. Class sessions have no waiting rows (`reserve` answers `seatsFull`), so nothing is promoted there.
10. **`extend`** locks the row: not held, or past its end, is `notHeld`; the `ownAi` door is `neverExtended` (MC C3); `extended` already set is `alreadyExtended`; else `held_until` rises by 10 minutes, `extended` is set, and the saved-time clock row's due time moves with it (Q-12).
11. **`readActiveBundle`** reads the `bundles` row with `active` (at most one: `bundles_one_active`); **`readBundleValue`** reads `bundle_values` by key and returns the stored bytes as UTF-8 text with their size and sha256, which the reader checks (K-01 v1 `storedValue`). **`publishBundleCopy`** inserts the registry row and every value once (K-04 checks the bytes and sha256 against the value); the same bundle again with the same values answers `repeated`. **`setActiveBundle`** locks the active row, compares it with `expectActive` (`activeChanged` otherwise), clears it and sets the new one with `activated_at`; an id already active answers `repeated`; an id with no registry row answers `notPublished`. Rolling back is the same call with the earlier id (tour line 658).
12. **`parkTurn`** inserts the `turns` row as `parked` with `tries` 3 and `parked_at` (arch 11 line 576), the one "nothing changed" outbox row and its event-log entries; a parked turn answers `repeated`, a committed one `alreadyCommitted`.

### How each v1.1 call works (K-04 v1 and K-07 v1 as frozen)

13. **`claimOutbox`** (v1 item 3, with K-07's claim): a claim writes or updates the row's `outbox_claims` row (`claimer`, `claimed_at` = `now`, `lapses_at` = `now` + 60 s, `claim_no` 1 or raised by one, its own `version` raised) and returns it as `claim`, with `claimedFrom`. Under the recipient's lock the walk now also takes a `sending` row whose claim has lapsed (`lapses_at` ≤ `now`), or that has no claim row (claimed before v1.1 was migrated): claimed again by compare-and-set (row version and `claim_no`), its unsent parts under their stored keys with `attempts` raised as v1 says, and `first_try_at` and `next_try_not_before` kept. A `sending` row with a live claim stops the walk, as in v1. A `waiting_chat` row is passed, as a held row is (K-07: it waits for the chat to open, not for the dispatcher), and is not listed in `passedHeld`; `planned` and `stale` rows stop the walk; finished rows (`sent`, `delivered`, `dropped_stopped`, `withdrawn`, `failed`, `superseded`) are skipped.
14. **`renewClaim`** is the dispatcher's call just before each send of a part, a first send or a retry under the same key (K-07: "renewed by 60 s at each part attempt"; `firstTryAt` "written by the dispatcher at its first send"). It locks the row and its claim: the row must be `sending` and the claim the caller's (`claimer` and `claimNo`), or `claimLost`; a lapsed claim nobody has taken again is still the caller's. The key must be a `pending` part of the row (`wrongState`). A `next_try_not_before` after `at` answers `notYet` with that time. Otherwise `lapses_at` = `at` + 60 s, `first_try_at` = `at` if null, `next_try_not_before` cleared; only the claim row's version rises, not the outbox row's.
15. **`markPart`** (v1 item 4, with K-07's moves): the part moves as K-07's `partMove` allows (`wrongState` otherwise: `sent` for a part that is not pending, a receipt for a part neither sent nor failed), and the row moves with its parts in the same transaction: the last part accepted, `sending` to `sent`; every part's latest try delivered, to `delivered` (from `sent`, or from `sending` after a 4001 or 4006); `failed` with `retry` on a part of a `sent` row, back to `checked`, so it is claimed again. Every mark that changes a part raises the row's version by one, and the answer's `row` gives the state and version, so the dispatcher compares them in its next `markRow` (the database engineer's note). `failed` may carry `providerMessageId` (stored in `linq_message_id` when the part has none, so a receipt that comes after a 4001 or 4006 finds it: K-07 open gap 13) and, with `retry`, `nextTryNotBefore`, the provider's Retry-After, stored in the claim's `next_try_not_before`. **A failed safety line** (arch 02 line 125: it "retries every 10 s for 15 minutes and goes at once every other way the person allows"; RULES 4.12; K-07 retry rule 3): with the safety line's first reported failure, `failed` carries `followUps` (`safetyOtherWay` rows, one per other way the person allows) and their `events`, and the call inserts the rows in the same transaction as the failure, as item 17 writes follow-up rows (`planned`, under the failed row's turn id, bundle and trace id; `commit_seq` from K-04's identity column), with one K-08 `outbox_row.created` entry per row whose `why` names the failed row and `safetyOtherWay` (the link K-07 open gap 3 keeps in the event log). The answer lists them in `followUpRows`. A repeat (the part already failed) writes none; a row id already taken refuses the mark with `constraint`. That the row is a safety line, and that only its first failure carries them, are code checks (C-126); its retries every 10 s carry none.
16. **`markRow`** (v1 item 4): the row must be `sending` (`wrongState` otherwise). `waitingChat` moves it to `waiting_chat`, clears `held_until` and deletes its `outbox_claims` row; no clock arms and nothing is sent (arch 06 line 313; RULES 4.1b; MC C9). The other outcomes keep the claim row, so `claim_no` keeps counting the row's claims (a held row's morning claim is claim 2: K-07 `outbox-held-text-hours`).
17. **`dispatcherGivesUp`** locks the row and its claim: `sending` (`wrongState`), the caller's claim (`claimLost`), its version (`versionChanged`), and a `first_try_at` at least 15 minutes before `at` (`tooSoon`, with the time, or null when no part has gone). The row moves to `failed`; the claim row stays as the record of the tries; parts keep their states. **In the same transaction** the rows that follow it are written (arch 02 line 125: "Sends still failing after 15 minutes of tries: the next way the person allows; none left, the owner gets the number to call"; S12-10; K-07 retry rule 5): `followUps`, each a K-07 follow-up kind and a new row as a commit writes one (`followUpRow`): `nextWay`, one row per next way the person allows (such as an email row with no `copyOfRowId`), or, with none left, one `ownerGetsNumber` row to the owner. Each is inserted `planned` with no plan under the failed row's `turn_id`, `bundle_hash`, `bundle_build` and `trace_id` (K-04 `outbox_rows.turn_id` is not null, and a turn row is written only for texts), with `commit_seq` from K-04's identity column, so it comes after every row committed before; `unplannedRows` lists it with that turn's rows, and it is composed and checked as any row is (`writePlan`), then claimed and sent. `events` (at least one) are appended with the failed row's turn id, trace id and bundle: the move to failed (K-08 `outbox_row.state_changed`) and one `outbox_row.created` per follow-up row whose `why` names the failed row and its follow-up kind, which is the link K-07 open gap 3 keeps in the event log. The answer lists the rows in `followUpRows`. A row id already taken refuses the call with `constraint`, and nothing is written. `followUps` is empty only for a safety line whose other ways already went at its first failure (item 15) or a row to the owner with no other way left (open gap 13). Which ways the person allows is the caller's read (K-05 v1.2's recipient send state; C-126).
18. **The commit's effects** (`commitTurn` and `fireClock`, `writes.effects`): after the state writes, each `write` is inserted into `effects` as `pending` with the turn's id (or, for a firing with no turn, the request's `jobId`), `tries` 0, `runs` 1, under its own business (per write; a contact effect, with no business, on the runtime side: K-07). Each `letGo` locks its effect, compares its version (`versionChanged`) and needs `outage` (`wrongState`), and moves it to `cancelled`. Both are listed in `written` with their versions. A unique key already taken (`effects_idempotency_key_key`) or a K-07 CHECK refuses the commit with `constraint`. The commit logs only what it writes, in `events`, as for every other write: one K-08 `effect.created` entry per effect written, and one entry per effect let go for its move outage → cancelled (`commit-lets-go-outage-effect`). A try's result is never logged by a commit: `recordEffectResult` appends it in its own transaction (item 21).
19. **The commit's waiting rows** (`writes.waitingChat`): with `supersede`, every `waiting_chat` row to `recipientHandleId` moves to `superseded`; with `withdrawForBookings` and `withdrawForQuestions`, every `waiting_chat` row whose `booking_id` or `open_question_id` is listed moves to `withdrawn`. The call finds the rows itself, `FOR UPDATE`, so none is missed, raises each version, appends one event-log entry per row (K-08 `outbox_row.state_changed`: actor rosie, old state `waiting_chat`, the new state, `why` naming the answer row or the closed booking or question; id `<row id>/superseded` or `<row id>/withdrawn`), and lists them in `commitResult.waitingChat`. That the answer row is one of this commit's `outboxRows` to that handle is a code check. The event-log entry is the link K-07 open gap 3 asks for until a column holds it.
20. **`claimEffects`** takes, oldest `created_at` first (`effects_claimable_idx`), `FOR UPDATE SKIP LOCKED`, `pending` rows and `running` rows whose `claim_lapses_at` ≤ `now`, of the listed `ports` or any. A pending row starts its run: `running`, `first_try_at` = `now`, `tries` 0. A lapsed running row keeps `tries`, `runs` and `first_try_at`. Both get `claimed_by` and `claim_lapses_at` = `now` + 60 s, and a raised version. Rows in `outage` wait for `serviceBack`. It takes no event-log entries: it picks its rows itself (`SKIP LOCKED`), so the caller cannot name them beforehand, and K-08 v1 has no kind for a claim (only `effect.created` and `effect.result`); the run it starts shows in each result's entry (item 21: old state `running` with its tries and runs). An entry for the claim itself is open gap 15.
21. **`recordEffectResult`** locks the effect: `running` (`wrongState`), the caller's claim (`claimLost`), its version (`versionChanged`). `tries` rises by one and `last_try_at` = `at`. `ok`: `succeeded`, with `provider_object_id` and `ledger_line_id`. `declined`: `declined` with `error_code`, never tried again (RULES 3.11). `networkError`: `error_code`; the run's 5th try moves it to `outage`, else it stays `running` with `claim_lapses_at` = `nextTryAt` + 60 s (`at` + 60 s when `nextTryAt` is null). Leaving `running` clears `claimed_by` and `claim_lapses_at` (K-07 `effects_running_is_claimed`). **Every result is logged in the same transaction** (arch 09 lines 457, 492: every write appends who, what, old → new, when, why): `events` is required, at least one K-08 `effect.result` entry for the effect (actor `job`, the effects runner; old and new state, tries, runs and error; `why` the try's outcome, and on the run's 5th failed try the service's outage), appended with the effect's turn id, or its job id when it has none, its trace id, and the turn's bundle (null for a job) (K-04 `event_log_turn_or_job`). The runner's span for the call is K-08's `effectRun`, not an entry here.
22. **`serviceBack`** takes the port's `outage` rows, oldest first (`effects_outage_idx`), `FOR UPDATE SKIP LOCKED`: `running`, `runs` + 1, `tries` 0, `first_try_at` = `now`, claimed as `claimEffects` claims. Each runs once more on its same key (arch 11 line 582). Like `claimEffects` it takes no event-log entries (open gap 15); the new run shows in each result's entry (`runs` raised, `tries` from 0).
23. **`recordProviderEvent`** runs on the runtime side, unscoped (the gateway may not know the business, and row-level security would hide another business's row from the conflict's read: the database engineer's note): `insert ... on conflict (provider, provider_event_id) do nothing`; on a conflict it reads the stored row and answers `repeated` with its `receivedAt` and `effectId`, whatever the repeat's body. It writes nothing else; `handled_at` stays null (open gap 11).
24. **`reconciliationRefund`** inserts one `stripe_refund` effect, `pending`, with `job_id` and `booking_id` null (K-07 default 12), under the refund's business, and its event-log entries with the job id (K-04 `event_log_turn_or_job`). The same effect id again answers `repeated` with the stored version and writes nothing; another effect id with a taken idempotency key is `constraint` (23505).
25. **`writeAllSet`** writes the one short "all set" (arch 02 line 125: "once texts work, one short 'all set'"; S12-10: "Once texts work, a short 'all set' goes out. Nothing already emailed is sent again in full"). **Who:** the dispatcher (C-126), once it finds texts to the person work again. **When** texts count as working the sources do not say (K-07 open gap 12): open gap 14 here, so the call carries no rule for it. It locks each of `failedRowIds` (each must be `failed`: `wrongState`, or `notFound`) and inserts `row`, a text row (never email), `planned` with no plan under the first failed row's turn id, bundle and trace id, as item 17 writes follow-up rows, with its `events` (K-08 `outbox_row.created`, `why` naming the failed rows it closes). That the failed rows are this person's and went another way is a code check. K-07 gives the "all set" no follow-up kind of its own, so it is an ordinary row.

### The stop and the send (T-259's window)

A STOP can commit at any moment, and the part's send is a call to Linq outside the database, so nothing inside the database can close the window between the last read of the stopped flag and Linq's acceptance of the part: holding a lock on the phone row across the send would hold a transaction open across a network call and stop the STOP's own commit, which must go at once (RULES 7.2). What v1.2 does: the last read before a send is the renewal itself (item 32): the dispatcher renews just before each part goes, reads the stopped flag in that same transaction, `FOR SHARE`, so a STOP that is committing is waited for and seen, and sends with no other read between (T-259's re-read before `sendPart` becomes the renewal's). **What is left:** a STOP that commits after the renewal's read and before Linq accepts the part lets that one part out. An exact opt-out word (STOP, UNSUBSCRIBE, OPTOUT, CANCEL, END, QUIT) is blocked by Linq itself, 403 with code 2024, on every send after it (arch 10 line 524), so what can still go is one part after a stop in other words, which a turn decides and commits inside that gap of milliseconds; the next part's renewal reads the stop (open gap 21).
