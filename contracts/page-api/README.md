## What it defines

The calls the web app makes (02-contracts K-21: "each served by a Tool API call or a page-only call of the action layer"). Every screen is an optional view of something also done by text or email, except where a page is needed: typing a card, signing, private details, an ID photo, connecting Stripe or a calendar (FS line 8, D83). Every change is read back and confirmed first (FS line 630). v1 covers journeys 1 and 2 and the shells of M2 and M3b; customer screens, the public listing and the owner console's pages come with K-21's journey versions (02-contracts K-21 "Minor versions").

Every field's `description` names its source. "arch NN line N" are the lines of `scratch/text/architecture.txt`, as `ops/plan/02-contracts.md` cites them. Frozen contracts are reused by relative `$ref` where a call carries their shapes, never redefined: K-09 v1 (`notAllowedError`, `bookingPausedError`, `fixedLineId`, `emailAddress`, `kindId`, `saveSetupStep.response` and `.errors`, `readSetup.response` and `.errors`, `sendProofCode.errors`, `proveCode.response`, `acknowledgePage.response` and `.errors`, `decideReviewItem`'s decision, response and errors, `gateAndCommit.fired` and its `notArmed` error, `pageTeam`'s reasons, `openReviewItem`'s kinds), K-05 v1 (`version`, `rowRef`, `transientError`, `versionChangedError`), K-08 v1 (`traceId`), K-01 v1 (`stepId`, `answerField`), K-02 v1 (`choice`, `language`), K-11 v1 (`sendPart.request`, `.response`, `.errors`), K-14 v1 (`httpsUrl`, `clientSecret`, `cardShown`), K-16 v1 (`provider`) and the shared formats (`id`, `turnId`, `utc`, `zone`). K-22 v1, K-23 v1, K-28 v1, K-29 v1, K-36 v1 and K-37 v1 are table lists, so the calls name their tables and columns in words and enums.

### No browser value says who anyone is

Every request carries a page envelope (`$defs/page`, `linkPage`, `signedInPage`, `signedInLinkPage`): the page's own request id (the repeat key), the trace id, the session cookie's token as the browser sent it, and the signed link's short code. **No request names the person or the business it acts for.** The action layer's page entry builds K-09 v1's caller on the server:

- **The person** is the live session's: the server takes the token's sha256 and asks K-22 v1 `session_for_token`, whose person the call then acts for (K-22 v1 rule 4: "a portal or secure-page call with a session: the session's person"). With no live session the call acts for no one, and a call that needs a person answers `signInNeeded`. The schema refuses a sign-in request that names a person (`invalid/refuse-sign-in-names-person.json`) and a page's yes with no session (`invalid/refuse-yes-without-session.json`).
- **The business** is the signed link's own (the link row on the server, K-22 v1.1 `page_links`, names its business, its step and the person it was made for: section "Links"), or the business of the row a call names (a question, a review item, a test phone), checked against the session's person by row-level security and limit 1 (arch 10 line 546; arch 06 line 299).
- **A link is never the proof** (FS line 701; S13-45: "Opening a link never counts"). It names which page, which business and whose page, never who is at the browser. A link's page acts for its person only when a session of that same person comes with the request; with anyone else's session it acts for no one (`openLink` answers proof none, and a call that needs the link's person answers `signInNeeded`), and the answer never says whose link it is. The schema refuses an open link with no session that answers as if it proved someone (`invalid/refuse-link-as-proof.json`).
- **Whom a code is for** (K-09 v1 `sendProofCode.forPersonId`) is set by the server: from the account the typed mobile or email finds on the runtime side (a portal sign-in, S11-52), or from the person the page's own signed link was made for (a secure page's sign-in, S1-10's owner email), never from the browser (K-09 v1 default 34). The page holds only an opaque attempt id; the code's id and its person stay on the server with it (K-22 v1 rule 4; security note N13 on K-09).
- **Ids the K-09 calls take** that a page could forge come only from the server's records: the page's yes event (`yesEventId`, made by the server), the owner's proving text (`provenByEventId`), an upload's object key, the Stripe account and bill card ids, a calendar link id.

### Who may call, how each is bound, its repeat rule and its errors

Every call reads PostgreSQL's **primary, uncached**: each is a decision, a write, or a screen that acts at once (arch 02 line 117; arch 10 line 538). None is search or a report. No source gives a time budget for a page call; the K-09 call behind one keeps its own (K-09 v1 README). Every call writes a `pageRequest` span (K-08 v1) under the request's trace id. Every call may also answer `transient` (K-05 v1: nothing was written; send again), and while PostgreSQL is down a call answers `bookingPaused` where its errors list it (K-09 v1; arch 11 line 566: "the booking page hear[s] that booking is paused"), and `transient` otherwise.

- **The same answer whether or not an account matches** (S13-45: "Those words are the same whether or not a booking exists"): `signInStart` answers `started` with an attempt id either way, never a masked address; a way with no contact on file sends nothing. A `paused` answer (five wrong codes, or the day's codes to a contact used up: "At most a few codes a day per contact", S13-45; K-22 v1 `proof_code_limits`) is counted per contact typed, so it shows for any contact typed that often.

The server keeps only its sha256 (K-22 v1 `sessions_token_hash_form`), and the device cookie's sha256 (`sessions.device_sha256`), so it cannot send the token again: a repeat of that answer, and any later check of the same attempt, answers `alreadySignedIn` with no token, and a page with no session signs in again (default 20; `sign-in-already-signed-in.json`, `invalid/refuse-already-signed-in-with-token.json`; the security reviewer's gap 1 on 2413b65).

## Links (A4-42; FS line 701; S13-45)

- **The link row** is K-22 v1.1's `page_links` (`../db-schema/people-access/people-access.v1.1.tables.json`, added with this contract by T-030; DL-109): the business the page acts in, the person it was made for, its purpose (the page kind: `setup_id_check`, `owner_confirm`, `registration`, `staff_page`), the step that sent it, its code's sha256 (never the code), the person's own contact it went to, `expires_at`, and `ended_at` with `ended_why` (`step_done`, `contact_changed` naming the change, `left`, `handed_over`), with a version. It is scoped by business; the Tool API reads every column but the hash, inserts only a live link and ends only a live one, never reopening it (K-22 rule 8).
- **How a link is issued:** by the commit of the turn, or of the call made alone, whose step sends it (S1-10's ID check, S1-77's owner link, S1-27's or S1-29's registration screens, S1-79's summary, S2-06's staff page): one K-05 `stateWrite` insert into `page_links`, which K-05 v1.2's `commitTurn` already carries as it is (its `stateTable` admits every domain table but those with lists of their own), per write under the link's business, in the same commit as the outbox row whose message carries the link (arch 10 line 508). Code makes the code just before that commit (default 18), writes only its sha256, and hands the code to the slot filler (C-088), which fills K-03's `link.secure` with the host and the code when it finalizes that outbox row in the same run; the code is stored nowhere but in the message that carries it. No K-09 v1 call issues a link, and none is needed (open gap 19: a run that stops between the two).
- **How a link is found:** the page entry takes the code's sha256 and asks K-22 v1.1 `page_link_for_code`, a security-definer call that answers the live link's business, person, purpose, step, end time and version, or no row; no row is `linkExpired`. Then the call runs under that business's scope, for the session's person when it is the link's own (section "No browser value says who anyone is").
- **How a link ends:** it lapses at `expires_at` (its length is a setting: open gap 4); a contact change ends every link and page of that person sent before it, in the commit that writes the change (D75; S13-45 row 3: `contact_changed`, naming the change); a person who leaves the team (RULES 8.7) and a hand-over (S11-100) end theirs; and a setup link (`setup_id_check`, `owner_confirm`) ends once its step has given its keys (S1-10: "once"; security note N10 on K-09): the commit that gives them ends it where it can carry the state write (`step_done`), and the page entry answers `linkExpired` for such a link once K-09 v1 `readSetup` shows its step's keys given, whether or not the end was written, since a page's `saveSetupStep` made alone carries no other write (default 19).
- A link is the host plus a short code; the host is a config value (Q-51), rosfield.com/test on staging (DL-014, DL-023). The code is unguessable, with at least 128 bits (default 18); an unknown, lapsed and ended code all answer `linkExpired`.
- `openLink` with no session of the link's own person shows only what the page is for (`pageKind`, `stepId`, `sections`) and the business's public name, never a name, a time or anything on file for the person (S13-45: "nothing on file for it is used or hinted at"), and always offers both sign-in ways, so it hints at nothing on file either. With that person's session it may show its secure-page-only sections; their contents come from the page's own reads.
- After a setup link has ended, a new owner email needs a signed-in session plus the ID re-check (S13-45 row 8; security note N10 on K-09).

## Answers, read-backs and the page's yes
