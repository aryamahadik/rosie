## What it defines

One interface with two adapters (02-contracts K-16; MC 8 "Calendars": "Google and Microsoft are approved: two-way, busy times only"). Each call is a definition set under `$defs`: `<call>.request`, `<call>.response`, `<call>.errors` and `<call>.exchange` (a fixture). Google's and Microsoft's paths, headers, field names and codes stay inside the adapters (02-contracts section 5). Every field's `description` names its source; "arch NN line N" are the lines of `scratch/text/architecture.txt`.

| Call                 | What                                                                                                                                                                                       | Repeating it                                                                              | Span (K-08 v1)                  |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------- | ------------------------------- |
| `connectStart`       | The provider's consent address for one person's link, the state, the narrowest scopes and when the start lapses; started only on a page already open (`startedOn`: Q-10)                   | Safe: a new start each time; only the one finished counts                                 | none (no outside call)          |

| `renew`              | Renew it at `renewAt` or on Graph's `reauthorizationRequired`: Google a new channel replacing the old, Graph a new expiry on the same subscription                                         | Safe                                                                                      | `portCall`, one per try         |

The root is any one exchange, life, row or span, so the type generator writes a type for each. The effect calls are named for K-07 v1's effect kinds, as K-08 v1 already names them (`call`: "a K-07 effect kind such as charge or calendarWrite"; its fixture `span-effect-run-retry.json` uses `calendarUpdate` and passes `calendar.span`).

### Tokens and keys (arch 05 line 271; rule 7)

- **A token never crosses the port.** `connectReturn` exchanges the one-time code once; the adapter seals the access and refresh tokens under the person's key (K-04 v1 `sealing_keys`, C-156) with the link, the row K-27 (availability, F14) holds, and answers `tokens: "sealedUnderPersonKey"`, which says where they are. Every later call names the link by `calendarLinkId`; the adapter unseals, refreshes (Google access tokens are short-lived; Microsoft issues a new refresh token on each refresh, which replaces the old one: spike rows 7, 16) and seals again. No request, answer, span or log line holds a token, a code past `connectReturn`, a client secret or a push verifier (`refuse-token-in-answer.json`). Fixtures hold placeholders only (`placeholder-auth-code-…`, `made-at-test-time`).
- **The keys, named, never held** (02-contracts section 2 item 13; defaults until the CTO and the release engineer name them): `GOOGLE_CALENDAR_CLIENT_SECRET` and `MICROSOFT_CALENDAR_CLIENT_SECRET` for the token exchange and refresh; `CALENDAR_PUSH_SECRET` for push verifiers; the client ids `GOOGLE_CALENDAR_CLIENT_ID` and `MICROSOFT_CALENDAR_CLIENT_ID` are configuration, as are the redirect on the staging host (`rosfield.com/test`, J-05, J-13, Q-51) and the gateway's push address. The double needs none.
- **A refused token is a dropped link.** A refresh answered `invalid_grant` (access revoked; a Google refresh token unused for six months, over Google's 100 per account per client, or in Testing status past its 7 days; an admin's restriction) or Graph's `interaction_required` makes any call answer `linkDropped` with why `tokenRevoked`, which the caller gives K-09 v1's `calendarLinkDropped` (`error-link-dropped.json`).

### Connect (MC 8 "Calendars"; Q-10; S1-24; S2-06)

The person connects on a page already open: registration screen 16, the owner console or the staff page (`startedOn`); no link is texted for it, so no value names one (`refuse-texted-connect.json`). The caller (C-189) writes the link row first, new or the dropped one being reconnected (S12-13 "Reconnect your calendar"). The adapter keeps the pending connect (person, link, PKCE verifier) under the state until `expiresAt`. The scopes are frozen at the narrowest that cover K-16 (`refuse-scope-widened.json`):

| Provider  | Scopes asked and held                                     | Why                                                                                                                                                              |
| --------- | --------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Google    | `https://www.googleapis.com/auth/calendar.events.owned`   | T-1123: "the narrowest single scope that covers K-16, on calendars the person owns"; events.list and events.watch accept it, freebusy.query does not (rows 5, 6) |
| Microsoft | `offline_access`, `Calendars.Read`, `Calendars.ReadWrite` | ReadWrite writes events (T-1123 [M2]); Read because event subscriptions need it (row 14); offline_access for a refresh token. No admin consent (T-1123 [M1])     |

`declined` (the person said no) and `scopesMissing` (Google's granular consent let them untick a scope: the partial grant is revoked and the page asks again) leave S1-24's safe default: "nothing blocked yet, with one reminder". iCloud is not a provider (Q-11; `refuse-icloud.json`).

### Watch and renew (arch 05 lines 261, 271)

`watch` asks for the longest life each provider allows: Google's channel time-to-live default, 604800 s (7 days; no maximum stated), and Graph's 10,080 minutes for events less a minute. `renewAt` is halfway: "Each change subscription is renewed when half its life is left". Google channels cannot be renewed, so `renew` starts a new channel and stops the old one after it (both live in the overlap; a push on either is taken); Graph renews by a new expiry on the same subscription, which also reauthorizes it, and a subscription Graph removed is made again. Graph's `reauthorizationRequired` triggers a renewal at once (row 11).

**A renewal that keeps failing is a dropped link.** Each try is one `portCall` span with its `attempt`. Tries follow the effect rule, at most 5 in 10 minutes on one key (arch 10 line 542), each after any Retry-After (arch 10 line 540). The fifth failure drops the link with why `renewalFailed`; a try that finds the tokens refused drops it at once with why `tokenRevoked`. The caller then calls K-09 v1's `calendarLinkDropped`, and S12-13 follows: the owner is texted at once, that person's open times come off, booked visits stay, the rest of the team is still offered, and one reminder goes after 24 hours (arch 11 line 580; S12-14). `renewal.life` records the tries and the end (`renewal-failed-dropped-link.json`; `refuse-dropped-before-five-tries.json`). A first watch that fails is retried the same way (`watchId` null).

### Checking a push (the gateway, C-044; arch 02 line 109)

The gateway answers within its 1 s ("Stripe · calendar hooks: verify · scrub cards · dedupe · store sealed · acknowledge in < 1 s"):

| Push                                             | Check                        | Answer                                                        | Stored                                                                                                                             |
| ------------------------------------------------ | ---------------------------- | ------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| Graph's validation (`?validationToken=`)         | none: it carries no verifier | 200, `text/plain`, the URL-decoded token, within 10 s (row 9) | nothing                                                                                                                            |
| Google push, `sync` (number 1)                   | the channel token            | 200, `ignored`                                                | nothing: it only says the channel was made                                                                                         |
| Google push, `exists` or `not_exists`            | the channel token            | 200 after the write                                           | one K-07 provider event, eventType the state, notice `changed`                                                                     |
| Graph change or lifecycle notifications          | each item's `clientState`    | 200 after the writes (Graph wants a 2xx within 3 s, row 10)   | one per item: `created`, `updated`, `deleted` (changed), `missed`, `reauthorizationRequired`, `subscriptionRemoved` (watchRemoved) |
| Any verifier that does not match                 | as above                     | 401, dropped                                                  | nothing                                                                                                                            |
| A verified item of a watch Rosie no longer holds | as above                     | 200 (so the provider stops), counted in `unknownWatches`      | nothing                                                                                                                            |

A failed write answers 503 and the provider retries (arch 02 line 109; Google backs off on 5xx, Graph retries for up to 4 hours: rows 2, 10). **The verifiers:** Google's channel token (at most 256 characters) and Graph's `clientState` (at most 128) each carry the link's id and an HMAC under `CALENDAR_PUSH_SECRET`, compared in constant time, so the check needs no database read; neither is a credential to the provider, and neither is ever logged. Fixtures hold `made-at-test-time` and say in `given.verifier` how it was made; the contract test makes it at run time, as K-11's fixtures sign at run time. **Provider event ids** (K-07 stores each once by provider and id): Google's channel id and message number (`gcal-channel-riley-03:7`); Graph's notification id; for a Graph lifecycle notification, which has none, its subscription, event and subscription expiry (`graph-sub-sam-01:missed:2026-11-13T09:20:30Z`), so a repeated challenge is dropped and one after a renewal is new. The payload is `calendarNotice` (link, watch, notice), never an event's content; `businessId` is null (a link is a person's, across businesses: FS line 743) and `effectId` null (S12-33).

What a stored notice starts (C-136): `changed` and `missed`, a read (`readChanges`, trigger `push`); `reauthorizationRequired`, a renewal; `watchRemoved`, a new watch and then a read. Pushes are not fully reliable (row 2: "Notifications are not 100% reliable"; Graph drops notifications from slow endpoints, row 10), so the 30-minute poll (arch 11 line 578; C-137) runs `readChanges` with trigger `poll` on every link, and a fresh read is taken whenever a booking is written.

### Reading changes into busy blocks (arch 05 lines 261, 265)

`readChanges` answers the busy blocks that are new or changed and the keys no longer busy since the cursor (Google's sync token, Graph's delta link), and the next cursor. A busy block is its key, start and end in UTC, the event's zone and its source (provider and link), **never its title**, place, notes or guests (`refuse-busy-block-with-title.json`; S12-33: "The event's title is never shown to Sam or anyone"). Repeating events come as their instances inside the window, the 90 days ahead (arch 05 line 265). `full` is a whole new set for the link: the first read, a cursor the provider no longer takes (Google's 410 Gone; Graph's `syncStateNotFound` or 410: rows 3, 12), or a window that has moved; then `removed` is empty and the caller replaces the link's blocks.

**Busy, free and Rosie's own** (arch 05 line 265: "every event counts as busy, tentative ones too, except one marked free or a declined invite"; line 267: "Rosie's own events never come back in as busy"):

| Event                | Google (row 4)                                                            | Microsoft (row 13)                                           | Answer                    |
| -------------------- | ------------------------------------------------------------------------- | ------------------------------------------------------------ | ------------------------- |
| Busy                 | `transparency` opaque (the default), `status` confirmed                   | `showAs` busy, `oof`, `workingElsewhere` or `unknown`        | a busy block              |
| Tentative            | `status` tentative, or the person's answer tentative                      | `showAs` tentative                                           | a busy block              |
| Marked free          | `transparency` transparent                                                | `showAs` free                                                | removed                   |
| A declined invite    | the person's own entry (`attendees[].self`) has `responseStatus` declined | `responseStatus.response` declined                           | removed                   |
| Deleted or cancelled | `status` cancelled                                                        | `@removed`, or `isCancelled`                                 | removed                   |
| Rosie's own event    | Rosie's client-chosen id and a private extended property                  | Rosie's `transactionId` and a single-value extended property | never busy, never removed |
| All-day              | `start.date`, in the calendar's zone                                      | `isAllDay`, in its zone                                      | a busy block over the day |

The double turns `given.calendar` into its answer by this table (`changes-to-busy-blocks.json`: a declined invite and a free event removed, a tentative event busy, Rosie's own event left out). Zones: Graph names zones the Windows way (`Pacific Standard Time`), so the adapter maps them to IANA names.

### The fresh free/busy read (arch 05 line 259; A6-10)

"Search reads them from the read replica, so a booking is written only after a fresh free/busy read." `freeBusy` reads one link live over a span: `bookingWrite`, the visit's time, when the booking is written (A6-10, B6-10: "Rosie checks the calendars once more, then saves the booking"); `clashCheck`, the time ahead, when a dropped link is back, before its times are offered again (S12-13; K-09 v1 `calendarLinkBack`: "a fresh free/busy read through K-16"). It answers busy times only, with the event rules above and never Rosie's own events, so it runs as Google's events list over the span (freebusy.query refuses `calendar.events.owned`: row 5) and as Graph's calendarView for every account (getSchedule serves no personal account and returns subjects: row 15). If it fails, A6-10's safe default holds: "the booking isn't written until the time is still free" (`error-rate-limited.json`).

### Events out (arch 05 line 267; K-07 v1 effects)

After the commit, one effect row per visit per booked person: `calendar_write`, `calendar_update` (a move, B8-37) or `calendar_delete` (a call-off or a change of person), with this port's request as its `portRequest` (`calendarEffect.row`), run by C-109 on one idempotency key, at most 5 tries in 10 minutes (K-07 v1 rule 8). The event shows the business's display name, the service and the first name of the person served, or for a child the parent's (RULES 4.7); with the sensitive switch on only "Visit" and initials, never the service (RULES 4.6; S13-22; `event-sensitive.json`, `refuse-sensitive-with-service.json`). The adapter writes the title from those parts, as "Lee's Barbershop · Haircut · Alex" or "Visit · A.M.", on the person's primary calendar, marked busy, with no notes, place or guests, and sends no invitation. **Rosie's own events:** the event key makes the provider's repeat guard, Google's client-chosen event id (base32hex, 5 to 1024 characters, unique per calendar) and Graph's `transactionId` (set at creation, never changed), so a retried write answers the same event (`alreadyWritten`); with a private marker they are what the reads leave out. A delete of an event already gone answers `alreadyGone`; an update of an event the person deleted answers `gone` and is not written again (`event-move-gone.json`; default 12).

### The double (02-contracts K-16; Q-56; BP 9.4 "Seeded state")

Fake calendars, notifications, a dropped link and a clash, for the demo shops and test owners, until J-13's OAuth apps exist. The exchange fixtures are its answers; it is the C-216 and C-217 adapters' twin, and the contract test checks both against the same fixtures (on recorded samples once J-13 lands).

- **Its world:** Lee's Barbershop (Sam, owner, on Outlook, `callink-sam-microsoft`; Riley, staff, on Google, `callink-riley-google`) and Lee Associates (Maya on Outlook, Iris on Google), all in America/New_York. Alex's haircut with Riley on Sat Nov 14 (K-07's `effect-calendar-*` and K-05's `commit-writes-effect`) and Ben T.'s visit with Sam on Sat Nov 21 are the booked visits the clashes fall on.
- **Connect:** its consent page (`calendar-double.example.com`, Q-51's habit) returns at once with a placeholder code; a test may set its next return to `declined` or `scopesMissing`.
- **Its calendar:** a test sets a link's events (`given.calendar`, in the neutral terms of `doubleEvent`: shown as busy, tentative or free; the person's answer to an invite; Rosie's own or not; deleted or not), and the double answers `readChanges` and `freeBusy` by the event rules. A clash is a busy event over a booked visit (S12-33: `changes-to-busy-blocks.json`; `free-busy-clash-check.json`).
- **Pushes:** after a change the double posts a push for the link's watch, with a valid verifier, through the real gateway; a test may make one with a wrong verifier.
- **A dropped link:** a test sets the next call on a link to answer `linkDropped` (token revoked), or the next renewals to fail until the fifth (renewal failed).
- **Errors:** a test sets the next call to fail with `unavailable`, `rateLimited` (with its Retry-After) or `badRequest`; later calls answer as before. The setting is the double's test-only option, never a field of a request.

## Defaults used (T-025)

4. **The pending connect** (person, link, PKCE verifier) is kept under the state for 15 minutes (`expiresAt`); no source gives a time.
5. **The scopes** are T-1123's narrowest, with Graph's `Calendars.Read` added for event subscriptions (spike row 14). T-1123's option B (calendar.events.freebusy with calendar.app.created, events on a calendar Rosie makes) is the CTO's call and would be a new version.

## Open gaps

1. **J-13 and Q-56** (the OAuth apps, their accounts and the redirect; Google's sensitive-scope verification): T-1123 says submit by about Nov 20 for Dec 3. Until verification, Testing status allows 100 test users and their refresh tokens expire in 7 days, so staging links drop weekly (`linkDropped`, S12-13's text and S12-14's reminder).
2. **Graph and `Calendars.ReadWrite` alone:** the documents name `Calendars.Read` for event subscriptions and refuse write permissions "when only read access permissions are needed" (row 14), so v1 asks for both. A live check at J-13 confirms it; asking for both widens nothing.
3. **Which calendars count** (default 13): Google's scope reaches every calendar the person owns; Graph's `/me/events` subscription covers every calendar in the mailbox while the reads cover the default calendar, so a push from another calendar costs one empty read. Reading more calendars is a question for Jay (S1-24 speaks of one calendar).
4. **Rosie's own events in Graph's delta:** whether delta answers carry `transactionId` or the extended property (`$select` is not supported, row 12) is unverified; failing both, the adapter leaves out events whose id is a `providerObjectId` of Rosie's calendar effects. To be recorded from samples at J-13.
5. **The 90-day window:** Google's sync token takes no time bounds (row 3), so the adapter keeps only the instances inside the window and expands repeating events itself or through the instances list; Graph's delta range cannot move (row 12), so the adapter starts a new full read when the window has moved too far (how often is the adapter's). Both from samples at J-13.
6. **K-27 (F14) and K-05:** the link row (its sealed tokens, cursor, subscription and its life) and the busy blocks are K-27's; storing them and listing a link's unhandled provider events (K-05 v1.1 open gap 11) need data-access calls in a later K-05 minor version. 7. **A calendar effect on a dropped link:** K-07 v1 has no effect state for a refusal (its open gap 5).
