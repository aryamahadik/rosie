## What it defines

The port in Rosie's own terms (02-contracts K-13, section 5): six calls. R2's own interface and how a link is signed stay inside the adapter (C-219); the fixtures are port-level exchanges. Each call is a definition set under `$defs`: `<call>.request`, `<call>.response`, `<call>.errors`, and `<call>.exchange` (a fixture). Every field's `description` names its source; "arch NN line N" are the lines of `scratch/text/architecture.txt`.

| Call           | What                                                                                                                                                                                               | Repeating it                                                                                                              | Key                 |
| -------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- | ------------------- |
| `uploadLink`   | The signed upload from a secure page: kind, owner, size and type in; a short-lived link for one file and the object key out (02-contracts K-13). No object exists until the browser sends the file | A new key and link each call; the caller keeps the first with its upload id (K-21 v1: "a repeat answers the same upload") | `FILES_LINK_SECRET` |
| `checkUpload`  | The signed upload's second half: what came to the link, its size and its type read from its bytes: `stored`, `notStored`, or refused (`tooLarge`, `wrongType`, removed first)                      | Safe: a read, but a refused file is removed                                                                               | the `FILES` binding |
| `readLink`     | A short signed read link for one object, given only after the caller's check of who may see it; the call's span is the view's log line                                                             | Safe: a fresh link and a fresh log line each call                                                                         | `FILES_LINK_SECRET` |
| `serverWrite`  | A server-side write of one system object: a sealed trace, the event-log export, an export, a report, a photo that came in by text                                                                  | Safe under `writeId`: the same bytes answer `repeated` true; other bytes answer `conflict`                                | the `FILES` binding |
| `serverRead`   | Rosie's own read of one object's bytes on the server, for no person's eyes: C-120's photo reading, reports and evals reading the export (default 11)                                               | Safe: a read                                                                                                              | the `FILES` binding |
| `deleteObject` | The delete, for erasure under RULES 4.10 only; no deletion rule is invented (Q-31)                                                                                                                 | Safe: a second delete answers `alreadyGone` true                                                                          | the `FILES` binding |

Every call is neither a primary nor a replica read: it reads no database. No source gives any call a time budget; the calling stage's applies. Each try of each call writes one K-08 v1 `portCall` span, provider `r2` (section "Spans"). Every call may answer `unavailable` (R2 failed, timed out, refused or rate-limited it: a 5xx, a 429 or a network error), and the caller retries as arch 10 line 540 says for its job or turn; a page answers K-21's `providerUnavailable` meanwhile.

### Media types

The closed list (`mediaType`, default 17): the photo types K-21 takes (`image/jpeg`, `image/png`, `image/heic`, `image/heif`, `image/webp`) and `application/pdf` for uploads; for server writes, `video/mp4` and `video/quicktime` (a report, default 6), `text/csv` (an export, default 7), `application/vnd.apache.parquet` (the event-log export) and `application/octet-stream` (a sealed trace's sealed bytes). A photo takes only the image types; every other upload kind a photo or a PDF. Each write kind takes only its own: a sealed trace octet-stream, the export Parquet, an export CSV, a report a PDF, a photo or a video, a photo the image types. Nothing a browser runs as a page is ever taken: no SVG, no HTML or XHTML (K-35 v1 default 20; `invalid/refuse-svg-upload.json`).

### Owners

`owner` is whose an object is (02-contracts K-13 "owner (business, person or booking)"), bound on the server from the page's session and link, never from the browser (K-21 v1 "No browser value says who anyone is"):

- **person:** a file that is one person's own: their ID document, with no business (K-22 v1 `id_uploads` is per person across businesses; `invalid/refuse-id-document-for-business.json`), or a team member's own paper at their business.
- **business:** the business's photos, price list and own papers, and the customer list it exports.
- **booking:** a customer's photos, forms and papers on their own link, a report, a DONE photo; `personId` is the one person the file is from or about, so an erasure finds it, or null for the business's own record of the visit (a DONE photo, which B10-14's record holds as "the photos").
- **rosie:** a system object of no one business: a sealed trace and the event-log export (default 17 below gives each write kind its owner).

### The object key

`objectKey` is the file reference every other contract stores (K-02's photo reading, a later K-02 minor version: 02-contracts K-02 "a K-13 file reference"; K-06 v1's attachments; K-11 v1's `photo.fileId`; K-22 `id_uploads.object_key` and K-35 `document_files.object_key`, sealed; K-23 `business_photos.object_key`; K-31 `visit_marks.photo_key` and `visit_price_lines.receipt_key`; K-30's page answer paper, K-21 v1.2 default 65). Its form is `<kind>/<day>/<id>` (default 2):

- `<kind>` is the file's kind, so a later rule by kind (a lifecycle rule, a listing) needs no new key;
- `<day>` is the UTC day the key was made, `YYYY-MM-DD`; for the event-log export, the day of the rows it holds, so a reader takes one day's rows by the prefix `eventLogExport/<day>/` (default 18);
- `<id>` is 26 lowercase letters and digits from a cryptographically secure random source, at least 128 bits.

**The port makes every key.** `uploadLink` makes the id; `serverWrite` takes the writer's `writeId`, made by the same rule once per object, and its `day`. So a key never holds a name, a number, an address or anyone's words (`invalid/refuse-caller-names-key.json`), and it is never guessable from a row id, which keeps a sealed key the only way to its file (K-22 v1 README: "deleting the key erases the way to the file"). The key is never shown to a browser (K-21 v1 default 12: "the page names an upload id, never an object key") and never enters a span or a log (`invalid/refuse-key-in-span.json`).

### The link

An upload link takes **one file, by one PUT, with the type asked as its Content-Type**, of at most `maxBytes`, until `expiresAt`, and nothing else; a read link serves **one object until its end, always as an attachment with `X-Content-Type-Options: nosniff`**, never inline (K-35 v1 default 20; `invalid/refuse-read-link-inline.json`), so no stored file runs as a page, while a photo link still shows in a page's image (K-21 v1.1's listing photos). A link carries no key or secret a page could reuse for anything else (K-21 v1 `uploadUrl`). An upload link lasts 1 to 30 minutes and a read link 1 to 15, as the caller asks (default 3: K-21 v1's upload links last 15 minutes, v1.2's 10, v1.1's listing photo links 10).

**How a link is made** is the adapter's, behind these fields (default 13): a link the Worker signs itself, on its own route under the link host (on staging `https://rosfield.com/test/...`), with a secret named `FILES_LINK_SECRET` (rule 7: named, never shown; the CTO and the release engineer may rename it), which the Worker checks before it streams the file to or from the private bucket through the `FILES` binding (`wrangler.jsonc`, T-441). So the Worker can stop an upload past `maxBytes` while it streams, check its leading bytes, and add nosniff to every read, and no new credential or bucket setting is needed. The other way, R2's S3-compatible presigned URLs, would need an R2 API token as two more secrets (`R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`, a credential the user makes in the dashboard), a CORS rule on the bucket for the pages' origin (the bucket has none: section "Spike findings"), and could not add nosniff to a read (a presigned GET can set only the response's type and disposition); the port's fields would not change, but K-35 v1 default 20's nosniff would not hold. Server writes, reads and deletes go through the `FILES` binding and need no secret.

### What checkUpload reads

`checkUpload` reads the stored object's size and its type **from its leading bytes** (the signatures of JPEG, PNG, HEIC and HEIF, WebP and PDF), never from the browser's word or the Content-Type alone (default 8). A file larger than `maxBytes`, or whose bytes are not the type asked, is **removed before the answer** (`removed` true), so nothing refused is kept (`check-upload-wrong-type.json`). No file under the key is `notStored`, an answer, not an error (`check-upload-not-stored.json`). A file the page sent but never finished (no `checkUpload` call) stays in the bucket: open gaps.

### Each view logged

RULES 4.5: "These stay on the secure page, each view logged." A read link is asked only after the caller's own check of who may see the file (02-contracts K-13; C-094; limit 7), and the request says whom it checked and on what ground (`viewer`, default 15); with no viewer it is refused (`invalid/refuse-read-without-permission.json`):

- `self`: the person the file is about, on their own secure page;
- `business`: an owner, admin or staff member the file's business lets see it, in the portal or on the job or pricing page (K-35 v1's readers; K-30 v1's page answers; K-21 v1.2 default 60), never a customer of the business;
- `rosieTeam`: a person on Rosie's team, for a review item they work (S1-76; K-37 v1; K-36 v1 `team_page_recipients`; Q-18);
- `listing`: anyone, for a photo the business shows on its public listing, naming no person (FS row B07; FS 6.3; S1-84); only a photo (`invalid/refuse-listing-read-of-id-document.json`).

**Every read link's span is the view's log line** (default 12): who (`got.viewer`), on what ground (`got.as`), which row's file (`got.fileTable`, `got.fileRow`, from the request's `file`), when (the span's `at`), with no key or link (`span-read-link-logged.json`). Its full detail goes to the sealed traces (arch 02 diagram line 105). A view is the link's giving: a link the page fetches twice in its short life is one view. Whether RULES 4.5's log must also be an event-log row is open (open gaps). The port refuses no viewer itself: it holds no record of who may see what, and the link gives nothing beyond that one object for that short while.

### Repeats

- `uploadLink`: a new key and link each call; the caller keeps the first with its upload id and answers a repeat from it.
- `checkUpload`, `readLink`, `serverRead`: safe; `readLink` gives a fresh link and logs again.
- `serverWrite` (default 10): the writer makes `writeId` once per object and keeps it, with its `day`, for every retry (arch 10 line 540), so a retry lands on the same key. The same bytes there (the same `sha256`) answer `stored` with `repeated` true and the first `storedAt`, writing nothing again (`server-write-repeat.json`); other bytes there answer `conflict` and are never written over.
- `deleteObject`: nothing there answers `deleted` with `alreadyGone` true (`delete-already-gone.json`).

### Server writes and reads

A server write's bytes travel beside the request as the call's body, never in it; `sizeBytes` and `sha256` say which bytes. Each write kind has its owner, types and source (default 17): a sealed trace and the event-log export are Rosie's (`rosie`) and written by Rosie's code (`source` `rosie`); an export is the business's; a report a booking's; a photo a person's, the business's or a booking's. Only a photo comes in by text (`source` `linq`, with its K-06 `eventId` and `attachmentId`, so the attachment id becomes a file reference: K-06 v1 "K-13 turns the id into a file reference"; `server-write-linq-photo.json`). `serverRead` gives an object's bytes back beside its answer, for Rosie's own code (default 11): C-120's photo reading (`server-read-photo.json`), reports and evals reading the export. A person who sees a file gets a read link instead.

### Delete, for erasure

02-contracts K-13: "Delete, for erasure under RULES 4.10. How long ID files are kept follows Q-31's default (no deletion rule is invented)." So `deleteObject` takes one reason, `erasure`, with the person being erased and when their request was checked to be theirs (RULES 4.10: "A copy or delete is done in 45 days after a check it is the person"); any other reason is refused (`invalid/refuse-delete-without-erasure.json`). The erasure job (C-156) unseals each file's key from its row while the person's key still exists, deletes the object here, and only then deletes the person's key (K-35 v1 rule 8; `delete-erasure.json`); after it, `readLink` answers `notFound` (`read-link-not-found.json`). A sealed trace needs no delete: deleting the person's key erases it wherever it lies (arch 01 line 93; arch 10 line 516). Which files the trade's rules or the law keep is the job's to decide before it calls (open gaps).

### Spans

Each try of each call writes one K-08 v1 span on the `portCall` hop, provider `r2`, its `call` by this contract's name and its `attempt` (K-08 v1 README: `portCall` covers "an R2 upload link, read link, server-side write or delete (K-13, C-219)"); `filesSpan` closes what it got (`step`, `kind`, `owner`, `mediaType`, `sizeBytes`, `source`, `as`, `viewer`, `fileTable`, `fileRow`, `erasureOf`) and decided (`result`, `sizeBytes`, `repeated`, `alreadyGone`), so no object key, link, hash, file name or file ever enters a span, though K-08 alone would take a key as a label (`invalid/refuse-key-in-span.json`). An error leaves `decided` out; its name is the span's `error_code`, with outcome `refused` (`tooLarge`, `wrongType`, `notFound`, `conflict`), `failed` or `timedOut` (`unavailable`). A page call's span carries its request id as `job_id` and no turn; the erasure job's its job id (K-08 v1).

## The double (02-contracts K-13; C-219)

An in-memory store for tests, holding each object's bytes, type, size and owner by key; the exchange fixtures are its answers. How a test drives it:

- **The browser's PUT:** the double's test-only `put(url, bytes, contentType)` stores the bytes under the link's key, as the link would: refused after `expiresAt`, past `maxBytes`, or with another Content-Type. Its links are opaque `https://files.example/...` addresses.
- **What came:** `checkUpload` reads the double's store by the leading bytes, as default 8 says, and removes a refused file.
- **A read:** `readLink`'s address, fetched through the double's `get(url)`, gives the bytes with `Content-Disposition: attachment` and `X-Content-Type-Options: nosniff`, until its end; `serverRead` gives the bytes beside its answer.
- **An error:** the test sets the double, before the call, to fail its next call with `unavailable`; later calls answer as before. The setting is the double's test-only option, never a field of the port's request.
- **What it holds:** its test-only `objects()` lists the keys it holds, so an erasure test can see nothing is left.

## Defaults used (T-022)

1. **Q-31:** every object is private in R2, kept with no deletion rule invented, so v1 deletes only for erasure under RULES 4.10; who may view an ID file is the caller's check (open gaps).
2. **The port makes every object key,** `<kind>/<day>/<id>`, the id 26 lowercase letters and digits of at least 128 bits of secure randomness; `serverWrite` takes the writer's `writeId` by the same rule, and its `day`. No source gives a key's form (K-23 v1, K-31 v1 and K-35 v1 wait for it).
3. **A link's life:** an upload link 1 to 30 minutes, a read link 1 to 15, as the caller asks (K-21's fixtures: 15 and 10 minutes for uploads, 10 for listing photos); "short-lived" and "short" are the sources' only words.
4. **The upload limit is 10 MiB,** K-21 v1 default 12's example, made K-13's own; server writes have no limit in v1 beyond R2's own.

7. **An export is CSV** (`text/csv`): S11-61 "Exports the customer list" names no format.

9. **Every read is an attachment with nosniff** (K-35 v1 default 20 and its open gap), never inline.
10. **Repeats:** `serverWrite` is safe under its `writeId` and sha256 (the same bytes: `repeated`; other bytes: `conflict`, never overwritten); a second delete answers `alreadyGone`.
