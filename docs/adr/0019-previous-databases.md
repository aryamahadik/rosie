- Owner: architect. Decides: the CTO, with the security reviewer (what may be read, the STOP, rule 9), and the user for Jay (rule 8's J-04, and turning the flag on).

### 2. The bindings: staging only, never written

- **`wrangler.jsonc` `env.staging.d1_databases`**, two entries, each with exactly `binding`, `database_name` and `database_id`: `PREVIOUS_ROSFIELD_DB` for `rosfield-db`, and `PREVIOUS_DEMO_DB` for `rosfield-demo-db`. Each `database_id` is the one the account lists for that name; the release engineer's card takes both from the lead's inventory. An id is no secret (the file already holds the staging KV namespace's, line 96), but this record writes none.
- **Never at the top level or in `env.production`.** The top level is production's (line 5) and `env.production` is the CTO's (lines 111 to 162): a production binding needs the CTO, as production's Hyperdrive and keys do.
- **No `remote`, no `preview_database_id`, no migrations folder or table setting.** A local session and the Workers test pool then get local stand-ins [D1-local]. With `remote`, a local run would hold real people's rows (rule 9) and local code could change them for good.
- **The names carry the meaning** (ADR-014 section 3): with one `PREVIOUS_` prefix, one test pins that no file outside the port and the root's one line that hands the bindings to it names either.
- **Never in a branch preview.** `deploy-preview.sh` step 3 strips env.staging's `d1_databases` as it strips the Hyperdrive list, and stops a preview whose config still names one (lines 27 to 31). This lands in the same card as the bindings, so no preview ever gets them.
- **Nothing in this build writes, migrates or deletes them** (the user's "keep them"): no migration folder, no script, and no statement but the port's selects (section 4). `cf.sh` gains a guard: for either database, named by name or id, it refuses every `d1` command but `info`, `list` and `execute --remote --json --command` holding one select of `sqlite_master` (the lead's structure read); `export` included, since it writes every row to a file on the Mac (rule 9). It also refuses `dev --remote` when the config it reads binds either. `delete` stays refused as today.
- **The way back**, should anything ever write them, is Cloudflare's own: "Restore a database back to a specific point-in-time", within the last 30 days [W-d1]. The user's, from the dashboard; never a script's.

### 3. What may be read while the flag is on

**One rule for every read.** A read of the previous databases may make the new build more careful (a stop), or name a fact the new database lacks that grants nothing (a business's public listing facts). It never grants: no yes, role, sign-in, chat, link, booking, price, payment or permission comes from it (RULES 6.5, 6.10, 7.1), and it never links a person to an old record. Each read is by a key the new build already holds or was just given, returns at most 5 rows, and never lists a table.

**The stop read.** For a recipient's handle, a phone number or an email address, the previous databases say **stopped** when:

1. its `handle` row has a `stop_at` with no `start_at` after it (a tie, or a time the port cannot read, reads as stopped), or a `send_block` with any value but the column's empty one; or
2. its `person_index` row has an `opt_out` with any value but the column's empty one.

Any value the port cannot read reads as stopped (RULES 7.2: "Unsure: treat it as a stop"). The stop's time is `stop_at` when the stop comes from it and can be read; otherwise it is unknown. A number is matched by its digits, so a handle stored with or without its plus, spaces or punctuation still matches; an email address is matched lower-cased. The card proves each stored form with made-up rows. The demo database holds no column that records a stop (open point 2).

### 4. The port: closed while off, SELECT only

- **One reader.** Only the port reads `PREVIOUS_ROSFIELD_DB` and `PREVIOUS_DEMO_DB`; the root hands it the two bindings and the release-flag read, and nothing else in the Worker names either binding (section 2's pin).
- **Its own statements only.** The port holds a closed list of statement texts, constants in its code, one for each read of section 3. Each is one statement that begins with `select`, holds no `;`, none of `insert`, `update`, `delete`, `replace`, `upsert`, `create`, `drop`, `alter`, `attach`, `detach`, `pragma`, `vacuum`, `reindex`, `analyze`, `begin`, `commit`, `rollback`, `savepoint`, `release` or `returning`, ends in `limit 5` or less, and binds every value as a parameter (`?1`), never text built from input. Before `prepare`, the port refuses any text that is not exactly one of the list, and the list's own test checks every text by those rules and pins each statement's tables and columns to section 3. So any other text is refused before it reaches D1, and a later change to the list is a reviewed change to this record's section 3.
- **One way to run them.** `prepare(text).bind(...).all()` only, so every answer carries its `meta`; never `run`, `first`, `raw`, `batch`, `exec`, `dump` or `withSession`.
- **Every answer checked.** An answer whose `meta` shows `changes` above 0, `rows_written` above 0 or `changed_db` true shuts the port for the isolate's life and logs the label `previousWrote` (it should never happen: the check keeps it so). The flag is still read first, so turning it off answers `closed` again at once.
- **Its answers** (the K-38 contract, section 7): for the stop read, `closed`, `notStopped`, `stopped` with its time or null, or `unreadable`; for a business known before, `closed`, `none`, `found` with section 3's fields, or `unreadable`. `unreadable` covers a D1 error, a time limit passed (default 5 s, as the dispatcher's wait for the actor's reading: ADR-018's amendment, CQ-288), a row the port cannot read and a port shut by `previousWrote` while the flag is on. A D1 error's message is never kept or logged: only its class.
- **Where it is picked** (a table of its own, as `DOWN_PATH_PICKS`, since no D-017 hop runs it): `test`, the real port over the Workers test pool's local D1 stand-ins, which each test fills with made-up rows; `staging`, the real port, closed while the flag is off; `production`, closed.

### 5. Precedence

- **The new database wins whenever both answer.** A previous read fills only what the new database lacks: a business the new database knows is answered from it alone, and no previous fact outranks, changes or joins a new row.
- **A stop, either way.** Either database's stop stops the text, so the stricter of the two always wins (RULES 7.2, 4.8). For limit 8 the send state becomes: `stopped` when the new database or the stop read says stopped; `stopAt` the later of the two stop times when both are known, and null when the previous stop's time is unknown, so no yes lifts it (limit8.ts lines 144 to 145). A yes newer than both stops lifts it exactly as T-1099 lifts a stop today (RULES 7.5): the person's own START, or fresh yes for that booking, sent to the new build after an old STOP and recorded as K-05's `textsConsent` with `fromContact` (limit8.ts lines 139 to 153), turns texts back on. An email row's stop is its address's newest texts row, never the stopped flag (limit8.ts lines 105 to 116), so a previous stop of that address counts there as a withdrawal and the row is dropped the same way.
- **A safety line and a stop reply never wait for it.** Limit 8 sends both to a stopped phone (limit8.ts lines 13 to 14; RULES 4.12), so neither asks the port or the flag.
- **An unreadable stop read sends nothing and drops nothing for it.** The row waits for a later run, as when the send state cannot be read (limit8.ts lines 54 to 55); it goes, or drops as stopped, once the read answers. A confirmed previous stop drops the row as limit 8 drops any stopped phone's row.
- **Nothing is copied.** No row or value of either database is written into the new database by this record or any card under it, and the new build writes nothing because a previous database held it. A value a person confirms (an owner taking a business known before as theirs) is written as that person's answer, as any answer is. A copy would be its own migration and ruling (arch 01 line 33: it would move a fact's home).

### 6. Spans and logs

A previous read records labels and counts only, in the span of the hop that asked (the dispatch span for limit 8; the turn's or page call's span for a lookup), as K-08 v1's `spanFacts` already allows: no new hop and no K-08 version. The named values: `previousDatabases` (`on`, `off` or `unread`), `previousDatabase` (`rosfield-db` or `rosfield-demo-db`), `previousRead` (`stop` or `businessKnownBefore`), `previousOutcome` (`closed`, `notStopped`, `stopped`, `none`, `found` or `unreadable`), and the counts `previousRowsRead` (from `meta.rows_read`) and `previousRows`. Never a number, an address, a name, a row, a statement's text, a bound value, a database id or D1's error message; an error is its class label. The K-08 contract test's refusals of a raw number or words in a span hold for these too.

## Consequences

- **While the flag is off, which is the default, nothing changes.** No binding is read; previews and local runs never get the real databases; the build answers from the new database alone. On staging the flag reads off until the staging database and the flags' step are bound (flags.sh lines 19 to 20), whatever the set says.
- **The databases are kept.** This build never writes, migrates or deletes them, and after T-1378 `cf.sh` refuses every command that could, and every export.
- **With the flag on,** a number stopped before gets no text but a safety line and a stop reply (and, after T-1382, RULES 7.3's one reply to a later question) until the person's own yes; a business known before can be named, never booked.
- **A stop's time from before is used, never kept.** It reaches limit 8's decision and no table; spans carry labels and counts only.
- **Costs.** One flag read per run of a caller; with the flag on, one D1 read per row a stop binds and per lookup that misses, whose time no one has measured (T-1381 and T-1384 time them in their spans). A D1 outage with the flag on holds every routine row to every recipient until D1 answers: the stricter failure, and turning the flag off ends it.
- **Rule 8** stays whole while the flag is off; turning it on is the user's allowance for exactly section 3's reads.

## Alternatives not chosen

- **Copy the previous rows into the new database** (one migration): the card forbids it here, it would bring real people's rows into the new build's home and give a fact two homes (arch 01 line 33), and it needs its own ruling under rule 8.
- **A read-only binding:** D1 has none [D1-api].
- **Read through Cloudflare's API with a token:** a key the Worker would hold (rule 7; a secret write is the user's, DL-497), an outside call per read, and whether a read-only token refuses a writing statement was not checked.
- **The flag as a Wrangler var, or per phone or business:** a deploy per change (ADR-010's alternatives); and with a phone's row one number's past would count and another's not.
- **Honour a previous STOP even while the flag is off:** against the user's ask, which is the flag's whole point (DL-745). Open point 1 carries the risk to the CTO.
- **Read everything and filter in code:** every row would pass through the Worker; the port's statements name only section 3's columns.
- **Read the staff and the waitlist now:** each needs a ruling first (open points 4 and 5).
