### 2. The bindings: staging only, never written

- **`wrangler.jsonc` `env.staging.d1_databases`**, two entries, each with exactly `binding`, `database_name` and `database_id`: `PREVIOUS_ROSFIELD_DB` for `rosfield-db`, and `PREVIOUS_DEMO_DB` for `rosfield-demo-db`. Each `database_id` is the one the account lists for that name; the release engineer's card takes both from the lead's inventory. An id is no secret (the file already holds the staging KV namespace's, line 96), but this record writes none.
- **Never at the top level or in `env.production`.** The top level is production's (line 5) and `env.production` is the CTO's (lines 111 to 162): a production binding needs the CTO, as production's Hyperdrive and keys do.
- **No `remote`, no `preview_database_id`, no migrations folder or table setting.** A local session and the Workers test pool then get local stand-ins [D1-local]. With `remote`, a local run would hold real people's rows (rule 9) and local code could change them for good.
- **The names carry the meaning** (ADR-014 section 3): with one `PREVIOUS_` prefix, one test pins that no file outside the port and the root's one line that hands the bindings to it names either.
- **Never in a branch preview.** `deploy-preview.sh` step 3 strips env.staging's `d1_databases` as it strips the Hyperdrive list, and stops a preview whose config still names one (lines 27 to 31). This lands in the same card as the bindings, so no preview ever gets them.
- **Nothing in this build writes, migrates or deletes them** (the user's "keep them"): no migration folder, no script, and no statement but the port's selects (section 4). `cf.sh` gains a guard: for either database, named by name or id, it refuses every `d1` command but `info`, `list` and `execute --remote --json --command` holding one select of `sqlite_master` (the lead's structure read); `export` included, since it writes every row to a file on the Mac (rule 9). It also refuses `dev --remote` when the config it reads binds either. `delete` stays refused as today.
- **The way back**, should anything ever write them, is Cloudflare's own: "Restore a database back to a specific point-in-time", within the last 30 days [W-d1]. The user's, from the dashboard; never a script's.

### 3. What may be read while the flag is on

**One rule for every read.** A read of the previous databases may make the new build more careful (a stop), or name a fact the new database lacks that grants nothing (a business's public listing facts). It never grants: no yes, role, sign-in, chat, link, booking, price, payment or permission comes from it (RULES 6.5, 6.10, 7.1), and it never links a person to an old record. Each read is by a key the new build already holds or was just given, returns at most 5 rows, and never lists a table.

**The stop read.** For a recipient's handle, a phone number or an email address, the previous databases say **stopped** when:

1. its `handle` row has a `stop_at` with no `start_at` after it (a tie, or a time the port cannot read, reads as stopped), or a `send_block` with any value but the column's empty one; or
2. its `person_index` row has an `opt_out` with any value but the column's empty one.

Any value the port cannot read reads as stopped (RULES 7.2: "Unsure: treat it as a stop"). The stop's time is `stop_at` when the stop comes from it and can be read; otherwise it is unknown. The demo database holds no column that records a stop (open point 2).

**How a handle is matched.** A number is matched by its digits. The statement takes out of the stored `handle` each character a written number adds (the plus, spaces, dashes, dots and brackets) with SQLite's `replace()` function, one call per character, and compares what is left with the recipient's digits bound as values: `?1` its E.164 digits, and `?2`, for a number with country code 1, its ten national digits (else `?1` again). So a number stored with or without its plus or its country code, or with any of those characters, still matches. An email address is matched lower-cased on both sides (`lower()`). No index serves such an expression, so the read goes through each table's rows: the span counts them (`previousRowsRead`, section 6) and T-1382 times it. T-1380 proves each stored form with made-up rows.

### 4. The port: closed while off, SELECT only

- **One reader.** Only the port reads `PREVIOUS_ROSFIELD_DB` and `PREVIOUS_DEMO_DB`; the root hands it the two bindings and the release-flag read, and nothing else in the Worker names either binding (section 2's pin).
- **The flag first.** Every call takes the flag's reading as section 1 rules (read once per run of its caller) before it touches a binding: `closed` for an explicit off, no row or no flags bound; `unreadable` for a read that throws or answers anything else, with no D1 call; open only on exactly `enabled: true`. Open, a binding the Worker does not have (a preview, or staging before T-1378's deploy) answers `unreadable`, never `closed`.
- **Its own statements only.** The port holds a closed list of statement texts, constants in its code, one for each read of section 3. Each is one statement that begins with `select`, holds no `;`, none of `insert`, `update`, `delete`, `replace into`, `upsert`, `create`, `drop`, `alter`, `attach`, `detach`, `pragma`, `vacuum`, `reindex`, `analyze`, `begin`, `commit`, `rollback`, `savepoint`, `release` or `returning` (`insert or replace` is caught by `insert`), ends in `limit 5` or less, and binds every value as a parameter (`?1`), never text built from input. The word `replace` alone is not banned: SQLite's `replace()` function is how the stop read matches a number's digits (section 3), and a text that begins with `select` and holds no `;` cannot be a `REPLACE` statement. Before `prepare`, the port refuses any text that is not exactly one of the list, and the list's own test checks every text by those rules and pins each statement's tables and columns to section 3. So any other text is refused before it reaches D1, and a later change to the list is a reviewed change to this record's section 3.
- **One way to run them.** `prepare(text).bind(...).all()` only, so every answer carries its `meta`; never `run`, `first`, `raw`, `batch`, `exec`, `dump` or `withSession`.
- **Every answer checked.** An answer whose `meta` shows `changes` above 0, `rows_written` above 0 or `changed_db` true shuts the port for the isolate's life and logs the label `previousWrote` (it should never happen: the check keeps it so). The flag is still read first, so turning it off answers `closed` again at once.
- **Its answers** (the K-38 contract, section 7): for the stop read, `closed`, `notStopped`, `stopped` with its time or null, or `unreadable`; for a business known before, `closed`, `none`, `found` with section 3's fields, or `unreadable`. `unreadable` covers a flag read that fails (section 1), a binding the Worker does not have while the flag is on, a D1 error, a time limit passed (default 5 s, as the dispatcher's wait for the actor's reading: ADR-018's amendment, CQ-288), a row the port cannot read and a port shut by `previousWrote` while the flag is on. A D1 error's message is never kept or logged: only its class.
- **Where it is picked** (a table of its own, as `DOWN_PATH_PICKS`, since no D-017 hop runs it): `test`, the real port over the Workers test pool's local D1 stand-ins, which each test fills with made-up rows; `staging`, the real port, closed while the flag is off; `production`, closed by its pick whatever the flag says (section 2: no binding there without the CTO).

### 5. Precedence

- **The new database wins whenever both answer.** A previous read fills only what the new database lacks: a business the new database knows is answered from it alone, and no previous fact outranks, changes or joins a new row.
- **The stop read binds only what a stop binds, and only ever holds or drops.** A safety line and a stop reply never ask the port or the flag and never wait for them: limit 8 decides both from the new database's send state alone, exactly as today (limit8.ts lines 13 to 14; RULES 4.12). Every other row (a routine row, below) is decided by the new database first, as today, and the stop read can then only hold it or drop it: it never sends a row, sets the opt-out override or counts a chat as open where the new database alone would not.
- **A stop, either way.** Either database's stop stops a routine row, so the stricter of the two always wins (RULES 7.2, 4.8). Limit 8 takes the stop read's answer beside the send state (one optional field, T-1382; left out, today's decision) and weighs it where today's decision sends a routine row; every other decision of today's stands (a row dropped, withdrawn, held for its hours, waiting for a chat or stale), and the row is weighed again when a later run would send it:
  - **A phone row:** stopped when the new database or the stop read says stopped; the row is dropped as any stopped phone's row is (`droppedStopped`), unless the person's own yes newer than `stopAt` lifts it, exactly as T-1099 lifts a stop today (RULES 7.5; `yesAfterStop`, limit8.ts lines 139 to 153): the person's own START, or a fresh yes for that booking, sent to the new build after the old STOP and recorded as K-05's `textsConsent` with `fromContact`.
  - **`stopAt`** (N1) is the later of the two stop times when every stop that stands has a known time, and null when any stop that stands has none (the new database's stopped phone with no `stop_at`, types.ts lines 397 to 401, or a previous stop whose time is unknown), so no yes lifts it (limit8.ts lines 144 to 145).
  - **An email row:** the new database's withdrawal decides first, as today (a withdrawal there drops every class, ADR-016's open point 7; this record changes nothing there). A previous stop of the address then binds as a phone's stop does, never as a withdrawing texts row (N3): the routine row is dropped, and a safety line or a stop reply never is, since neither asks. - **The flag as a Wrangler var, or per phone or business:** a deploy per change (ADR-010's alternatives); and with a phone's row one number's past would count and another's not.
