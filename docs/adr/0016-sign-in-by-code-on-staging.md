### 2. Sending that row (B2)

- **After `sendSignInCode` commits, the same request runs one dispatch for the row's recipient handle**: the root's own dispatcher run (`runDispatch` with `recipientHandleId`, as a turn's wake makes it: root.ts lines 489 to 511), with the same claim under the recipient's lock (dispatcher.ts lines 11 to 20), the same limit 8 and the same retry queue. It runs in the request's `waitUntil`, after the answer has gone (section 4: the answer waits on no write the two paths do not share).
- A send that fails is retried by the retry queue as any row's is (dispatcher.ts lines 26 to 31; root.ts lines 487, 517 to 530), and every try passes limit 8 first (dispatcher.ts line 377), so the row's `not_after` binds each retry (section 3).
- **A request whose isolate ends before the dispatch** leaves the row `checked` and unclaimed until its recipient's next wake (the person's next code). That wake claims it first, in commit order, and limit 8 withdraws it unsent, since its `not_after` has passed (section 3); the new code's row goes after it. Default: accepted (open point 6).
- Not the minute sweep (it runs clock rows only, index.ts line 28, and would add up to a minute); not a queue job, whose message would carry the code.

### 3. Its send class and limit 8 (B3)

- **Send class `quick_reply`**, one of K-04's four (0010 line 53): RULES 4.3 sends "a quick reply" at any time (line 187), and the code answers the person's own request in the same call and dies in 10 minutes (RULES 6.2; 0020 line 364). It skips text hours (limit8.ts line 172), so a row with no business never reads a zone (lines 179 to 189).
- **Limit 8's chat rule is a text rule.** Rosie never writes first in iMessage (RULES 4.1b, line 162; MC C9), and K-07 parks `waiting_chat` for "a customer mobile" (README line 31). An email row skips lines 157 to 159 and goes on to the checks after them; a row on a text channel keeps the rule unchanged. T-264 needs this for every email row: K-12's `confirmation` exists for "a mobile whose chat is not open" (K-12 README line 50).
- `versions_read` is empty, so limit 8 never makes the row stale or withdrawn by a version (limit8.ts lines 164 to 169).
- **The 10-minute window** (round 2, point 5). Limit 8 checks the row's `not_after`, from the claimed row's `notAfter`, right after the SMS refusal (line 138) and before anything else: at or after it, the row is marked `withdrawn` (K-05 item 4's move, README line 95; limit 8's own outcome, line 168) and nothing is sent. Every try runs limit 8 first (dispatcher.ts line 377), so no retry sends a dead code, and a row whose dispatch never ran is withdrawn at its next wake (section 2).
- **The stop for an email address** (round 2, point 4). For an email handle `sendStateOf` takes `stopped` from the phone row, which an email handle has not, so it is always false (`runtime/src/wiring/real.ts` line 2253). An email contact's stop is its newest texts consent row: "which for an email contact is the stop record, since only a phone carries the flag" (K-05 item 28, README line 195; `db/repo/send-state.ts` line 12). That row already reaches limit 8 unchanged with its `revoked` flag (real.ts line 2255; `dispatch/types.ts` lines 342 to 347). So limit 8 reads the stop of a row on the email port as `textsConsent.revoked`, and such a row is `droppedStopped`; a text row keeps lines 142 to 154 unchanged. It is card E1's, inside `runtime/src/dispatch/limit8`; `stopped` keeps its phone-only meaning (real.ts lines 2242 to 2243; STATE note 10). A code to a stopped address is dropped (open point 7).
- **The chat step** (round 2, point 6). The dispatcher asks `recipients.chatFor` and ends `noChat` when there is none (dispatcher.ts lines 392 to 393), and an email handle has none (real.ts lines 2276 to 2282). A row whose claimed `port` is `email` (`dispatch/types.ts` line 78) skips that step and asks a new `RecipientDirectory.emailFor(recipientHandleId)` (beside `chatFor`, lines 330 to 333): the recipient's address from the same `sendState` read, whose recipient carries its kind and address (K-05 item 28), as `chatTargetOf` takes the chat from it. None (not an email handle) ends the run with nothing sent. E2 builds the step in `runtime/src/dispatch`; F builds `emailFor` in `runtime/src/wiring/real.ts`.
- **How a code row ends** (round 2, point 1). It ends `sent` or `delivered` as any row, or `droppedStopped`, or `withdrawn` at its `not_after`. **It is never given up and never `failed`, and it has no follow-up**:
  - K-07 retry rule 5 gives up after "15 minutes of tries" counted from the first try (K-07 README line 100; K-05 item 17's `tooSoon`, README line 136). A code row's first try comes after its code was made, so its `not_after`, 10 minutes after the code, always comes first, and limit 8 withdraws it at the next try.
  - Rule 5's follow-ups are a business's: "the next way the person allows; none left, the owner gets the number to call" (arch 02 line 125; S12-09, S12-10). A sign-in has no business and no owner, and a code sent another way after its 10 minutes is dead. The person asks again: the page answers `expired` and offers a new code (K-21 README line 116).
  - So no entry is written under a turn id for it: the withdrawal takes none (`markRow`, as for every row). V3 makes `dispatcherGivesUp` (item 17), `writeAllSet` (item 25) and `markPart`'s follow-ups (item 15) refuse a row with no turn with a new error, `noTurn`, writing nothing: a new error shape, which v1.1 counts as a minor change (K-05 README line 107). Neither of the first two is built yet (`db/repo/outbox.ts` lines 1 to 19; the dispatcher's `OutboxStore`, `dispatch/types.ts` lines 248 to 269), so the refusal goes with the card that builds each.
- So the code goes within seconds of the answer (arch 04 line 227: "Send ≤ 1 s" for the dispatcher's part), far inside its 10 minutes. Resend's own delivery time is not measured (section "Not measured").

**The lead note T-264 needs** (runtime/src/dispatch is its folder: P line 4032):

> **Lead note for T-264 (ADR-016 section 3).** An email row is not a text: limit 8's chat rule (limit8.ts lines 157 to 159) applies to rows on a text channel only, and an email row goes on to the checks after it. Its stop is its contact's newest texts consent row with `revoked` true (K-05 item 28), not the phone's `stopped`. A row with a `notAfter` at or before now is withdrawn and never sent, at every try. A row on the email port skips the chat step and goes to `emailFor`'s address. A row's K-12 purpose comes from its `email_purpose` (K-04 v1.1; the claim's `emailPurpose`, K-05's sign-in version). ### 4. The pause and the day's cap, on the server (B4; STATE note 74)

**The store: K-22 v1.2 adds `sign_in_attempts`** in PostgreSQL beside `proof_codes` and `sessions`, the system of record (arch 10 line 504), so the try, the code's check and the session insert commit together (K-22 README line 114's path, "all in one transaction"). It is K-22 README line 210's "how the code id, and the person the code was made for, are kept on the server", and the map's R3.

| Column                                         | What                                                                                                                                                                       |
| ---------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

| `attempt_id`, unique                           | the page's `attemptId` (K-21 schema line 751), at least 128 bits from a cryptographically secure generator (K-21 default 18, README line 212); kept as made (open point 3) |
| `request_sha256`, unique                       | sha256 of the device's sha256 and the page's `requestId`: the start's repeat key (K-21 README line 75)                                                                     |

- Indexes on `(contact_hash, started_at)` and on `started_at` (rule 0). Row-level security on; `rosie_job` selects, inserts and updates; `rosie_app` holds no grant and reaches a row only through three security-definer calls keyed by what the caller holds, as K-22 rule 5's four are (README lines 94 to 101; owned by the migrations' role, `search_path` pinned as 0020 lines 857 to 882, `EXECUTE` to the two roles only): `sign_in_attempt(attempt_id, device_sha256, at)` answers the binding or no row (any other device: no row); `sign_in_attempt_tried(id, check_sha256, outcome, at)` records a check, a wrong one raising `wrong_tries` and the fifth setting the pause, as `check_proof_code` does (0020 lines 756 to 768), and answers the attempt's tries and pause after it; `sign_in_attempt_signed_in(id, session_id)`. None returns a hash.
- **`last_check_sha256`** is sha256 over the attempt's `id`, the device's sha256 and the check's `requestId`, joined by a fixed separator; never over a typed code, since a 6-digit code's plain sha256 falls to a million tries (K-22 default 7). **`last_outcome`** has a CHECK to K-21's `signInCheck` outcome labels (`signedIn`, `secondProofNeeded`, `wrong`, `paused`, `expired`, `alreadySignedIn`, `attemptNotFound`, `waitingForText`: K-21 README line 116), so no token can be kept there (the security reviewer's note b).
- **The key:** `contact_hash` is HMAC-SHA-256, under the Workers secret `PROOF_CODE_HASH_KEY`, of a fixed prefix, the typed kind and the contact as normalized (an email in lower case; a mobile in E.164), never the contact itself; the code's hash is the same HMAC with its own fixed, distinct prefix (K-22 README line 55). The name is the one K-22's fixtures use (`contracts/db-schema/people-access/fixtures/seed-proof-code.json` line 14); the release engineer may rename it (K-22 README line 131). One key with two prefixes: open point 4. The action layer reads no key itself (`actions/src/page-calls/staging/test-phone/types.ts` lines 4 to 5): the root hands it a hashing port.
- **The key's rollback conditions** (the security reviewer's note c): the key is staging's own random value, made in place, so DL-495's conditions for `SEALING_WRAP_KEY` hold for it (`ops/DECISIONS.md` line 506): after its live make, the lead records the first staging version that holds it in `ops/releases`, never rolls staging back past it, and checks `secret list` before any re-run. A lost or remade key voids every live code and restarts every contact's day count and pause, since their hashes change. Whether to keep a copy or rotate it joins CQ-218.

**`startSignIn`'s rules**, in one transaction under a transaction-level advisory lock keyed on the contact hash (as the claim locks a recipient: K-05 README line 94), so two starts never both pass the cap:

0. **Staging's bound on rows** (round 2, point 10; open point 13): when `SIGN_IN_STARTS_PER_HOUR` (default 100) attempts of any contacts were started in the hour before now, answer `paused` until the oldest of them is an hour old, and write nothing. It reads no account and answers alike for every contact. It is read before the contact's lock, so a burst can pass it by at most the number of starts running at once. It bounds the attempt rows a script can write by varying the typed contact to about 2,400 a day, while no delete job exists (open point 10).
1. A row with the request's key: answer it again (`repeated`: its attempt id and expiry), write nothing. So a repeated `requestId` sends no second code (K-21 schema line 688).
2. The contact's latest `paused_until` after now: answer `paused` until then, write nothing.
3. **The day's cap:** with `SIGN_IN_STARTS_PER_DAY` (default 5) attempts of that contact whose `started_at` is after now minus 24 hours, answer `paused` until the earliest `started_at` among those attempts plus 24 hours, and write nothing (S13-45: "At most a few codes a day per contact"; open point 1). A start past the cap writes nothing, so the window never holds more than the cap, and at that time the earliest one leaves the window (`started_at > now - interval '24 hours'`, by the database's clock). V2 states this exactly (the database engineer's note).
4. The account, in one statement: by `accounts.email` with `email_proven_at` set, or by `accounts.mobile`, with whether its person holds a live owner or admin role (K-04 `person_roles`). Way email needs the account's proven email (K-21 schema line 688: "never to an email not yet proven"). `accounts.email` is not unique (0020 lines 98 to 107: only the mobile has a unique key, line 104), so **exactly one** matching account names a person; none, or two or more, name none, and the start goes on as for no account (open point 14).
5. Insert the attempt, with the person and the role flag when found, else null and false, and answer `started`. For the server only it names the person and the email handle to send to; neither reaches the page.

Rules 0 to 3 never read an account, and rules 4 and 5 run the same statements whether or not one matches, so a pause and a cap answer alike for any typed contact (K-21 schema line 780). **The answer waits on no write the two paths do not share:** the code, its row and its entries come after it. **After the answer**, with an account, `sendSignInCode` first reads `proof_code_limits` for that email handle and `sign_in` since 24 hours ago (0020 lines 777 to 797): when the codes to that address, every purpose, have reached the cap, or a sign-in code of it is paused, nothing is written or sent. The answer already said `started`, as for any way with no contact on file (K-21 README line 114).

**The check** (`proveSignIn`, one transaction): the binding by `sign_in_attempt` (none: `attemptNotFound`); a repeat of this check answers its first result, a `signedIn` one as `alreadySignedIn` with no token (K-21 README line 115); a signed-in attempt: `alreadySignedIn`; `paused_until` after now: `paused`; past `expires_at`: `expired`; then `check_proof_code(code id, typed hash, at)`.

- **Every answer to a code that is not right comes from the attempt** (round 2, point 7; the security reviewer's item 1), on both paths. `check_proof_code` only tells `right` from not right (and `used`, for `alreadySignedIn`). Its `wrong`, and its `paused` at the fifth wrong code (0020 lines 756 to 763), are both recorded by `sign_in_attempt_tried` as a wrong try. With no code the attempt calls it with a null id, which answers `unknown` before any write (0020 lines 723, 737 to 739), and that is recorded the same way. The answer is then read from the attempt after the try: `wrong` with its tries left, or at the fifth `paused` until its `paused_until`. Both pauses are the same `at` plus 15 minutes, so the answer equals `sign-in-wrong-five.json`'s (`paused` until 15:22:10Z, lines 20 to 23) with or without an account. The attempt's own pause and expiry are read before `check_proof_code`, and the attempt expires no later than its code (section 4's table), so the code's `paused` and `expired` answers (0020 lines 744 to 750) are never reached first.
- A wrong code records its try and commits at once, so it counts whatever fails after (K-22 README line 212). `right`: section 6's steps. So **a sixth check after five wrong ones answers `paused` from the server, with or without the page's cookie** (STATE note 74; T-520's security note a, T-520.md line 75), and a new start for that contact answers `paused` (rule 2) and sends nothing, for a contact with an account and one without.

**The numbers** are code's, named in the page call: 5 tries, a 15-minute pause, a 10-minute code (RULES 6.2; 0020 lines 364 to 371), `SIGN_IN_STARTS_PER_DAY` = 5 in a rolling 24 hours (open point 1) and `SIGN_IN_STARTS_PER_HOUR` = 100 (open point 13). The pause stays per attempt, as K-22 default 8 keeps it per code; the day's cap bounds the guesses (at most 25 a day for a contact, against a million 6-digit codes, if each code is drawn evenly: card A).

## Alternatives not chosen

- **A turn row for the call** (K-05 open gap 3's other option): a page call is not "a batch of a handle's texts" (arch 01 line 59), turn ids hash texts' event ids (K-08 default 9), and a call that writes no row has no handle to own it.
- **Sending the code outside the outbox** (K-12 line 25 names such a send): K-22 rule 5 sends a code "in the one commit with its outbox row" (README line 89), K-09 and K-12's fixtures make it a row (`out-sam-signin-code`; `send-code.json`'s key), and it would lose the retries, limit 8's stop and the trace.
- **A K-04 v2 (breaking) at once:** section 1's guard keeps every reader as deployed safe; the CTO decides the number (open point 12).
- **A code row's follow-ups as K-07 rule 5 gives a business's row:** a dead code sent another way, or a number to call with no owner (section 3).
- **The 10 minutes read from the proof code at send:** the outbox row has no key to its code, and limit 8 reads only the claimed row and the send state; `not_after` is one nullable column.
- **Mapping the email stop into `stopped`:** `stopped` is the phone's flag alone (real.ts lines 2242 to 2243; STATE note 10).
- **The attempt in a Durable Object or KV:** the system of record is PostgreSQL (arch 10 line 504), the try must commit with the code's check and the session, and KV takes about 60 s to agree (arch 10 line 518).
- **One role for the whole sign-in:** as `rosie_job` the session insert loses K-22 rule 5's lock; as `rosie_app` there is no grant on `accounts` (0020 lines 46 to 47), and its grants on `outbox_rows` and `event_log` admit only its own business's rows (`0012_core_rls.sql` lines 89 to 96, 105), while a sign-in's rows have no business.
- **The pause by handle alone** (`proof_code_limits`): an address with no account has no handle, so the answers would differ (K-21 schema line 780).
- **Testers as K-36 team rows:** build prompt 9.4 (line 490).
- **The double's record as the testers' way in:** circular (K-21 README line 96).
- **A hashed attempt id:** a repeat must answer the same attempt (K-21 README line 75), which a stored hash cannot give back.
- **A per-device limit on starts:** a script makes a new device cookie at will, so it bounds nothing; the hour's bound counts every start (rule 0).
