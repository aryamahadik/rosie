## Decision

### 1. The code's email row with no turn (B1)

**An outbox row written by work with no turn carries a job id in place of a turn id, as the event log (0011 line 53) and K-07's effect rows (K-07 README line 117) already do. Sign-in's code and its row are written by one narrow K-05 call, `sendSignInCode`, not by CQ-44's general commit.**

**K-04 v1.1 (core), the outbox tables only:**

| Change                                                                                                                  | Why                                                                                                                          |
| ----------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| `job_id text` null: the work with no turn that wrote the row (here a sign-in; later a clock firing with no turn, CQ-28) | K-08 README line 244; K-05 open gap 3 (line 794)                                                                             |
| `turn_id` becomes nullable                                                                                              | a call made alone has no turn, and a made-up turn would break arch 01 line 59 and K-08 default 9                             |
| CHECK `outbox_rows_turn_or_job`: `turn_id is not null or job_id is not null`                                            | the event log's own rule (0011 line 53)                                                                                      |
| `email_purpose text` null, CHECK: null, or one of K-12 v1's six purposes on an `email` row only                         | the email path must know a code row (sections 3 and 5); K-12 README line 34 lists the purposes; K-04 v1 has no column for it |
| Index `outbox_rows_job_idx (job_id) where job_id is not null`, built concurrently in a file of its own                  | a repeat finds its rows by job id; the migration skill's rule for an index on an existing table                              |
| CHECK on `outbox_parts`: a `delivered` part holds `delivered_at`                                                        | CQ-211's default puts it in K-04's next minor version (QUESTIONS line 489), which this is                                    |

- **A minor version.** The migration only expands (build prompt 5.4): a nullable column, a NOT NULL dropped (the guard treats `SET NOT NULL` as contracting and lets `DROP NOT NULL` pass: `infra/ci/migration-guard.mjs` lines 165, 177), CHECKs added `NOT VALID` and then validated (CQ-211's form, QUESTIONS line 489). Every v1 writer still fills `turn_id`. The v1 readers found here select rows by turn id (K-05 items 1 and 2, README lines 88 and 89), and the claim answers no turn id at all (`runtime/src/dispatch/types.ts` lines 64 to 87), so none meets a job row. That answers K-05 open gap 3: the change is an expansion, the shape two tables already have. The table-list format lists whole tables (`contracts/db-schema/tables.meta.schema.json`), so `core.v1.1.tables.json` restates each table it changes as it is after the change (K-04 README line 11).
- **The condition.** The version card lists every reader of `outbox_rows.turn_id` (db/repo, actions, runtime, tests). One that reads a row's turn id without having selected the row by it makes the change breaking for that reader; the card then stops with a NEED for the CTO's OK (build prompt 6.4, line 372).

**K-05, the send side: two calls** (their roles are section 6's).

- **`startSignIn`**, one transaction, before the page answers: section 4's rules; it writes the attempt row, never a code.
- **`sendSignInCode`**, one transaction, after the answer: the `proof_codes` row (`sign_in`, the account's person, its email handle, channel `email`, the code's keyed hash and `hash_key_name`: 0020 lines 333 to 375); the email row (job id: the attempt's server-made id; recipient: that handle and person; no business, no booking; channel and port `email`; send class `quick_reply`; `email_purpose` `code`; `versions_read` empty; the bundle active at the call, as K-08 default 1 names it for a hop outside a turn, README line 212; the page call's trace id; **its plan and final parts, state `checked`**); its `proof_code.sent` entry with the job id, no business and no bundle, the final parts left out (K-08 README lines 163, 244; tool-api schema line 4065); and the attempt's code id. A repeat for the same attempt writes nothing and answers the first send.
- **Why the plan and final parts go in the same transaction:** the code lives only in memory until its words are written (tool-api schema line 4065; K-21 README line 124 rules the same for a link's code), and a row with no final parts stops every later row to its recipient (K-05 README line 90). So the row makes K-07's two moves, (new) to `planned` and `planned` to `checked` (K-07 README lines 40 to 41), in one transaction; K-07 needs no version, since its test compares state pairs (CQ-187, QUESTIONS line 465). The plan is code-built, as a fixed-line row's is (CQ-177 item 128, QUESTIONS line 455): no compose input, no composer. The K-05 version card names its K-03 v1 shape and fixture, or reports a NEED for a K-03 minor version.
- **The words** are code's: K-12's `send-code.json` form (`contracts/port-email/fixtures/send-code.json`: the automated-assistant line, then "Code NNNNNN: type it on the sign-in page. It works for 10 minutes."), naming no business or booking (tool-api schema line 4065), from "Rosie" (K-12 default 3, line 174), subject "Your Rosie code". They are stand-ins for Jay's words (open point 5). A sign-in code has 6 digits, as S11-52's example (K-22 README line 131).
- **CQ-44's general commit with no turn** (a page's other writes, the console's) stays open; whatever call carries it writes outbox rows in v1.1's shape.

### 2. Sending that row (B2)

- **After `sendSignInCode` commits, the same request runs one dispatch for the row's recipient handle**: the root's own dispatcher run (`runDispatch` with `recipientHandleId`, as a turn's wake makes it: root.ts lines 489 to 511), with the same claim under the recipient's lock (dispatcher.ts lines 11 to 20), the same limit 8 and the same retry queue. It runs in the request's `waitUntil`, after the answer has gone (section 4: the answer waits on no write the two paths do not share).
- A send that fails is retried by the retry queue as any row's is (dispatcher.ts lines 26 to 31; root.ts lines 487, 517 to 530).
- **A request whose isolate ends before the dispatch** leaves the row `checked` and unclaimed until its recipient's next wake (the person's next code). It then goes after its code has lapsed and proves nothing (`check_proof_code` answers `expired`: 0020 lines 747 to 750). Default: accepted (open point 6).
- Not the minute sweep (it runs clock rows only, index.ts line 28, and would add up to a minute); not a queue job, whose message would carry the code.

### 3. Its send class and limit 8 (B3)

- **Send class `quick_reply`**, one of K-04's four (0010 line 53): RULES 4.3 sends "a quick reply" at any time (line 187), and the code answers the person's own request in the same call and dies in 10 minutes (RULES 6.2; 0020 line 364). It skips text hours (limit8.ts line 172), so a row with no business never reads a zone (lines 179 to 189).
- **Limit 8's chat rule is a text rule.** Rosie never writes first in iMessage (RULES 4.1b, line 162; MC C9), and K-07 parks `waiting_chat` for "a customer mobile" (README line 31). An email row skips lines 157 to 159 and goes on to the checks after them; a row on a text channel keeps the rule unchanged. T-264 needs this for every email row: K-12's `confirmation` exists for "a mobile whose chat is not open" (K-12 README line 50).
- `versions_read` is empty, so limit 8 never makes the row stale or withdrawn (limit8.ts lines 164 to 169). The stop rule stands (lines 142 to 154): a code to a stopped email handle is dropped (open point 7).
- **A code row that fails gets no follow-up**: no next way and no owner's number (K-07 rule 5, README line 100). The person asks again.
- So the code goes within seconds of the answer (arch 04 line 227: "Send ≤ 1 s" for the dispatcher's part), far inside its 10 minutes. Resend's own delivery time is not measured (section "Not measured").

**The lead note T-264 needs** (runtime/src/dispatch is its folder: P line 4032):

> **Lead note for T-264 (ADR-016 section 3).** An email row is not a text: limit 8's chat rule (limit8.ts lines 157 to 159) applies to rows on a text channel only, and an email row goes on to the checks after it. A row's K-12 purpose comes from its `email_purpose` (K-04 v1.1; the claim's `emailPurpose`, K-05's sign-in version). A row of purpose `code` goes at any hour (class `quick_reply`) to a handle that never texted, with no booking, no reply address, no manage link and no thread (`send-code.json`), its words as its final parts hold them, no line added; when it fails for good it gets no follow-up. **Proves it with, added:** `npm run test:workers -- runtime/src/dispatch runtime/src/email`: a row built from `send-code.json`'s request, to an email handle with no phone row and no open chat, at 3:00am, gives exactly one email-port send equal to that request and none by any other port; the same row to a stopped address is dropped (`droppedStopped`); a text-channel row to a phone with no open chat still waits (`waitingChat`) whatever its class; a code row that fails for good writes no follow-up row.

### 4. The pause and the day's cap, on the server (B4; STATE note 74)

**The store: K-22 v1.2 adds `sign_in_attempts`** in PostgreSQL beside `proof_codes` and `sessions`, the system of record (arch 10 line 504), so the try, the code's check and the session insert commit together (K-22 README line 114's path, "all in one transaction"). It is K-22 README line 210's "how the code id, and the person the code was made for, are kept on the server", and the map's R3.

| Column                                         | What                                                                                                                                                                       |
| ---------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `id`                                           | server-made (CQ-09); also the job id of the code's row and entries                                                                                                         |
| `attempt_id`, unique                           | the page's `attemptId` (K-21 schema line 751), at least 128 bits from a cryptographically secure generator (K-21 default 18, README line 212); kept as made (open point 3) |
| `request_sha256`, unique                       | sha256 of the device's sha256 and the page's `requestId`: the start's repeat key (K-21 README line 75)                                                                     |
| `device_sha256`                                | sha256 of the device cookie (K-21 schema line 726; README line 117)                                                                                                        |
| `contact_hash`, `hash_key_name`                | the typed contact's keyed hash (below) and the secret's name                                                                                                               |
| `way`                                          | `email` in this lane (the column admits `text`)                                                                                                                            |
| `person_id`, `owner_or_admin`                  | the account's person, null with none; whether that person held a live owner or admin role at the start (K-21 README line 110)                                              |
| `proof_code_id`, unique                        | set by `sendSignInCode`; null with no account                                                                                                                              |
| `started_at`, `expires_at`                     | `expires_at` = `started_at` + 10 minutes (CHECK, as 0020 line 364)                                                                                                         |
| `wrong_tries`, `last_wrong_at`, `paused_until` | 0 to 5; the fifth sets the pause 15 minutes on (CHECKs as 0020 lines 365 to 371)                                                                                           |
| `last_check_sha256`, `last_outcome`            | a check's repeat answers its first result (K-21 README line 76)                                                                                                            |
| `session_id`, unique                           | the session it started                                                                                                                                                     |
| `version`                                      | K-22 rule 2                                                                                                                                                                |

- An index on `(contact_hash, started_at)`. Row-level security on; `rosie_job` selects, inserts and updates; `rosie_app` holds no grant and reaches a row only through three security-definer calls keyed by what the caller holds, as K-22 rule 5's four are (README lines 94 to 101; owned by the migrations' role, `search_path` pinned as 0020 lines 857 to 882, `EXECUTE` to the two roles only): `sign_in_attempt(attempt_id, device_sha256, at)` answers the binding or no row (any other device: no row); `sign_in_attempt_tried(id, check_sha256, outcome, at)` records a check, a wrong one raising `wrong_tries` and the fifth setting the pause, as `check_proof_code` does (0020 lines 756 to 768); `sign_in_attempt_signed_in(id, session_id)`. None returns a hash.
- **The key:** `contact_hash` is HMAC-SHA-256, under the Workers secret `PROOF_CODE_HASH_KEY`, of a fixed prefix, the typed kind and the contact as normalized (an email in lower case; a mobile in E.164), never the contact itself; the code's hash is the same HMAC with its own prefix (K-22 README line 55). The name is the one K-22's fixtures use (`contracts/db-schema/people-access/fixtures/seed-proof-code.json` line 14); the release engineer may rename it (K-22 README line 131). One key with two prefixes: open point 4. The action layer reads no key itself (`actions/src/page-calls/staging/test-phone/types.ts` lines 4 to 5): the root hands it a hashing port.

**`startSignIn`'s rules**, in one transaction under a transaction-level advisory lock keyed on the contact hash (as the claim locks a recipient: K-05 README line 90), so two starts never both pass the cap:

1. A row with the request's key: answer it again (`repeated`: its attempt id and expiry), write nothing. So a repeated `requestId` sends no second code (K-21 schema line 688).
2. The contact's latest `paused_until` after now: answer `paused` until then, write nothing.
3. **The day's cap:** `SIGN_IN_STARTS_PER_DAY` (default 5) attempts of that contact in the 24 hours before now: answer `paused` until the oldest of them is 24 hours old, write nothing (S13-45: "At most a few codes a day per contact"; open point 1).
4. The account, in one statement: by `accounts.email` with `email_proven_at` set, or by `accounts.mobile`, with whether its person holds a live owner or admin role (K-04 `person_roles`). Way email needs the account's proven email (K-21 schema line 688: "never to an email not yet proven").
5. Insert the attempt, with the person and the role flag when found, else null and false, and answer `started`. For the server only it names the person and the email handle to send to; neither reaches the page.

Steps 1 to 3 never read an account, and steps 4 and 5 run the same statements whether or not one matches, so a pause and a cap answer alike for any typed contact (K-21 schema line 780). **The answer waits on no write the two paths do not share:** the code, its row and its entry come after it. **After the answer**, with an account, `sendSignInCode` first reads `proof_code_limits` for that email handle and `sign_in` since 24 hours ago (0020 lines 777 to 797): when the codes to that address, every purpose, have reached the cap, or a sign-in code of it is paused, nothing is written or sent. The answer already said `started`, as for any way with no contact on file (K-21 README line 114).

**The check** (`proveSignIn`, one transaction): the binding by `sign_in_attempt` (none: `attemptNotFound`); a repeat of this check answers its first result, a `signedIn` one as `alreadySignedIn` with no token (K-21 README line 115); a signed-in attempt: `alreadySignedIn`; `paused_until` after now: `paused`; past `expires_at`: `expired`; then `check_proof_code(code id, typed hash, at)`. **An attempt with no code calls it with a null id, which answers `unknown` before any write** (0020 line 723), read as a wrong code, so both paths send the same statements. A wrong code records its try and commits at once, so it counts whatever fails after (K-22 README line 212). `right`: section 6's steps. Outcomes map as K-21 README line 116 says. So **a sixth check after five wrong ones answers `paused` from the server, with or without the page's cookie** (STATE note 74; T-520's security note a, T-520.md line 75), and a new start for that contact answers `paused` and sends nothing.

**The numbers** are code's, named in the page call: 5 tries, a 15-minute pause, a 10-minute code (RULES 6.2; 0020 lines 364 to 371), and `SIGN_IN_STARTS_PER_DAY` = 5 in a rolling 24 hours (open point 1). The pause stays per attempt, as K-22 default 8 keeps it per code; the day's cap bounds the guesses (at most 25 a day for a contact, against a million 6-digit codes).

### 6. Roles (B7)

- So "the code and its email row in one commit" runs wholly as `rosie_job`, and "the check, `device_known` and the session insert in one transaction" wholly as `rosie_app`, where K-22 rule 5's session lock binds it. Both of the critic's single-transaction steps hold under two logins.

## Alternatives not chosen

- **A turn row for the call** (K-05 open gap 3's other option): a page call is not "a batch of a handle's texts" (arch 01 line 59), turn ids hash texts' event ids (K-08 default 9), and a call that writes no row has no handle to own it.
- **Sending the code outside the outbox** (K-12 line 25 names such a send): K-22 rule 5 sends a code "in the one commit with its outbox row" (README line 89), K-09 and K-12's fixtures make it a row (`out-sam-signin-code`; `send-code.json`'s key), and it would lose the retries, limit 8's stop and the trace.
- **A K-04 v2 (breaking):** section 1's expansion keeps every v1 reader and writer as it is.
- **The attempt in a Durable Object or KV:** the system of record is PostgreSQL (arch 10 line 504), the try must commit with the code's check and the session, and KV takes about 60 s to agree (arch 10 line 518).
- **One role for the whole sign-in:** as `rosie_job` the session insert loses K-22 rule 5's lock; as `rosie_app` there is no grant on `accounts` (0020 lines 46 to 47), and its grants on `outbox_rows` and `event_log` admit only its own business's rows (`0012_core_rls.sql` lines 89 to 96, 105), while a sign-in's rows have no business.
- **The pause by handle alone** (`proof_code_limits`): an address with no account has no handle, so the answers would differ (K-21 schema line 780).
- **Testers as K-36 team rows:** build prompt 9.4 (line 490).
- **The double's record as the testers' way in:** circular (K-21 README line 96).
- **A hashed attempt id:** a repeat must answer the same attempt (K-21 README line 75), which a stored hash cannot give back.
