# ADR-014: The Worker's database roles: one login for each side, each behind its own Hyperdrive configuration

- Status: proposed, default in use (T-1239; the lead's ruling DL-492, which hands the D-017 path audit's ruling R1 to this record)
- Date: 2026-11-11
- Owner: architect. Decides: the CTO, with the database engineer (CQ-208's owners).
- This record changes nothing by itself: no contract, migration, code, config or live step. Decision section 4 lists who makes each piece and which live steps are the user's. Production is not touched (section 5).

## Context

- **Two roles, one for each side.** Migration 0012 makes `rosie_app` for the Tool API (K-05 scope business) and `rosie_job` for the runtime side (the guard, the dispatcher, the clock sweep, the gateway, the publisher). With no business scope `rosie_app` sees no row and `rosie_job` sees every business's rows (`db/migrations/0012_core_rls.sql` lines 15 to 27). Both are NOLOGIN: "the deploy names the login role that is granted one of them (never both: a member of both would take both policies)" (lines 13 to 14).
- **Whom row-level security does not bind.** "A superuser and a table's owner (the migrations' role) bypass row-level security; no table forces it on its owner" (0012 line 28). PostgreSQL's page: "Superusers and roles with the `BYPASSRLS` attribute always bypass the row security system when accessing a table. Table owners normally bypass row security as well" [P2].
- **The code already takes one client for each side.** `pgTurnCalls(runtime, toolApi, ...)`: "`runtime` is a client whose connections run as rosie_job, `toolApi` one whose connections run as rosie_app" (`actions/src/tool-api/turn-face/pg/calls.ts` lines 93 to 96; `pgCallScope(toolApi)` line 40, `pgSafetyReads(runtime)` line 45, `pgRowData(runtime)` line 83, `pgReadOnlySealer(runtime, ...)` line 102). Each `RootOptions` comment names the role of its calls (`runtime/src/wiring/root.ts` lines 183 to 301; for example lines 233 to 240).
- **db/repo sets no role.** `createClient` passes `application_name` and, when a schema is set, `search_path`, and nothing else (`db/repo/client.ts` lines 114 to 123). `withBusiness` opens its own transaction (`db/repo/scope.ts` line 99); `bundles.ts` reserves a connection and begins (lines 158 to 187); `flags.ts` (lines 76, 142) and `bundles.ts` (lines 224, 246) send one bare statement with no transaction. A search of db/repo's history outside its tests (`git log -i -E -G "set (local )?role|session authorization" -- db/repo ":(exclude)db/repo/*.test.ts"`, Nov 11 2026) finds no commit that added or removed such a line. db/repo says whose the role is: "The role is the connection's: the caller passes the client of the role the read names" (`db/repo/turn-face-reads.ts` lines 26 to 27; `db/repo/safety-reads.ts` lines 18 to 19 say the same of "the client, or the transaction"). Outside db/repo the seeds switch role inside their transaction, as the migrations' role under Node (`db/seeds/core.ts` line 90), and the local integration tests set a `role` startup parameter on a direct connection (`actions/src/commit/pg/test-support.ts` line 72). So CQ-208's default, "switching to rosie_job or rosie_app per call as db/repo does" (`ops/QUESTIONS.md` CQ-208), rests on a wrong premise, as the D-017 path audit found (`ops/reviews/D-017-path-audit/order_d017.txt` line 12).
- **The configuration the spike made stores the migrations' role.** `rosie-staging-hyperdrive` was made from `STAGING_DATABASE_URL` (`infra/spikes/hyperdrive-host/FINDINGS.md` line 38; `run.sh` lines 160 to 178). The migrations run with that string (`infra/scripts/deploy-staging.sh` line 6) and the seeds log in with it (`infra/scripts/seed-staging.sh` lines 15 to 16), so its role made the tables and owns them, and row-level security does not bind it (0012 line 28; DL-492, ruling 2). The role's name was not checked (FINDINGS.md line 40) and need not be: whatever it is, the Worker must not hold it. Neon's page adds that a role made in its console or API (and by its CLI, unless told otherwise) is "granted membership in the `neon_superuser` role", which has CREATEROLE, CREATEDB, REPLICATION, BYPASSRLS (in projects made after Aug 15 2023) and the predefined roles that read and write all data, and whose privileges its members inherit; roles made with SQL "are not granted membership in the `neon_superuser` role" [N6].
- **What the spike measured through Hyperdrive.** A transaction kept one backend and one transaction id over 5 rounds while other queries went through the pool, and a setting made with `set_config(..., true)` held inside it and was not found on the pool afterwards (FINDINGS.md section 4). That is how `withBusiness` sets the business scope (`scope.ts` lines 42 to 45). The queries outside the transaction were seen on 3 backends (FINDINGS.md section 4, `backends_seen_outside_transaction`).
- **What the spike did not measure.** State that outlives a transaction on a pooled connection (FINDINGS.md line 165). Any startup parameter: the probe's Worker hands postgres.js the binding's string and "sets nothing else" (FINDINGS.md line 35). Which role the configuration stores, and `hyperdrive update` (FINDINGS.md line 40).
- **What Cloudflare's pages say** (read Nov 11 2026). "The Hyperdrive connection pooler operates in transaction mode"; "Hyperdrive supports SET statements for the duration of a transaction or a query"; "When a connection is returned to the pool, the connection is `RESET`", so that a `SET` does not carry to later queries [C3]. Among the features Hyperdrive does not support: "Any modification to per-session state not explicitly documented as supported elsewhere" [C4]. A configuration is given one origin user: `--origin-user`, "The username used to connect to the origin database", with `--origin-password`, or the user and password inside `--connection-string`; `hyperdrive update` takes the same options [C5]. Not stated on those pages: what Hyperdrive does with a startup parameter a client sends (a `role`, a `search_path`), which reset a returned connection gets, and which user a pooled connection logs in as.
- **postgres.js sends startup parameters.** Its Workers build puts every entry of the `connection` option into the startup message beside the user and the database (`node_modules/postgres/cf/src/connection.js`, `StartupMessage`; postgres 3.4.9 as installed). So `client.ts`'s `search_path` (line 121) and the tests' `role` are startup parameters. Through Hyperdrive they reach Hyperdrive, and what it does with them is not stated [C3][C4] and not measured.
- **A local or CI test sees none of this.** The local and CI login `rosie` is the container's first user (`infra/docker-compose.yml` lines 11 to 14; `.github/workflows/ci.yml` lines 34 to 36; ADR-006). Read on the local database (PostgreSQL 17.5) on Nov 11 2026, read-only: `rosie` has `rolsuper` and `rolbypassrls` true; `pg_has_role(current_user, ..., 'USAGE')` and `'MEMBER'` answer true for both `rosie_app` and `rosie_job`; the server holds 4 `businesses` tables, all 4 with row-level security switched on, and `row_security_active` answers false on all 4.
- **Two cards wait.** T-567 (the binding) waits for this record, "so it binds the right login or logins once" (DL-492, ruling 2). T-1093 is carded with a deploy-time check that the Worker's login is a member of exactly one of the two roles, owns no table or function, is not a superuser and has no BYPASSRLS (`ops/cards/T-1093.md`, "Gives").

## Decision

### 1. How each side gets its role: two dedicated logins (the card's option (a))

| Side                                  | Login role         | Inherits         | Staging's Hyperdrive configuration | Binding          |
| ------------------------------------- | ------------------ | ---------------- | ---------------------------------- | ---------------- |
| The runtime side (K-05 scope runtime) | `rosie_worker_job` | `rosie_job` only | `rosie-staging-hyperdrive-job`     | `HYPERDRIVE_JOB` |
| The Tool API (K-05 scope business)    | `rosie_worker_app` | `rosie_app` only | `rosie-staging-hyperdrive-app`     | `HYPERDRIVE_APP` |

- **Each login** is made `LOGIN NOSUPERUSER NOCREATEDB NOCREATEROLE NOREPLICATION NOBYPASSRLS` and granted its one role `WITH INHERIT TRUE, SET FALSE` [P3]. So it has the role's privileges without a switch and can switch to no role at all. PostgreSQL's own example of that grant: "it is not possible to become `island` at all; `joe` can only access those privileges via inheritance" [P4]. It is a member of no other role, owns nothing and holds no grant of its own, so 0012's grants and each later migration's stay the whole list of what the Worker may do.
- **Made with SQL, never in the host's console, CLI or API**, so the host adds no membership (a role made in Neon's console or API joins `neon_superuser` [N6]). T-1093's check proves the result either way (section 4).
- **The Worker's database handle** makes the runtime side's clients from `HYPERDRIVE_JOB` only and the Tool API's from `HYPERDRIVE_APP` only. No code that runs in the Worker sets a role: no `SET ROLE`, no `SET LOCAL ROLE`, no `role` startup parameter. With SET FALSE a switch would be refused anyway.
- **Both configurations have caching disabled** (ADR-007: both sides make decision reads).

Why:

1. **The role is fixed by the connection.** No call can forget a switch and run as another role, because there is no switch. With one membership and SET FALSE, nothing the Worker sends can widen a login.
2. **The Worker never holds the migrations' role,** which owns the tables, can alter or drop them, and reads past every policy (0012 line 28).
3. **Its safety rests on PostgreSQL and on the guard, not on pool state.** It needs PostgreSQL's logins, grants and policies, and from Hyperdrive only what a configuration is: one stored origin user [C5], used for queries and transactions as the spike measured (FINDINGS.md section 4). No role state has to cross the pool. That every backend of a configuration logs in as its stored user is documented only by those options and is not measured: the guard reads it in every call, and the live check measures it before traffic (section 2, "What the answer covers"; section 4, piece 7).
4. **It fits what is written.** 0012 lines 13 to 14 and T-1093's check hold word for word, once for each login.
5. **db/repo and @rosie/actions need no change.** They already take a client for each side and say the role is the connection's (Context). db/repo's own role checks read rights, not a name: `pg_has_role(current_user, 'rosie_app', 'USAGE')` and the same for `rosie_job` (`turn-face-reads.ts` lines 233 to 243; `safety-reads.ts` lines 198 to 206). `USAGE` "denotes whether the privileges of the role are immediately available without doing `SET ROLE`" [P1], so a login that inherits a role answers as the role does.
6. Cloudflare's Neon page suggests a dedicated role (FINDINGS.md section 6, its source [C1]).

One premise is PostgreSQL's and is not yet measured in this repository: that a policy written `to rosie_app` binds a login that inherits `rosie_app`. PostgreSQL's page: "Multiple roles can be assigned to a given policy, and normal role membership and inheritance rules apply" [P2]; 0012 lines 13 to 14 assume the same. Every test so far switches to the role itself (`test-support.ts` line 72; `core.ts` line 90). If the premise were wrong, the login would read and write no row of a table under row-level security, since there "all normal access to the table for selecting rows or modifying rows must be allowed by a row security policy" [P2]: it fails closed. The test rig's first tests measure it (section 4, piece 5).

### 2. The guard in every call

**Where.** In the Worker's database handle, `runtime/src/wiring/staging/db.ts` (the audit's part P1a: "role and schema checked inside each call", `order_d017.txt` line 29). Each client a call uses is opened for that call, and its first statement is the guard: one `select` of PostgreSQL's own functions. Only when it passes is the client handed to the call's code, and db/repo's calls then run on it unchanged.

**What it reads, and what it must get:**

| The guard reads                                         | Runtime side             | Tool API side            | A wrong answer means                                                                                |
| ------------------------------------------------------- | ------------------------ | ------------------------ | --------------------------------------------------------------------------------------------------- |
| `session_user` and `current_user`                       | both `rosie_worker_job`  | both `rosie_worker_app`  | another login is behind the binding, the bindings are crossed, or something switched role           |
| `pg_has_role(current_user, <its own role>, 'USAGE')`    | `rosie_job`: true        | `rosie_app`: true        | the login lacks its side's rights                                                                   |
| `pg_has_role(current_user, <the other role>, 'MEMBER')` | `rosie_app`: false       | `rosie_job`: false       | the login holds, or could take, the other side's rights (a superuser answers true)                  |
| `row_security_active('businesses')`                     | true                     | true                     | PostgreSQL says row-level security is not in force for this user: a superuser, BYPASSRLS, the owner |
| `current_schema()`                                      | `DB_SCHEMA`, or `public` | `DB_SCHEMA`, or `public` | the call would read and write another schema                                                        |

- The functions are PostgreSQL's own [P1]. `row_security_active` answers "Is row-level security active for the specified table in the context of the current user and current environment?", so the guard need not list every way a role can bypass. `MEMBER` "denotes direct or indirect membership in the role without regard to what specific privileges may be conferred", so a membership taken with INHERIT FALSE is caught too. `businesses` is the first of 0012's business-scoped tables, and both roles hold SELECT on it (0012 lines 90 to 93, 106 to 118).
- The schema is checked always, not only where `DB_SCHEMA` is set. The server's path, read through the spike's configuration, was `"$user", public` (FINDINGS.md section 2), so a schema named after a login would come first; the check catches it.
- **A wrong answer throws and writes nothing.** On a wrong answer or a missing row the handle ends the client and throws a refusal. The call's code never runs, so none of its statements is sent, and the guard itself only reads. The port fails closed exactly as it does with no binding. A refusal is never answered as `transient`: a retry cannot fix it. An error from the guard's own statement (a lost connection, say) is reported as the call's errors are, by the call's name and the SQLSTATE (`order_d017.txt` line 29), and the call's code does not run either.
- **What a refusal and its log line carry:** the side, the binding's name and the failed check's label. Never a connection string, a host, a password, a row, or any value the guard read.
- **Every call, never remembered.** Not once for an isolate, not once for a request: a configuration can be updated in place, and a role's memberships can change, while an isolate lives.
- **What it costs:** one more round trip for each client a call opens. On staging a one-row read on an open connection took p50 18 ms and p95 19 ms (FINDINGS.md section 3). That is arithmetic from the spike, not a measurement of the guard. If a later measurement shows the guard breaking a budget, it comes back to the architect; nobody drops it or caches it on their own.

**What the answer covers.** Outside a transaction Hyperdrive may serve the call's later statements from other backends (FINDINGS.md section 4 saw 3), so the guard reads the backend that answers it. Everything it reads about the role is a property of the login the configuration stores: who it is, what it inherits, what it owns. A configuration is given one origin user [C5], no code switches role, and SET FALSE refuses a switch, so every backend the configuration opens should answer the same, and the guard can sit in the handle, outside db/repo's own transactions. That every backend logs in as the stored user is the one Hyperdrive property this design takes from Cloudflare's documents rather than from a measurement. Three things hold it: the live check measures it on many backends of each configuration before any traffic (section 4, piece 7); the guard samples it again in every call; and once the spike's configuration is deleted (section 3), no configuration on the account stores any user for staging's database but the two logins, so even a fault in Hyperdrive's pools could at worst put a call on the other side's login, not on the migrations' role. Under a role switch (options (b) and (c) below) the role would be transaction or session state: the guard would have to run inside each of db/repo's transactions, and could not cover a bare statement at all.

**Where the schema check is sound, and previews.**

- Staging and production: `DB_SCHEMA` is empty (`wrangler.jsonc` lines 50, 67, 126), so `client.ts` sends no `search_path` (lines 90 to 99, 121). The path is then the server's default for the login, not session state, and the check is sound.
- Local runs and the test rig connect without Hyperdrive's pooling (with a local connection string, "Hyperdrive's connection pooling and query caching do not take effect": FINDINGS.md line 199, [C2]): one connection is one backend, and the check is sound.
- A branch preview: `deploy-preview.sh` uploads a version of rosie-staging from the branch's `wrangler.jsonc` with `DB_SCHEMA` set to `preview_<slug>` (`infra/scripts/deploy-preview.sh` lines 28 to 34; `wrangler.jsonc` line 61). Once T-567 lands, a preview carries env.staging's two bindings, and its schema would reach Hyperdrive only as a startup parameter, whose handling is not stated and not measured (Context). The guard would catch a wrong path on the backend that answers it, but could not prove the path on the backends that run the call. **So the handle opens no client through either binding while `DB_SCHEMA` is set:** a preview's database ports stay closed, as with no binding, until a spike measures a startup `search_path` through the pool or the schema is set another way (Consequences, open question 1). On a direct connection `DB_SCHEMA` works as today.

**Why a local or CI test cannot prove this by itself.**

1. The local and CI login is a superuser with BYPASSRLS (Context). It bypasses row-level security, passes every privilege check and may become any role. So a test that connects as `rosie` passes whichever client the handle picked, and "current_user is rosie_job" after a role option passes locally under any design (the T-1154 map's critics: `ops/reviews/T-1154-map/critic_size.txt` B2, `critic_collisions.txt` B1).
2. With the rig's own two logins, a local test proves the guard's logic and the policies against local roles. It cannot show which login staging's configuration stores, what that login owns or inherits on staging's server, or what the host added to it.

So three proofs, each for what the others cannot see:

- **The rig, locally and in CI** (pieces 5 and 6): the guard passes on the right login and refuses the superuser, crossed bindings, a login that inherits both roles, a login that is a member of the other role with INHERIT FALSE, a login that owns `businesses`, and a wrong schema. After each refusal the call's code did not run and the row counts are unchanged.
- **T-1093's check, at each deploy:** the catalog of the real server and each configuration's stored user, before traffic.
- **The guard itself, in the deployed Worker, in every call,** and once the live check (piece 7).

**The script's rules (piece 2).** It follows T-1236's way with staging's secrets (`infra/scripts/make-staging-secrets.sh` lines 2 to 56; CQ-210) and the spike's `run.sh` (lines 14 to 27, 160 to 184).

- It lists first and makes only what is missing (T-567's lead note, DL-476): a configuration of the name that exists is left exactly as it is, never replaced. It never changes the migrations' role, and never makes a configuration with the migrations' user.
- Before it makes anything it prints the server's `max_connections`, and each login's shape as it finds it (names and flags, never a value).
- For each missing configuration, in one run: piece 1's file makes the login if it is missing; a fresh password is set on the login; `hyperdrive create` makes the configuration with that login as the origin user and caching disabled; the password is dropped.
- The password is 32 random bytes from Node's crypto, as T-1236 makes its values (`make-staging-secrets.sh` lines 24 to 26), written with no character that needs quoting (hex or base64url). That meets Neon's rule of at least 60 bits of entropy and 12 characters [N6].
- To PostgreSQL it goes inside `ALTER ROLE ... PASSWORD '...'`, sent by a Node process over the connection the string names. Neon takes a password only in clear text ("Hashed passwords are not supported" [N6]), so the statement's text holds it, and PostgreSQL's caution applies: it "might also be logged in the client's command history or the server log" [P5]. So the script sends it from Node, never on a shell or `psql` line, with postgres.js's debug off. Whether staging's host logs such a statement: not checked.
- To wrangler it goes as `--origin-password`, one argument [C5], as the spike's string did (`run.sh` lines 23 to 24: wrangler takes it no other way). The security reviewer accepted those seconds in the process list for the spike on this single-user Mac (DL-482), which is why the run happens while no agent runs (DL-486).
- It is held nowhere else: not printed, not written to a file, not in `.dev.vars`, not exported. Inherited export marks are dropped first (DL-482's lesson), xtrace is refused, and wrangler's output is redacted on failure (`run.sh` lines 179 to 184). It exists only in PostgreSQL and in the configuration.

## Alternatives not chosen

- **(b) One login that switches with `SET LOCAL ROLE` in each transaction, through a named hook.** `SET` for the length of a transaction is documented [C3], and the spike measured a transaction-scoped setting (FINDINGS.md section 4), though not a role. It is rejected for what it needs elsewhere:
  - The login must be able to become both roles, against 0012 lines 13 to 14 and T-1093 as written.
  - A forgotten switch runs as the login. If the login inherits both roles, both sets of policies apply, "combined using `OR`" for permissive policies [P2], so a Tool API read with no scope sees every business. If it is today's stored login, it bypasses row-level security. Only a login that inherits nothing fails closed, and that login would have to be made anyway, so (b) saves no live step.
  - A login with SET on both roles can also run a plain `SET ROLE`, which outlives the transaction on a pooled backend; which reset Hyperdrive runs is not stated [C3], so such a mistake could reach another client's statements. Under (a) SET FALSE refuses it.
  - db/repo has no place for the hook. Each call opens its own transaction or sends a bare statement (Context), so every K-05 call's code would change, every bare read would become a transaction (on staging a transaction of four round trips took p50 72 ms against 18 ms for one statement: FINDINGS.md section 3), and each new call would have to remember.
- **(c) A `role` startup parameter, as the local tests set.** It is per-session state, unsupported unless documented [C4]; startup parameters are not mentioned on the pages read [C3][C4]; it was never measured (FINDINGS.md line 35); and the login would need SET on both roles. If Hyperdrive dropped the parameter, the call would run as the stored login, which today is the migrations' role: it fails open.
- **Binding the spike's configuration now and moving to a dedicated role later** (CQ-208's earlier default; DL-482). Staging holds test data only, but every call would run past the policies, so staging would prove nothing about row-level security, and T-570's pass would not show production's shape (DL-492, ruling 2).
- **One login for both sides, as `rosie_job`, with the scope checks alone.** The Tool API would lose `rosie_app`'s "no scope, no row" and its narrower grants (0012 lines 15 to 20; `scope.ts` lines 8 to 12).
- **Forcing row-level security on the tables' owner.** FORCE binds an owner, but not a superuser or a role with BYPASSRLS [P2]; it changes every table (a K-04 change); and the Worker would still hold the role that can drop them.
- **The logins in a migration.** 0012 lines 13 to 14 leave the login to the deploy. A migration runs in every schema of a server (0012 lines 12 to 13) and its text is public and frozen, so no password can be in it, and the passwords would still need a script. One SQL file that the staging script and the rig both run is one source, and T-1093's check proves it on the server.
- **Turning the spike's configuration into one of the two with `hyperdrive update`.** The command exists [C5] and was not run (FINDINGS.md line 40); `create` was. A new name also says which login it stores.
- **Running the guard inside each of db/repo's transactions.** It would change db/repo and still miss its bare statements. Under (a) the role is the configuration's, so the handle is the place.
- **A guard that checks the name alone, or once for an isolate.** A name says nothing of what the login inherits or owns, and an isolate can outlive a change to a configuration.
