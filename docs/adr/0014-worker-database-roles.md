# ADR-014: The Worker's database roles: one login for each side, each behind its own Hyperdrive configuration

- Status: proposed, default in use (T-1239; the lead's ruling DL-492, which hands the D-017 path audit's ruling R1 to this record, and DL-499, which sent it to a second round)
- Date: 2026-11-11
- Owner: architect. Decides: the CTO, with the database engineer (CQ-208's owners).
- This record changes nothing by itself: no contract, migration, code, config or live step. Decision section 4 lists who makes each piece and which live steps are the user's. Production is not touched (section 5).

## Context

- **Two roles, one for each side.** Migration 0012 makes `rosie_app` for the Tool API (K-05 scope business) and `rosie_job` for the runtime side (the guard, the dispatcher, the clock sweep, the gateway, the publisher). With no business scope `rosie_app` sees no row and `rosie_job` sees every business's rows (`db/migrations/0012_core_rls.sql` lines 15 to 27). Both are NOLOGIN: "the deploy names the login role that is granted one of them (never both: a member of both would take both policies)" (lines 13 to 14).
- **Whom row-level security does not bind.** "A superuser and a table's owner (the migrations' role) bypass row-level security; no table forces it on its owner" (0012 line 28). PostgreSQL's page: "Superusers and roles with the `BYPASSRLS` attribute always bypass the row security system when accessing a table. Table owners normally bypass row security as well" [P2].
- **The code already takes one client for each side.** `pgTurnCalls(runtime, toolApi, ...)`: "`runtime` is a client whose connections run as rosie_job, `toolApi` one whose connections run as rosie_app" (`actions/src/tool-api/turn-face/pg/calls.ts` lines 93 to 96; `pgCallScope(toolApi)` line 40, `pgSafetyReads(runtime)` line 45, `pgRowData(runtime)` line 83, `pgReadOnlySealer(runtime, ...)` line 102). Each `RootOptions` comment names the role of its calls (`runtime/src/wiring/root.ts` lines 183 to 301; for example lines 233 to 240).
- **db/repo sets no role.** `createClient` passes `application_name` and, when a schema is set, `search_path`, and nothing else (`db/repo/client.ts` lines 114 to 123). `withBusiness` opens its own transaction (`db/repo/scope.ts` line 99); `bundles.ts` reserves a connection and begins (lines 158 to 187); `flags.ts` (lines 76, 142) and `bundles.ts` (lines 224, 246) send one bare statement with no transaction. A search of db/repo's history outside its tests (`git log -i -E -G "set (local )?role|session authorization" -- db/repo ":(exclude)db/repo/*.test.ts"`, Nov 11 2026) finds no commit that added or removed such a line. db/repo says whose the role is: "The role is the connection's: the caller passes the client of the role the read names" (`db/repo/turn-face-reads.ts` lines 26 to 27; `db/repo/safety-reads.ts` lines 18 to 19 say the same of "the client, or the transaction"). Outside db/repo the seeds switch role inside their transaction, as the migrations' role under Node (`db/seeds/core.ts` line 90), and the local integration tests set a `role` startup parameter on a direct connection (`actions/src/commit/pg/test-support.ts` line 72). So CQ-208's default, "switching to rosie_job or rosie_app per call as db/repo does" (`ops/QUESTIONS.md` CQ-208), rests on a wrong premise, as the D-017 path audit found (`ops/reviews/D-017-path-audit/order_d017.txt` line 12).
- **The configuration the spike made stores the migrations' role.** `rosie-staging-hyperdrive` was made from `STAGING_DATABASE_URL` (`infra/spikes/hyperdrive-host/FINDINGS.md` line 38; `run.sh` lines 160 to 178). The migrations run with that string (`infra/scripts/deploy-staging.sh` line 6) and the seeds log in with it (`infra/scripts/seed-staging.sh` lines 15 to 16), so its role made the tables and owns them, and row-level security does not bind it (0012 line 28; DL-492, ruling 2). The role's name was not checked (FINDINGS.md line 40) and need not be: whatever it is, the Worker must not hold it. Neon's page adds that a role made in its console or API (and by its CLI, unless told otherwise) is "granted membership in the `neon_superuser` role", which has CREATEROLE, CREATEDB, REPLICATION, BYPASSRLS (in projects made after Aug 15 2023) and the predefined roles that read and write all data, and whose privileges its members inherit; roles made with SQL "are not granted membership in the `neon_superuser` role" [N6].
- **How the spike gave wrangler the password.** Its create step passed the whole connection string, password included, as one `--connection-string` argument, because "wrangler has no other way to take it" (`run.sh` lines 23 to 24, 177 to 178). Wrangler's other form takes `--origin-password` [C5]. DL-482 accepted those seconds in the process list for that one step.
- **What the spike measured through Hyperdrive.** A transaction kept one backend and one transaction id over 5 rounds while other queries went through the pool, and a setting made with `set_config(..., true)` held inside it and was not found on the pool afterwards (FINDINGS.md section 4). That is how `withBusiness` sets the business scope (`scope.ts` lines 42 to 45). The queries outside the transaction were seen on 3 backends (FINDINGS.md section 4, `backends_seen_outside_transaction`).
- **What the spike did not measure.** State that outlives a transaction on a pooled connection (FINDINGS.md line 165). Any startup parameter: the probe's Worker hands postgres.js the binding's string and "sets nothing else" (FINDINGS.md line 35). Which role the configuration stores, and `hyperdrive update` (FINDINGS.md line 40).
- **What Cloudflare's pages say** (read Nov 11 2026). "The Hyperdrive connection pooler operates in transaction mode"; "Hyperdrive supports SET statements for the duration of a transaction or a query"; "When a connection is returned to the pool, the connection is `RESET`", so that a `SET` does not carry to later queries [C3]. Among the features Hyperdrive does not support: "Any modification to per-session state not explicitly documented as supported elsewhere" [C4]. A configuration is given one origin user: `--origin-user`, "The username used to connect to the origin database", with `--origin-password`, or the user and password inside `--connection-string` [C5]; the API's create takes the same origin in a request body, where the password is "write-only" and never returned [C7]. Not stated on those pages: what Hyperdrive does with a startup parameter a client sends (a `role`, a `search_path`), which reset a returned connection gets, and which user a pooled connection logs in as.
- **postgres.js sends startup parameters.** Its Workers build puts every entry of the `connection` option into the startup message beside the user and the database (`node_modules/postgres/cf/src/connection.js`, `StartupMessage`; postgres 3.4.9 as installed). So `client.ts`'s `search_path` (line 121) and the tests' `role` are startup parameters. Through Hyperdrive they reach Hyperdrive, and what it does with them is not stated [C3][C4] and not measured.
- **Every server is PostgreSQL 17 today.** Staging reported `17.11` (FINDINGS.md lines 11 and 50); the local and CI image is `postgis/postgis:17-3.5` (`infra/docker-compose.yml` line 7; `.github/workflows/ci.yml` line 32).
- **A local or CI test sees none of this.** The local and CI login `rosie` is the container's first user (`infra/docker-compose.yml` lines 11 to 14; `.github/workflows/ci.yml` lines 34 to 36; ADR-006). Read on the local database (PostgreSQL 17.5) on Nov 11 2026, read-only: `rosie` has `rolsuper` and `rolbypassrls` true; `pg_has_role(current_user, ..., 'USAGE')` and `'MEMBER'` answer true for both `rosie_app` and `rosie_job`; the server holds 4 `businesses` tables, all 4 with row-level security switched on, and `row_security_active` answers false on all 4.
- **The Workers test pool runs env.staging, and test files need their own data.** Both Workers projects read `wrangler.jsonc` with `environment: "staging"` and add one binding of their own (`vitest.config.ts` lines 76 to 79 and 139 to 142); by default their test files run side by side [C12]. The integration tests keep files apart with a schema per file, reached through `DB_SCHEMA`'s search path (`db/repo/test-db.ts` lines 1 to 2; `client.ts` lines 90 to 99, 121), and the audit asked the Workers rig for "one migrated, seeded schema per test file (named up front)" (`order_d017.txt` line 28; `ops/reviews/T-1154-map/critic_collisions.txt` B3). What the pool's binding points at locally and in CI had no default (the audit's R2, `order_d017.txt` line 74).
- **Two cards wait.** T-567 (the binding) waits for this record, "so it binds the right login or logins once" (DL-492, ruling 2). T-1093 is carded with a deploy-time check that the Worker's login is a member of exactly one of the two roles, owns no table or function, is not a superuser and has no BYPASSRLS (`ops/cards/T-1093.md`, "Gives").

## Decision

### 1. How each side gets its role: two dedicated logins (the card's option (a))

| Side                                  | Login role         | Inherits         | Staging's Hyperdrive configuration | Binding          |
| ------------------------------------- | ------------------ | ---------------- | ---------------------------------- | ---------------- |
| The runtime side (K-05 scope runtime) | `rosie_worker_job` | `rosie_job` only | `rosie-staging-hyperdrive-job`     | `HYPERDRIVE_JOB` |
| The Tool API (K-05 scope business)    | `rosie_worker_app` | `rosie_app` only | `rosie-staging-hyperdrive-app`     | `HYPERDRIVE_APP` |

- **Each login** is made `LOGIN NOSUPERUSER NOCREATEDB NOCREATEROLE NOREPLICATION NOBYPASSRLS` and granted its one role `WITH INHERIT TRUE, SET FALSE` [P3]. So it has the role's privileges without a switch and can switch to no role at all. PostgreSQL's own example of that grant: "it is not possible to become `island` at all; `joe` can only access those privileges via inheritance" [P4]. It is a member of no other role, owns nothing and holds no grant of its own, so 0012's grants and each later migration's stay the whole list of what the Worker may do.
- **PostgreSQL 16 or later.** The grant's INHERIT and SET options are new in PostgreSQL 16 ("the new `GRANT ... WITH INHERIT` clause"; "a new `GRANT ... SET` option" [P9]), and the checks below read them back from `pg_auth_members`' `inherit_option` and `set_option` columns [P8]. Staging, local and CI are PostgreSQL 17 (Context); production's server must be 16 or later too (section 5). Piece 1's file refuses an older server (`server_version_num` below 160000).
- **Made with SQL, never in the host's console, CLI or API**, so the host adds no membership (a role made in Neon's console or API joins `neon_superuser` [N6]). The guard and T-1093's check prove the result either way (sections 2 and 4).
- **The Worker's database handle** makes the runtime side's clients from `HYPERDRIVE_JOB` only and the Tool API's from `HYPERDRIVE_APP` only. No code that runs in the Worker sets a role: no `SET ROLE`, no `SET LOCAL ROLE`, no `role` startup parameter. With SET FALSE a switch would be refused anyway.
- **Both configurations have caching disabled** (ADR-007: both sides make decision reads).

Why:

1. **The role is fixed by the connection.** No call can forget a switch and run as another role, because there is no switch. With one membership and SET FALSE, nothing the Worker sends can widen a login.
2. **The Worker never holds the migrations' role,** which owns the tables, can alter or drop them, and reads past every policy (0012 line 28).
3. **Its safety rests on PostgreSQL and on the guard, not on pool state.** It needs PostgreSQL's logins, grants and policies, and from Hyperdrive only what a configuration is: one stored origin user [C5], used for queries and transactions as the spike measured (FINDINGS.md section 4). No role state has to cross the pool. That every backend of a configuration logs in as its stored user is documented only by those options and is not measured: the guard reads it in every call, and the live check measures it before traffic (section 2, "What the answer covers"; section 4, piece 7).
4. **It fits what is written.** 0012 lines 13 to 14 and T-1093's check hold word for word, once for each login.
5. **db/repo and @rosie/actions need no change.** They already take a client for each side and say the role is the connection's (Context). db/repo's own role checks read rights, not a name: `pg_has_role(current_user, 'rosie_app', 'USAGE')` and the same for `rosie_job` (`turn-face-reads.ts` lines 233 to 243; `safety-reads.ts` lines 198 to 206). `USAGE` "denotes whether the privileges of the role are immediately available without doing `SET ROLE`" [P1], so a login that inherits a role answers as the role does.
6. Cloudflare's Neon page suggests a dedicated role (FINDINGS.md section 6, its source [C1]).

One premise is PostgreSQL's and is not yet measured in this repository: that a policy written `to rosie_app` binds a login that inherits `rosie_app`. PostgreSQL's page: "Multiple roles can be assigned to a given policy, and normal role membership and inheritance rules apply" [P2]; 0012 lines 13 to 14 assume the same. Every test so far switches to the role itself (`test-support.ts` line 72; `core.ts` line 90). If the premise were wrong, the login would read and write no row of a table under row-level security, since there "all normal access to the table for selecting rows or modifying rows must be allowed by a row security policy" [P2]: it fails closed. The test rig's first tests measure it (section 4, piece 5).

### 2. The guard in every call

**Where.** In the Worker's database handle, `runtime/src/wiring/staging/db.ts` (the audit's part P1a: "role and schema checked inside each call", `order_d017.txt` line 29). Each client a call uses is opened for that call, and its first statement is the guard: one `select` of PostgreSQL's own functions and catalogs. Only when it passes is the client handed to the call's code, and db/repo's calls then run on it unchanged.

**What it reads, and what it must get:**

| The guard reads                                                             | Runtime side                                                   | Tool API side                      | A wrong answer means                                                                                    |
| --------------------------------------------------------------------------- | -------------------------------------------------------------- | ---------------------------------- | ------------------------------------------------------------------------------------------------------- |
| `session_user` and `current_user`                                           | both `rosie_worker_job`                                        | both `rosie_worker_app`            | another login is behind the binding, the bindings are crossed, or something switched role               |
| The login's memberships: the rows of `pg_auth_members` whose `member` is it | exactly one: `rosie_job`, inherit true, set false, admin false | exactly one: `rosie_app`, the same | a membership a person or the host added (`pg_read_all_data`, `neon_superuser` [N6]), or the wrong grant |
| `pg_has_role(current_user, <its own role>, 'USAGE')`                        | `rosie_job`: true                                              | `rosie_app`: true                  | the login lacks its side's rights                                                                       |
| `pg_has_role(current_user, <the other role>, 'MEMBER')`                     | `rosie_app`: false                                             | `rosie_job`: false                 | the login holds, or could take, the other side's rights through any chain (a superuser answers true)    |
| `row_security_active('businesses')`                                         | true                                                           | true                               | PostgreSQL says row-level security is not in force for this user: a superuser, BYPASSRLS, the owner     |
| `current_schema()`                                                          | `public`                                                       | `public`                           | the call would read and write another schema (the handle never sends a search path: below)              |

- The functions are PostgreSQL's own [P1]. `row_security_active` answers "Is row-level security active for the specified table in the context of the current user and current environment?", so the guard need not list every way a role can bypass. `MEMBER` "denotes direct or indirect membership in the role without regard to what specific privileges may be conferred", so a membership taken with INHERIT FALSE is caught too. `businesses` is the first of 0012's business-scoped tables, and both roles hold SELECT on it (0012 lines 90 to 93, 106 to 118).
- **Memberships are read by member, never by role.** Only the login's own rows count (`member` is "ID of a role that is a member of `roleid`" [P8]). When a role that is not a superuser makes a role, PostgreSQL grants the new role back to its maker "WITH ADMIN TRUE, SET FALSE, INHERIT FALSE" [P7], so on staging the migrations' role will hold such a row on each login, with the login as `roleid`, not as `member`. Locally and in CI the maker is the superuser `rosie` and no such row appears. Read by member, both servers answer alike; read by role, staging would refuse a correct login that local tests pass (the database engineer's round 1 note 3).
- **Why the membership read is needed beside `row_security_active`.** A membership in a role that bypasses does not always turn row-level security off for the member: PostgreSQL names LOGIN, SUPERUSER, CREATEDB and CREATEROLE as attributes "never inherited as ordinary privileges on database objects are" [P4]; that BYPASSRLS behaves alike is the database engineer's round 1 note 1, not read on a page. Either way an inherited `pg_read_all_data` or `pg_write_all_data` opens every table that has no policy, such as `phones`, `handles` and `sealing_keys` (0012 lines 18 to 19, 98 to 103), while `row_security_active('businesses')` stays true. Exactly one membership catches it in every call, not only at deploy.
- **A wrong answer throws and writes nothing.** On a wrong answer or a missing row the handle ends the client and throws a refusal. The call's code never runs, so none of its statements is sent, and the guard itself only reads. The port fails closed exactly as it does with no binding. A refusal is never answered as `transient`: a retry cannot fix it. An error from the guard's own statement (a lost connection, say) is reported as the call's errors are, by the call's name and the SQLSTATE (`order_d017.txt` line 29), and the call's code does not run either.
- **What a refusal and its log line carry:** the side, the binding's name and the failed check's label. Never a connection string, a host, a password, a row, or any value the guard read.
- **Every call, never remembered.** Not once for an isolate, not once for a request: a configuration can be updated in place, and a role's memberships can change, while an isolate lives.
- **What it costs, timed apart from the connect.** The guard is one statement more on a client the call has just opened (P1a: one short-lived client per call, `order_d017.txt` line 29), so it follows the connect and postgres.js's own first reads. On staging the first query on a new connection took 140 ms and 93 ms (FINDINGS.md line 108), and a one-row read on an open connection p50 18 ms and p95 19 ms (FINDINGS.md section 3). That is arithmetic from the spike, not a measurement of the guard. Piece 6's tests and T-570's run time the connect and the guard separately, so neither hides in the other. If a measurement shows the guard breaking a budget, it comes back to the architect; nobody drops it or caches it on their own.

**What the answer covers.** Outside a transaction Hyperdrive may serve the call's later statements from other backends (FINDINGS.md section 4 saw 3), so the guard reads the backend that answers it. Everything it reads about the role is a property of the login the configuration stores: who it is, what it inherits, what it owns. A configuration is given one origin user [C5], no code switches role, and SET FALSE refuses a switch, so every backend the configuration opens should answer the same, and the guard can sit in the handle, outside db/repo's own transactions. That every backend logs in as the stored user is the one Hyperdrive property this design takes from Cloudflare's documents rather than from a measurement. Three things hold it: the live check measures it on many backends of each configuration before any traffic (section 4, piece 7); the guard samples it again in every call; and once the spike's configuration is deleted (section 3), no configuration on the account stores any user for staging's database but the two logins, so even a fault in Hyperdrive's pools could at worst put a call on the other side's login, not on the migrations' role. Under a role switch (options (b) and (c) below) the role would be transaction or session state: the guard would have to run inside each of db/repo's transactions, and could not cover a bare statement at all.

**`DB_SCHEMA`: one rule in every runtime.** The Worker's handle never sends a search path. While `DB_SCHEMA` is set it opens no client through either binding, wherever it runs (a deployed Worker, `wrangler dev`, the Workers test pool), and the call fails closed as with no binding; otherwise the guard expects `public`. So the handle has one path, the one staging runs, and needs no way to tell a test from a deployment.

- **Staging and production:** `DB_SCHEMA` is empty (`wrangler.jsonc` lines 50, 67, 126), so `client.ts` sends no `search_path` (lines 90 to 99, 121). The path is then the server's default for the login, not session state. The server's default read through the spike's configuration was `"$user", public` (FINDINGS.md line 54), so a schema named after a login would come first; the check catches it.
- **Branch previews:** `deploy-preview.sh` uploads a version of rosie-staging from the branch's commit with `DB_SCHEMA` set to `preview_<slug>` (`infra/scripts/deploy-preview.sh` lines 28 to 34, 166 to 167; `wrangler.jsonc` line 61). Through Hyperdrive that schema could travel only as a startup parameter, whose handling is not stated and not measured (Context). So a preview's database ports stay closed until open question 1 is answered. The rule lives in the branch's own code, which runs unreviewed on a preview (`deploy-preview.sh` lines 3 to 7), so it binds only a branch that leaves the handle alone: new task a takes the two bindings off previews (Consequences).
- **The Workers test rig:** each test file gets a database of its own with `DB_SCHEMA` empty, not a schema (section 4, "The Workers test pool"), so the rig runs the handle exactly as staging does.
- **Local runs:** `DB_SCHEMA` is empty (`wrangler.jsonc` line 67), and each binding's local string connects straight to the local server: with a local connection string "Hyperdrive's connection pooling and query caching do not take effect" (FINDINGS.md line 199, [C2]). One connection is one backend, and the check is sound.

**Why a local or CI test cannot prove this by itself.**

1. The local and CI login `rosie` is a superuser with BYPASSRLS (Context). It bypasses row-level security, passes every privilege check and may become any role. So a test that connects as `rosie` passes whichever client the handle picked, and "current_user is rosie_job" after a role option passes locally under any design (the T-1154 map's critics: `ops/reviews/T-1154-map/critic_size.txt` B2, `critic_collisions.txt` B1).
2. With the rig's own two logins, a local test proves the guard's logic and the policies against local roles. It cannot show which login staging's configuration stores, what that login owns or inherits on staging's server, or what the host added to it.

So three proofs, each for what the others cannot see:

- **The rig, locally and in CI** (pieces 5 and 6): the guard passes on the right login and refuses the superuser, crossed bindings, a login that inherits both roles, a login that is a member of the other role with INHERIT FALSE, a login that owns `businesses`, a login with a second membership (`pg_read_all_data`), a schema named after the login, and `DB_SCHEMA` set. After each refusal the call's code did not run and the row counts are unchanged.
- **T-1093's check, at each deploy:** the catalog of the real server and each configuration's stored user, before traffic.
- **The guard itself, in the deployed Worker, in every call,** and once the live check (piece 7).

- **The binding names carry the role,** so a mix-up shows in review, and code written against the spike's one name finds no binding and fails closed.
- **The login names are the same on every server** (local, CI, staging, production: each is its own server), so the guard and T-1093's check need no setting to know them. That also means a binding to the wrong server passes a name check: new task b (Consequences).
- **The spike's configuration is never bound in a deployed environment.** It stores the migrations' role (Context). The two new configurations are made with the API's create [C7], the operation the spike ran through wrangler (FINDINGS.md lines 33 to 36); nothing here rests on `hyperdrive update`, which was not run (FINDINGS.md line 40). Deleting the spike's configuration takes the migrations' password out of Cloudflare, where nothing needs it, and leaves no configuration on the account that stores a user row-level security does not bind (section 2). `cf.sh` refuses `delete` in any command (`infra/scripts/cf.sh` lines 17, 143 to 144; FINDINGS.md line 34), and one delete needs no script, so the user deletes it in Cloudflare's dashboard, by name. Until then T-567's test pins that its id is in no environment of `wrangler.jsonc`. This replaces DL-482's default (the stored role now, moved to a dedicated role later by an update in place).

**The script's rules (piece 2).** It follows T-1236's way with staging's secrets (`infra/scripts/make-staging-secrets.sh` lines 2 to 56; CQ-210) and the spike's `run.sh` (lines 14 to 27, 160 to 190), with one change the security review of round 1 asked for: **no command line, and no environment of a child process, ever holds a login's password.**

- **One Node process holds each password from start to end.** It makes the password, gives it to PostgreSQL only as the second bound value of one call, over its own connection, of a temporary function that runs `ALTER ROLE` inside the server, never in a statement's text (T-1371, on CQ-225's ruling; below), signs in once as the login with the password to check it (T-1369), and sends the password to Cloudflare's API in the body of one HTTPS request to the create operation, `POST /accounts/{account_id}/hyperdrive/configs`, whose `origin.password` is "write-only" and is never returned [C7]. Wrangler never sees it: no `--origin-password`, no `--connection-string`, now or for any later change (that goes to the API's edit, `PATCH .../hyperdrive/configs/{hyperdrive_id}` [C9]). Not printed, not logged, not written to a file, not in `.dev.vars`, not exported; the variable is cleared after the request. Its test runs the script against stand-ins (as T-1236's tests run behind the real `cf.sh`: commit 19ab9b5) and checks that the value the stand-in API received appears in no argument and no environment of any child process, and in none of the script's output.
- **The API's token is the Rosfield sign-in's,** fetched with `wrangler auth token --json` ("Retrieve your current authentication token or credentials for use with other tools and scripts"; an OAuth token is "automatically refreshed if expired" [C11]) through `cf.sh`, which points wrangler at the sign-in in `~/.config/rosfield` (`cf.sh` lines 2 to 5, 231). The Node process reads it from that child's standard output, a pipe, and holds it in memory only; it is removed from any error text and never printed. Wrangler hands back `CLOUDFLARE_API_TOKEN`, or a key and email, before the sign-in [C11], so that child's environment drops those three names and `STAGING_DATABASE_URL`, and the script accepts only the type `oauth`. The sign-in can create a configuration (FINDINGS.md line 36); the create asks for "Hyperdrive Write" [C7]. The account is the one `cf.sh` pins (line 23).
- **It lists first and makes only what is missing** (T-567's lead note, DL-476): `cf.sh hyperdrive list`, read by the parser. A configuration of either name that exists is left exactly as it is, never replaced: the script prints `<name> already exists: id <id>, caching <caching>` and checks that its stored user is that name's login; another user stops the run. With both present, it connects to nothing and makes no password.
- **Before any password, on the one connection that will send it** (as the migrations' role, from `STAGING_DATABASE_URL`, read by name and never shown; a pooled host refused as `run.sh` lines 166 to 172 refuse it; postgres.js with debug off): it refuses a server older than PostgreSQL 16; prints the server's version beside `pg_postmaster_start_time()` (for T-1255's persistence proof), `max_connections` and each login's shape as it finds it (names and flags, never a value); and checks the server's logging. It first tries to set, for its own session only, `log_statement` to `none` and `log_min_error_statement` to `panic`; each needs a superuser or the `SET` privilege on the setting [P6], so a refusal there changes nothing. It also sets `debug_print_parse`, `debug_print_rewritten` and `debug_print_plan` off and `log_parameter_max_length_on_error` to 0, which any role may. Then it reads the session's values and **refuses to make a password when any would write the `ALTER ROLE`'s text, or the call's bound values, to the server log or keep them** [P6]: `log_statement` `ddl`, `mod` or `all` ("`ddl` logs all data definition statements, such as `CREATE`, `ALTER`, and `DROP`"); `log_min_error_statement` `error` or a lower level (a failing statement's text is logged; "The default is `ERROR`"); `log_min_duration_statement` 0 or more; `log_min_duration_sample` 0 or more with `log_statement_sample_rate` above 0; `log_transaction_sample_rate` above 0. It fetches the token next, and runs piece 1's file. These rules, and those added since (the two `debug_print` settings by T-1252; `log_min_error_statement` `log`, and pgaudit naming `role`, `ddl` or `all`, by T-1271), still stop the run. **T-1371 adds, on CQ-225's ruling (DL-733):** `debug_print_plan` on, or `log_parameter_max_length_on_error` other than 0, each read back after the script's own `SET` ("Zero (the default) disables including bind parameters in error messages" [P6]); `pg_stat_statements.track` `all`, which also tracks "nested statements (such as statements invoked within functions)" [P11] and so would keep the `ALTER ROLE` the function runs, while `top` or `none` goes on, since `top` keeps only the call's text, which holds no value, and `track_utility` is printed and decides nothing; anything that could record the call's plan or values: `auto_explain.log_min_duration` set and not -1, any `pg_stat_monitor` or `pg_store_plans` setting present (each read with `missing_ok`), or `log_statement_stats`, `log_parser_stats`, `log_planner_stats` or `log_executor_stats` on [P12], whose reports reach the server log with the context of the statement they measure; pgaudit loaded with any class but `none`, or with `pgaudit.log_parameter` on; and no `TEMPORARY` privilege on the database, or no `plpgsql`, which the temporary function needs. Printed for the record, deciding nothing: `log_min_messages`, `log_error_verbosity`, `log_lock_waits`, `deadlock_timeout`, `log_parameter_max_length`, `password_encryption` and, where the role may read it, `shared_preload_libraries` (names only). T-1369 answered with a SCRAM-SHA-256 verifier in place of the password, but Neon takes none: "Passwords must be supplied in plain text but are encrypted when stored. Hashed passwords are not supported." [N6]. So the ruling keeps the plain password out of every statement's text instead.

`create function pg_temp.<fn>(login text, secret text) returns void language plpgsql set search_path = pg_catalog`, whose body runs `execute pg_catalog.format('alter role %I password %L', login, secret)` and holds no value, and whose handler, `exception when others or query_canceled` (`OTHERS` "matches every error type except `QUERY_CANCELED` and `ASSERT_FAILURE`" [P16]), raises another error with the caught SQLSTATE and the script's own words, never the caught message, detail, hint or context, since the context of an error inside `EXECUTE` names the statement it ran, password included; ## Alternatives not chosen

- **(b) One login that switches with `SET LOCAL ROLE` in each transaction, through a named hook.** `SET` for the length of a transaction is documented [C3], and the spike measured a transaction-scoped setting (FINDINGS.md section 4), though not a role. It is rejected for what it needs elsewhere:
  - The login must be able to become both roles, against 0012 lines 13 to 14 and T-1093 as written.
  - A forgotten switch runs as the login. If the login inherits both roles, both sets of policies apply, "combined using `OR`" for permissive policies [P2], so a Tool API read with no scope sees every business. If it is today's stored login, it bypasses row-level security. Only a login that inherits nothing fails closed, and that login would have to be made anyway, so (b) saves no live step.
  - A login with SET on both roles can also run a plain `SET ROLE`, which outlives the transaction on a pooled backend; which reset Hyperdrive runs is not stated [C3], so such a mistake could reach another client's statements. Under (a) SET FALSE refuses it.
  - db/repo has no place for the hook. Each call opens its own transaction or sends a bare statement (Context), so every K-05 call's code would change, every bare read would become a transaction (on staging a transaction of four round trips took p50 72 ms against 18 ms for one statement: FINDINGS.md section 3), and each new call would have to remember.
- **(c) A `role` startup parameter, as the local tests set.** It is per-session state, unsupported unless documented [C4]; startup parameters are not mentioned on the pages read [C3][C4]; it was never measured (FINDINGS.md line 35); and the login would need SET on both roles. If Hyperdrive dropped the parameter, the call would run as the stored login, which today is the migrations' role: it fails open.
- **Binding the spike's configuration now and moving to a dedicated role later** (CQ-208's earlier default; DL-482). Staging holds test data only, but every call would run past the policies, so staging would prove nothing about row-level security, and T-570's pass would not show production's shape (DL-492, ruling 2).
- **One login for both sides, as `rosie_job`, with the scope checks alone.** The Tool API would lose `rosie_app`'s "no scope, no row" and its narrower grants (0012 lines 15 to 20; `scope.ts` lines 8 to 12).
- **Forcing row-level security on the tables' owner.** FORCE binds an owner, but not a superuser or a role with BYPASSRLS [P2]; it changes every table (a K-04 change); and the Worker would still hold the role that can drop them.
- **The logins in a migration.** 0012 lines 13 to 14 leave the login to the deploy. A migration runs in every schema of a server (0012 lines 12 to 13) and its text is public and frozen, so no password can be in it, and the passwords would still need a script. One SQL file that the staging script and the rig both run is one source, and T-1093's check proves it on the server.
- **The password in wrangler's arguments** (`--origin-password` or `--connection-string` [C5], as the spike did: `run.sh` lines 23 to 24, 177 to 178). It sits in the process list while wrangler runs; DL-482 accepted that for the spike's one step, and round 1's security review did not accept it for the logins. The API takes the password in a request body [C7], so nothing needs a command line. A token made by hand for the API was not chosen either: the sign-in already creates configurations (FINDINGS.md line 36), and a second credential would be one more for the user to make and keep.
- **A schema per Workers test file through `DB_SCHEMA`, with a switch that lets the handle send a search path in tests** (a variable only the pool sets, or a check of the binding's host). The handle would carry a path staging never runs and a switch a branch could set, and what a binding's host looks like in the pool is not in the pages read. A database per file keeps one path.
- **Turning the spike's configuration into one of the two with `hyperdrive update`.** The command exists [C5] and was not run (FINDINGS.md line 40); a create was. A new name also says which login it stores.
- **Running the guard inside each of db/repo's transactions.** It would change db/repo and still miss its bare statements. Under (a) the role is the configuration's, so the handle is the place.
- **A guard that checks the name alone, or once for an isolate.** A name says nothing of what the login inherits or owns, and an isolate can outlive a change to a configuration.
- **A SCRAM-SHA-256 verifier in `ALTER ROLE`, in place of the password** (T-1369's route, never run live). It gave PostgreSQL no password at all, but Neon's page says "Hashed passwords are not supported" [N6], so staging would most likely refuse it, or seem to take it on behaviour no source covers (CQ-225's ruling, DL-733). It left the script with its tests (T-1371).
- **The password in `ALTER ROLE`'s text, with `pg_stat_statements` reset after.** The text would be kept until the reset, readable by the role that ran it, superusers and `pg_read_all_stats` [P10]. Only the CTO could accept that exposure, and only if both routes fail (the ruling).
- **A reset in Neon's console.** The password would be on a screen, and then in the environment of whatever carries it to Cloudflare (the ruling).
- **Neon's API `reset_password` on a login made with SQL** (the second route, not built). It needs a Neon API key the user makes for that one run and revokes after, and the ruling's probes F1 to F6 first. It is carded only if staging refuses this route's login check or a stop rule cannot be met, after CQ-225 returns to the architect and the security reviewer.
