## The local merge-check (T-1111, DL-190)

GitHub Actions refuses to start jobs on this account (DL-165, DL-186), so the merge-check runs on the build Mac instead, with the same checks. The lead runs it once per branch before a merge (DL-063, DL-065), one run at a time and not beside heavy builder runs (DL-164):

```sh
git fetch origin
npm run merge-check:local -- task/T-xxx
npm run merge-check:local -- task/T-xxx --ai-change   # the branch changes what the AI does
```

`--verbose` also prints every step's output (it always goes to the log). A full run on a quiet Mac takes a few minutes; the parity shards add more when a parity input changed.

### What it runs

It reads `.github/workflows/merge-check.yml` at `origin/main` (the file `gh workflow run merge-check.yml` runs, from the default branch) with a small YAML reader for that file's shape, and runs its steps in the file's order. The step list is never written down a second time, so the two cannot drift: a new or changed run step runs as written, and anything the runner cannot mirror (an action other than checkout and setup-node, an unknown key, an expression outside the `inputs`, `matrix`, `job`, `needs` and `steps` contexts) fails the run before any step starts. The runner then needs a change, in the same pull request as the workflow's.

1. The merge-check job, from its postgres service on:
   - The service: a throwaway database of the run's own (below).
   - The branch-name check, as written (the same regex).
   - `actions/checkout`: a fresh `git clone` of this repository's git store by path (no network, no token), with `origin/main` and the branch set to what this repository holds, then `git checkout --force -B <branch> origin/<branch>` as checkout does. The clone's push URL is a dead end, so nothing can be pushed from it.
   - The rebase onto `origin/main`, as written: a conflict fails the run (the lead hands the branch back as a rebase step).
   - `actions/setup-node`: `node --version` must match `.nvmrc` (22 matches any 22.x). The Mac's Node is used; nothing is installed.
   - Every run step, as written: `npm ci`, `contracts:types`, `contracts:check`, `format:check`, `lint`, `typecheck`, `npm test`, the CI script tests, the three guards, `migrate`, `test:scripts`, `test:integration`, `test:scenario`, `test:e2e`, then the eval smoke slice line with `--ai-change`, and the job summary (which runs after a failure too, as `if: always()` says).
2. The parity-inputs job: its rule (`git diff --name-only origin/main...HEAD` over the parity inputs, with package.json judged by origin/main's `parity-inputs.mjs` when it is the only one: below), in the same clone.
3. The parity-shard job, only when that rule found a changed input: shards 1/3, 2/3 and 3/3, one after another. As the matrix's `fail-fast: false` says, every shard runs even when one fails.

Each run step runs as Actions runs a bash step: `bash --noprofile --norc -eo pipefail <script>`, with `CI=true`, the job's and the step's `env`, `${{ }}` filled in, and `GITHUB_STEP_SUMMARY` and `GITHUB_OUTPUT` as local files. Each job's `timeout-minutes` holds. The first failing step stops the run, and the run fails.

Where it differs from GitHub's runners, and why the bar is the same:

- All jobs share one clone. The leading steps a later job shares with an earlier one (the branch check, the checkout, the rebase, the Node check, `npm ci`) are done once and shown as `reused`; a step that differs runs again in the clone (parity-inputs' shorter rebase step does: on a rebased branch it is a no-op).
- Jobs run one after another, and a failure in the merge-check job skips the parity jobs (on GitHub they would still run beside it). The run fails either way.
- Steps get this shell's environment without git, GitHub, Cloudflare, npm, database or key variables, and git reads none of the user's own configuration. No secret, `.env` or `.dev.vars` is read.

### origin/main and the branch

- `origin/main` is this repository's remote-tracking ref (`refs/remotes/origin/main`) as last fetched, so run `git fetch origin` before each run. The local `main` branch is never used.
- The branch is the local branch `refs/heads/task/T-xxx`, else `refs/remotes/origin/task/T-xxx`. The result file names the ref used and its head; the lead checks that it is the pull request's head.

### The database

The merge-check job's service (`postgis/postgis:17-3.5`) is a database of the run's own in the local rosie-pg container (`npm run db:up`): `mc_<UTC time>_<6 hex>` on `127.0.0.1:54329`, with the local, non-secret `rosie` credentials of factory spec section 4. It is made from `template_postgis`, as the service image makes its database, and the run first checks that the local server runs the image's PostgreSQL and PostGIS versions (17 and 3.5). `DATABASE_URL` points at it for the merge-check job's steps, as the workflow's job `env` does; the parity jobs get no `DATABASE_URL`, as on GitHub. After the run, pass or fail (Ctrl-C included), it is dropped with `drop database ... with (force)`. The runner never drops any other database, and the dev database `rosie` is never touched.

`MERGE_CHECK_PG_URL` can name another PostgreSQL server on this Mac (its maintenance database; local hosts only); the tests use it.

### The result

Each run writes `scratch/ci/<branch, "/" as "-">-<short branch head>/` (git-ignored; a rerun of the same head replaces it):

- `merge-check.log`: every step's command and full output.
- `result.json`: `branch`, `branch_ref`, `branch_head`, `origin_main`, `rebased_commit` (the commit checked: the branch rebased onto `origin/main`, never pushed), `ai_change`, `result` (`success` or `failure`), `failed_step`, the times, the database, `jobs`, and `steps` (each step's job, name, command, status (`success`, `failure`, `skipped` or `reused`) and seconds).
- `summary.md`: the job summary the workflow's own steps write.

Exit codes: 0 only when every step passed; 1 when a step failed; 2 on a usage error; 130 when interrupted.

### Clean-up

A run that is killed outright (SIGKILL, a power cut) cannot drop its database or remove its clone. Databases: `npm run db:psql`, then `\l mc_*`, then `drop database "mc_..." with (force);` for each. Clones: `rosie-merge-check-*` folders in the system temp folder.

### Tests

`npm run test:ci-scripts` runs `local-merge-check.test.mjs` with the other CI script tests (`node --test infra/ci/local-merge-check.test.mjs` runs it alone). Its run tests need the local PostgreSQL (`npm run db:up`), or `DATABASE_URL`'s server inside a merge-check run: each run makes and drops a database of its own.

## The parity inputs (T-1067, T-1078, T-1320)

`merge-check.yml`'s parity-inputs job decides whether the parity shards run: only when a parity input changed on the branch rebased onto `origin/main`. The inputs are `compiler/src`, `fixtures/master`, `vitest.config.ts`, `package.json` and `package-lock.json`, listed in that step. Since T-1320 (DL-589, DL-600), when `package.json` is the only input that changed, `parity-inputs.mjs` judges it: the change is an input unless it is confined to the scripts object and leaves every script the parity run runs unchanged. Those scripts are `test:parity` and the root install scripts `npm ci` runs before it (`preinstall` to `postprepare`, and `dependencies`), each with its `pre` and `post` script, and every script their lines name (`npm run x`, `node --run x`, `npm:x`, npm's own `npm t` and the like), followed to the end on both sides. Every other field still counts, compared as parsed JSON with key order. A manifest that is not a JSON object, a scripts value that is not an object of strings, an odd script name, or a parity script line naming scripts through `$`, a backtick or a pattern makes the change an input. So T-1303's `check-tester:token:make` line, or T-1310's `pretest:ci-scripts`, runs no shard.

The step runs the rule as `origin/main` holds it (`git show origin/main:infra/ci/parity-inputs.mjs`), as it holds the workflow, never the branch's copy, so a branch cannot change the rule that judges it, and a change to the rule acts once it merges. It prints `scripts-only` or `input`, with its reasons on standard error; any other answer counts `package.json`, and a rule that fails (exit 2 on a git or usage error) fails the step, so the shards are never skipped by a broken rule. It does not follow a script reached only through another file (a shell script, a test, the Vitest config); today `test:parity` runs `vitest run --project parity` and `npm ci` runs no root script. The local merge-check runs the same step, so the same rule. `parity-inputs.test.mjs` runs that step, as the file holds it, in throwaway repositories, with a case for each shape: a script line alone, a dependency, devDependency or overrides change, `test:parity` or a script it runs, any other field, the lockfile, `compiler/src`, `fixtures/master` or the Vitest config, and a mixed change. `parity-placement.test.mjs` pins the list.

## The phone scan (T-1317)

The repository is public (DL-436), and no real phone number goes in it (DL-542, DL-581). `phone-scan.test.mjs` reads every file `git ls-files` lists (a symbolic link as its own target path, never the file it points to) and fails on any phone number outside the fiction ranges. One is +1, an area code that is not toll-free, then 555-0100 to 555-0199: in a toll-free area code 555 is not reserved, so such a line is no fiction (T-1359; `adapters/src/shared/samples.ts` and the Linq double's webhooks keep their own copy of the range, which still takes a toll-free area code). The others are Ofcom's UK numbers for drama (DL-616), nineteen blocks of a thousand that `phone-scan.mjs` lists as Ofcom's table writes them, such as London's 020 7946 0000 to 0999, the mobile 07700 900000 to 900999 and the no-area 01632 960000 to 960999; a UK number is read when written with +44. Northern Ireland has no block: the one the table gave was reallocated for real use, and Ofcom's current one cannot be confirmed from its own page (DL-632), so a Northern Ireland number fails like any other. It reads the shapes in `phone-scan.mjs`, which `wrangler-env.test.mjs`, `rosfield-test-route.test.mjs` and the chat-link spike's test (`web/spikes/chat-link/chat-link.test.mjs`) also import: a + and 7 to 15 digits with spaces, dots, dashes or brackets between them, and a North American number without the +, its area code bracketed or not, separated or not, with a 1 or none. The plus may be URL-encoded (`%2B`) or escaped (`\u002B`, `\x2B`), and a space, dash or dot between groups URL-encoded (`%20`, `%2D`, `%2E`). A number starts where no letter or digit stands right before it, or right after an escape (`\n` and the other one-letter escapes, or a whole `\uXXXX` or `\xXX`, never at its own hex digits) or a URL-encoded character, and ends where no digit follows. So none is read inside an id, a base64 blob, a sum or a longer run of digits (T-1304), and a North American number right after a plus is the + form's, read once. A North American number ends right before a letter only when it is separated: its groups split, its area code bracketed, or a 1 and a separator before ten digits in a row. Ten digits in a row right before a letter stay an id's (T-1332, T-1344). A failure names each file and line, never the number. A new test value is taken from a fiction range, so it needs no entry.

`phone-scan-exceptions.mjs` lists the deliberate inputs a file holds outside the ranges, each with its file, its kind and why it is no real number. A listed number passes only at its own file, and one its file no longer holds fails the run, so the list stays exact. The test checks each kind against the digits: an impossible code (an area code or exchange that starts with 0 or 1), the 555 exchange outside the fiction block under area code 555, which serves no area (since NANPA's 2016 change such a line in a real area code may be a person's, so none is listed there, T-1359; never the directory-assistance line or the one national-use line NANPA kept, DL-632, T-1344), a wrong length (the first 6, 8 or 9 digits after +1 of a fiction-block number, such as the block's first digits before a template's last ones, so only a fiction number or one under area code 555 begins with them, never a real number's first digits: area code and exchange 555, or an area code the fiction range takes with exchange 555 and the line's 01 and one more digit or none, T-1359; never seven, a local number's length, DL-636, and never ten or more, T-1344), not a phone number (an integer, a digest, a coordinate or a count, named in its why), and a public line (DL-616). A public line is one of four published public service lines the master's own trade text gives a customer: Poison Help, the National Domestic Violence Hotline, the National Elder Fraud Hotline and HUD's housing counseling line. Each entry names the line and its operator. It is listed only at the files that hold it: the master's trade files under `fixtures/master/engine/work/prof`, the forms built from them under `fixtures/v1/forms`, `fixtures/v1/KNOWN-STALE.md` and `compiler/src/slots/slots.test.ts`. The same number anywhere else fails. A number that could be someone's is never listed: it is a finding for its file's owner, who swaps it for a fiction-range one. The list writes each number with underscores (`+1_055_555_0142`), so it holds nothing the scan reads. The test also plants lines in throwaway repositories: an out-of-range line fails with its file and line, a listed number passes only at its own file, a public line fails at any file but its own, a London number in Ofcom's drama block passes and the line past it fails, and an untracked file is never read. Each shape T-1332 and T-1344 read passes with a fiction line and fails with the line past the block, and each case kept unread (an id's digits, an escape's own hex digits, a longer run of digits, a plus inside a word or a sum) passes with the line past the block. In every area code from 200 to 999, built when the test runs, a 555 line is of its kind under area code 555 only, a wrong length's first digits only when they begin a fiction-block number, and a fiction-block line is fiction only outside the toll-free area codes, where a planted one fails (T-1359).

## The Workers pool's messages (T-1207, DL-420)

The `workers` and `e2e-workers` projects run their tests inside workerd: `@cloudflare/vitest-plugin`'s pool sends each test file's runner its modules over one WebSocket, and workerd closes that socket on a message over 33,554,432 bytes (32 MiB; close code 1009, which Vitest reports as "Worker exited unexpectedly"). With Vitest's module cache on disk (`fsModuleCache`, on by default), a new runner got every already-transformed module of its graph in one message: 33,125,602 bytes for hop9 on 5d69f31, and over the limit (a crashed runner) once test-phone's graph grew by gateway/pages' test support. So both projects set `fsModuleCache: false` in `vitest.config.ts`: each module goes in its own message, and the largest is the largest single module (the Tool API's generated validators, 13,213,756 bytes). The other projects keep the cache.

`workers-pool-messages.test.mjs` guards it: it checks the socket's limit in workerd at `wrangler.jsonc`'s compatibility date, then runs test-phone's and root.worker's Workers tests (the largest graphs) in one Vitest process with one worker and every pool message measured (`workers-pool-messages.run.mjs`), and fails when either project caches modules on disk, when one message carries several modules, or when a message passes 25,165,824 bytes (24 MiB, 75% of the limit), naming the module. It needs the generated validators (`npm run build:validators`, which `npm test` runs first). A module that nears the budget is split; the other way out, measured but not taken, is workerd's `increase_websocket_message_size` compatibility flag in the pool's `miniflare` options, which raises the limit to 134,217,728 bytes (128 MiB) but keeps one message per graph, growing with every join.

## The db/ syntax guard (T-1329, DL-641)

Node runs some of db/ straight from TypeScript, with no bundler: the seed runner and the scripts and CI tests that load db/repo (DL-612). Node's type stripping cannot run parameter properties, enums or namespaces, so one such line in that chain crashes the script at import (train 143). `npm run typecheck` therefore runs a second program, `tsc --noEmit -p db/tsconfig.erasable.json`, which extends the root config with `erasableSyntaxOnly` over db/ minus its `*.test.ts` files (Vitest's transform runs those). The config is deliberately not named `tsconfig.json`, so ESLint, Vitest and wrangler keep reading the root one; a `db/tsconfig.json` had ESLint type db/ twice and run out of heap.

`db-erasable-syntax.test.mjs` guards it: it builds a throwaway repository from the real three tsconfig files and the real typecheck line, then plants a parameter property, an enum and a namespace in db/ files (each fails with TS1294 at its own line), the same syntax in `runtime/src` (passes) and in db/ test files (passes). It also checks that no `db/tsconfig.json` exists.
